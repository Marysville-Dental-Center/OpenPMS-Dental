# Port note: S3a-6 (SOAP clients without System.Web.Services)

Package S3a-6 of stage 3a of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-6 row, section 8 item 6,
decision 12, open point O-6, critique W1): branch `net10/s3a6-1` from `main` (`c01ea6fe4`). The five vendor web references of the
business layer no longer use `SoapHttpClientProtocol`: their generated `[XmlType]`/`[SoapType]` data classes stay, the proxies are
deleted, and the 14 document/literal operations the program uses plus DentalXChange DCI's rpc/encoded `lookupEligibility` go through one
hand-written caller, `OpenPmsDentalBusiness/WebServices/SoapCaller.cs` (`HttpClient` + `XmlSerializer`), with one client class per service
in `WebServices/SoapClients.cs`. No schema change, no new package or reference, nothing downloaded, no program started, no real endpoint
called: every test answers in process.

Commits: `7687144aa` (the caller, the clients and the envelope-equivalence tests, recorded against the generated proxies while they still
existed), `da15e7dd2` (the proxies go, the callers use the clients, the VDXC2 fake becomes an `HttpMessageHandler`), `1599aac57` (the fake
ITS endpoint, the DCI request and response tests), and this note with the plan's status line.

## 1. The caller

`SoapCaller` reproduces what `SoapHttpClientProtocol` did for these services, from the .NET Framework reference source:

- **Mapping.** Each operation is a method of a `SoapClient` subclass that carries the same attributes its generated proxy method carried:
  `[SoapOperation(action, RequestNamespace, ResponseNamespace)]` in place of `[SoapDocumentMethod(..., Use=Literal,
  ParameterStyle=Wrapped)]`, and the same `XmlElement`/`XmlArray`/`XmlArrayItem`/`XmlIgnore` attributes on the parameters and the
  return value. From them the caller builds the members as `SoapReflector` did (one `XmlReflectionMember` per parameter with
  `new XmlAttributes(parameterInfo)`; the return value named `<method>Result` unless its `XmlElement` names it, `IsReturnValue`, `XmlRoot`
  cleared) and imports them with `XmlReflectionImporter.ImportMembersMapping(name, namespace, members, hasWrapperElement:true, rpc:false,
  openModel:false, Write/Read)`, one importer per client whose default namespace is the binding's (`[SoapBinding]` in place of
  `WebServiceBinding`) and which knows the client's `XmlInclude` types, as `SoapClientType` did. `XmlSerializer.FromMappings` is called once
  per operation (request and response together), because a serializer assembly keys its mappings by member types and `validateClaim` and
  `lookupEligibility` share theirs (the proxy gave each mapping an internal key). The serializers are built once per client type and
  cached. These are the APIs WCF's `XmlSerializerFormat` uses on .NET, so they exist there too.
- **Envelope.** An `XmlTextWriter` over UTF-8 without a byte order mark: the XML declaration, `soap:Envelope` declaring `soap`, `xsi`,
  `xsd` (and for rpc/encoded `soapenc`, `tns`, `types`, with `soap:encodingStyle` on the body), no header, the body.
- **HTTP.** POST, `Content-Type: text/xml; charset=utf-8`, `SOAPAction: "<action>"` (quoted), the user agent the proxies sent by default
  (`Mozilla/4.0 (compatible; MSIE 6.0; MS Web Services Client Protocol 4.0.30319.42000)`; NewCrop's client still sets
  `ProductIdentity.UserAgent`), the client's `Timeout` (100 000 ms by default; NewCrop 3 000 and 15 000), no automatic redirects and no
  cookies (as `HttpWebClientProtocol`), the system proxy, and the Windows login only for an address on localhost at a port of 1024 or more
  (the proxies' `IsLocalFileSystemWebService`). One shared `HttpClient`; `SoapCaller.HttpHandlerForTests` replaces it in tests.
- **Response.** As `SoapHttpClientProtocol.ReadResponse`: a status of 300 or more other than 400 and 500 is a `WebException`
  (ProtocolError); a response that is not `text/xml`, or is empty, is a `WebException` for 400 and an `InvalidOperationException`
  ("Client found response content type of '...', but expected 'text/xml'." and a new line) otherwise. The failure text is
  `RequestResponseUtils.CreateResponseExceptionString`'s: "The request failed with HTTP status {code}: {reason}." for 400 and above
  other than 500; otherwise the body read with its charset (or else the ANSI page, `ODEncodings.GetAnsiEncoding()`, which the
  proxies' `Encoding.Default` was on .NET Framework, and its byte order mark) and HTML-decoded, as "The request failed with the error message:" /
  "--" / body / "--.", or "The request failed with an empty response." when there is none (an empty 200 `text/xml` answer, an empty 500, a 302). `SoapEnvelopeTests` checks a 500 HTML page, an empty 500, an empty 200
  `text/xml`, an empty 302 and a 503 against the texts the .NET Framework 4.8 proxy threw for the same responses from a loopback fake
  (fix round S3a-6-3). A timeout gives the proxy's text too: "The request was aborted: The operation has timed out." with status
  Timeout. The envelope is read
  with an `XmlTextReader` honouring the charset, DTDs prohibited, no resolver; the header is skipped; a fault is thrown; otherwise the
  response members are deserialized. A request that fails is a `WebException` (the inner `WebException`'s status when there is one) and a
  timeout is a `WebException` with status Timeout, where the proxies threw `WebException` too.
- **Faults.** `SoapFaultException` in place of `SoapException`: `Message` is the faultstring, `Code` the faultcode resolved to its
  namespace, `Actor`, and `Detail` the detail element (null when the fault has none, as `SoapException`'s was). `ClaimConnect`'s two
  catches (`Benefits270`, `GetPayerList`, the lines 304 and 817 of the plan) catch it and build the same text
  (`"...Claim Connect:  "+Message+"\r\n\r\n"+Detail.InnerText`); `Detail?.InnerText` there means a fault without a detail no longer throws
  `NullReferenceException` (the proxy gave `SoapHeaderException` with a null `Detail` then).

## 3. The DCI rpc/encoded body

`XmlSerializer`'s SOAP-encoded mappings (`SoapReflectionImporter`) cannot be relied on in .NET, so `DciSoapClient` writes the body by
hand, exactly as the old proxy's mapping wrote it (recorded in `tests/VDXC2Tests/SoapEnvelopes/Dci.lookupEligibility.request.xml`):

```xml
<soap:Body soap:encodingStyle="http://schemas.xmlsoap.org/soap/encoding/">
  <tns:lookupEligibility><in0 href="#id1" /><in1 href="#id2" /></tns:lookupEligibility>
  <tns:Credentials id="id1" xsi:type="tns:Credentials">
    <client xsi:type="xsd:string">...</client><password xsi:type="xsd:string">...</password>
    <serviceID xsi:type="xsd:string">...</serviceID><username xsi:type="xsd:string">...</username>
    <version xsi:type="xsd:string">1</version>
  </tns:Credentials>
  <tns:Request id="id2" xsi:type="tns:Request"><content xsi:type="xsd:string">EligRequest XML as text</content></tns:Request>
</soap:Body>
```

`tns` is `http://www.dentalxchange.com/webservice`, the envelope also declares `soapenc` and `types` (`.../webservice/encodedTypes`), a
null field is `<name xsi:nil="true" />`, a null part `<in0 xsi:nil="true" />`. The answer is read from `lookupEligibilityReturn`, inline
or as an `href` to a multiRef element after the wrapper (Apache Axis), and its `content` (nil gives null) is what
`ProcessEligibilityResponseDentalXchange` reads; a missing or nil return gives null, as the proxy did.

## 4. The equivalence proof

`tests/VDXC2Tests/SoapEnvelopeTests.cs`, in `7687144aa`, called each old proxy through a `WebRequest.RegisterPrefix` fake (the VDXC2
`FakeWebRequest`, registered for `https://soap-capture.example.test/` only) and each new client through `SoapCaller.HttpHandlerForTests`,
with the same synthetic arguments and the same canned response, for all 15 operations and four extra cases (nulls in DWS and DCI, a null
DEA narrative, `sendCompleteAttachment` with the release flag, DCI's inline answer). For every case:

- the envelopes were **the same bytes** (and canonically equal: element and attribute names with namespaces, `xsi:type` resolved, text);
- method, content type and SOAPAction were the same, and the user agent was each proxy's default;
- the canned response read into the same objects (serialized and compared);
- faults (with a detail, without, from DCI) gave the same message, code, actor and detail.

The run recorded the old proxies' requests, headers and results in `tests/VDXC2Tests/SoapEnvelopes` (`OPMS_SOAP_RECORD=1`). Since
`da15e7dd2` the same tests check the new clients against those recordings (canonical XML, so another runtime's serializer may declare
namespaces elsewhere), and the fault expectations are the ones the proxies gave. The default addresses and the timeout were compared with
the proxies' too (as `Uri`: the proxies gave their `Url` back through `Uri.ToString`, which drops the settings' `:443`).

Further tests of the new clients:

- `tests/VendorDirectTests/ChangeHealthcare/ItsSoapTests.cs`: a fake ITS endpoint (only the two ITS hosts, HTTPS) checks what
  `EmdeonMedical` sends (test and production addresses, SOAPAction, login, message type MCT/HCD and the report codes, file name, and the
  base64 zip with the batch at its root) and answers with an `ItsReturn` (accepted, rejected with rollback, reports saved, extracted and
  removed from the mailbox, an error).
- `tests/VendorDirectTests/DentalXChange/DciEligibilityTests.cs` with `DciLookupEligibilityResponse.xml`, a synthetic Axis multiRef answer
  (made-up values, no real patient, subscriber or login): the rpc/encoded request (element, namespace, parts and their types, field
  order, nil), the recorded answer read into the `EligBenefitResponse` that `FormInsPlan` and `FormEligibilityResponseDisplay` read, an
  inline "not eligible" answer and a fault.
- VDXC2's partner service fake is now `FakeDeaHandler`, an `HttpMessageHandler` installed as `SoapCaller.HttpHandlerForTests` per test,
  refusing every request while off and every host but DentalXChange's two partner service hosts.
- `tests/CLAIMDCMTests/WiringTests.cs`: `CreateAttachment` refuses a DICOM file before `new DeaSoapClient()`.

## 5. Project and release

The five `WebReferenceUrl` items left `OpenPmsDentalBusiness.csproj`; the Middle Tier's (`OpenDentalServer`) stays until 3b, and so does
the `System.Web.Services` reference its proxy needs. With it, `GenerateSerializationAssemblies` Auto still runs SGen for a Release build,
so `OpenPmsDentalBusiness.XmlSerializers.dll` is still built (critique W1); it now holds the Middle Tier proxy's serializers only, and the
vendor clients' serializers are generated at run time, once per client type, on first use. The folders keep their WSDL/XSD and the
`Reference.cs` with the data classes (a note at the top of each says the proxy went). The Release dry run is in section 6.

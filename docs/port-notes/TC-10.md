## 1. The blocker: TestProbeHost in the x64 test build

TC-9a's x64 build of ToothChartImageTests stopped at `tests/TestProbeHost` with NETSDK1047 ("Assets file ... doesn't have a target for
'net48/win-x64'", `.git/od-tools/test-results/tc9a-x64-toothchartimage.txt`). The cause: the SDK gives a .NET Framework **exe** the runtime
identifier of its `PlatformTarget` (win-x86 from the repository's x86, win-x64 when the lane builds with `PlatformTarget=x64`), and the build
needs that identifier's target in the project's assets file. The lane restores as the x86 build does, so TestProbeHost's assets file had
`net48` and `net48/win-x86` only. A library (every other project of the x64 test builds) gets no runtime identifier, which is why S3a-12's
and S3a-15's x64 builds never met this.

The fix is in the repository, the lane is unchanged:
- `tests/TestProbeHost/TestProbeHost.csproj`: `<RuntimeIdentifiers>win-x86;win-x64</RuntimeIdentifiers>`, with a comment. The restore (x86, in
  both builds) now writes both targets.
- `tests/TestProbeHost/packages.lock.json`: the lock file gains the empty `".NETFramework,Version=v4.8/win-x64": {}` target (TestProbeHost
  has no package). Written by hand in NuGet's order; the lane's locked restore (`RestoreLockedMode=true`) accepts it, so it is what NuGet
  writes.
- The x86 build is unchanged: the build still takes `win-x86` (the restore's extra target is not used), the output folders do not change
  (`AppendRuntimeIdentifierToOutputPath=false`), and the full lane build has 0 errors. `ChartBitnessTests.NormalBuild_StaysX86` pins that no
  project of the chart's stack, TestProbeHost included, sets another `PlatformTarget`.

In the x64 test build TestProbeHost is now built for x64 (`bin\x64\Debug\`, PE32+), so the second process loads the 64-bit test assembly:
the determinism test's second process ran and gave the in-process bytes in both bitnesses.

## 3. The x64 pictures and their reason

The tolerances are unchanged. A picture that the 64-bit process draws beyond them has its own copy in `Baselines/wpf-net48-x64/` (163
pictures) or `Baselines/simple2d-net48-x64/` (18), recorded by the existing recorders in a full x64 run of the assembly
(`OPMS_RECORD_WPF_CHART=1` with `OPMS_RECORD_WPF_CHART_OUT`; `OPMS_RECORD_2D_CHART=1`). Every recorded picture was repeatable (a second
`GetBitmap`) and the same in a fresh render of both layers. Each folder has a `README.md` with the reasons. In a 64-bit process the tests
compare with the x64 copy when there is one (`WpfCharts.ForThisBitness`, used by the gate, the perio printout, Simple 2D, the determinism and
gallery tests and the big-chart test); otherwise with the x86 picture. In a 32-bit process nothing changes. A Simple 2D recording in a
64-bit process writes to its own folder, never into the x86 set.

**The WPF chart: a text cell one pixel apart.** The 2D layer's text items were compared in both bitnesses on the same scene data (a
diagnostic test, not committed; `.git/od-tools/test-results/tc10-evidence/origins-*.txt`). Two items move, all others are on the same pixel:

| Picture | x86 | x64 | Difference |
|---|---|---|---|
| Tooth number "5" at 410x307 (142 of the 149 module-size scenes: the 7 others draw no Universal "5" there) | x 120 | x 121 | 31 pixels in one 16x16 block (limit 24) |
| The perio legend's second row: "Suppuration", "Clinical Attachment Level", "Furcation 2" (15 perio scenes, 3 prints, 3 saved images) | y 649 | y 648 | 1380 pixels in the chart, 2862 in the print and the saved image |

`ToothSceneBuilder.AddText` places the cell at `Math.Ceiling(xScreen)` and `Math.Floor(yScreen)` of `ToothScene.ProjectDirectX`, which
computes in `float`. The 32-bit JIT does that arithmetic on the x87 unit at double precision (control word 0x0009001F), the 64-bit JIT with
SSE in single precision (MXCSR 0x0008001F, the same on every thread and before and after a chart is made: the floating-point state is not
changed by anything the chart loads), so a coordinate that is a whole pixel in one process is a hair beside it in the other, and the cell
moves by one pixel. Everything else differs, where it differs, within tolerance. Not changed here: the program is x86 until 3b, and at 3b (.NET 10, always SSE) the x64
picture is the reference (S3b-5's `wpf-net10-x64`).

**Simple 2D: GDI+ text.** In the 18 Simple 2D pictures beyond tolerance (16 at 500x370, `text-all-kinds` at 640x320 and 360x480) the tooth
numbers that `ToothChart2D` draws with GDI+ in their white boxes have other anti-aliasing (2916 to 4175 pixels, up to 146 in one block); the
glyphs keep their places and size. The 17 others (the 410x307 ones among them) are within tolerance.

The determinism and gallery tests compare exact bytes, so `410x307/restored-adult` and `410x307/treatment-plan` had to be in the x64 set in
any case; they are among the 142.

## 5. The two checks brought back in BINATests

TC-9a's review found two checks of S3a-15's deleted `ToothChartEngineBitnessTests.cs` that still mattered for the code that stays. They are
back in a new file, `tests/BINATests/ToothChartBitnessTests.cs` (next to `ToothChartEnginesRetiredTests.cs`, which is unchanged), and run in
the x86 Targeted run and in the lane's x64 test build of BINATests (`-Projects BINATests -X64Test`):

- **`ChartPInvokes_PassHandlesAsIntPtr`**: S3a-15's scan, for SparksToothChart's own declarations. Mono.Cecil reads the loaded
  `SparksToothChart.dll` (from a copy of its bytes) and lists every method with `IsPInvokeImpl`: today the six gdi32 functions of
  `ChartFontMeasure` in `Wpf3D/ToothSceneBuilder.cs` (`CreateFontW`, `CreateCompatibleDC`, `SelectObject`, `DeleteObject`,
  `GetTextMetricsW`, `GetTextExtentPoint32W`). No parameter named as a handle is anything but `IntPtr`, the three that return a handle
  (HFONT, HDC, HGDIOBJ) return `IntPtr`, none returns `Int32` or `UInt32`, and the list is pinned with each signature (a new declaration is
  added on purpose). `TEXTMETRIC` (60 bytes) and `SIZE` (8) have no pointer field and the same size in both bitnesses; `_hdc` is `IntPtr`;
  and no SparksToothChart source casts a handle to a number or calls `ToInt32`/`ToInt64` on one.
- **`Simple2D_StartsOnAHiddenForm`**, and **`WpfChart_StartsOnAHiddenForm`** for what a stored DirectX or OpenGL choice starts now: on an STA
  thread, a borderless form whose window handle is created and which is never shown (asserted not visible), a 400x300 chart on it started
  by the stored choice through `DrawMode` (Simple 2D 1; DirectX 0 and OpenGL 2, which start the WPF chart since TC-8), its picture through
  `GetBitmap`: the engine expected, the size, more than one colour, no fallback logged. Each start is written to
  `ToothChartBitness.<x86|x64>.txt` next to the test assembly (saved as `.git/od-tools/test-results/tc10-bina-record.*.txt`).

Records (x64): Simple 2D came up Simple2D and drew 400x300 (1917 sampled colours, about 0.3 s); DirectX and OpenGL came up Wpf3D and drew
(844 colours; 1.6 s for the first, the render thread's start). The chart's own window handle is not created on a form that is never shown
(recorded, not asserted; S3a-15 did not assert it either). x86: the same (Simple 2D 1947 colours, 0.4 s; the WPF chart 844 colours, 1.8 s and 0.7 s); the same six declarations.

## 7. Found, not changed

- **The lane hides the reason of a failed assert.** The lane prints only the output lines that match `Assert|Exception` (and the summary);
  MSTest 4 writes a failed assert as "Assertion failed. Expected values to be equal." with the user message on lines of its own, so the x64
  runs showed which test failed but not why. Here a temporary diagnostic file (not committed) gave the messages. Suggestion for the lead's
  lane: print the line after "Error Message:" too, or the last 40 lines of a failing test's block.
- **A failing run's picture folders can be emptied by later tests.** In the first full x64 run `%TEMP%\ToothChartImageTests\wpf-failures`
  held the perio failures but not the 410x307 ones, and `simple2d-failures` was missing, although both tests failed with those pictures
  (seen in the filtered runs). A later test of the run deletes and rewrites those folders; the failing test's own message (section above)
  is the reliable record. Not changed (the folders are a convenience).
- **For TC-8b (parallel):** if TC-8b re-records any WPF picture at 410x307 or 649x696, or a perio print or saved image, the x64 copy of the
  same picture must be re-recorded in the same merge (a full x64 run with `OPMS_RECORD_WPF_CHART_OUT`, then copy only the pictures of
  `wpf-net48-x64`). Otherwise the x64 run compares the new drawing with the old one.
- **For S3b-5:** the x64 sets retire with .NET Framework; S3b-5 records `wpf-net10-x64` in full. The one-pixel text cells of section 3
  will be the x64 state there; whether to make `AddText`'s rounding robust (for example rounding to the nearest after a small epsilon) is a
  drawing change for the owner's gallery, not a test change.

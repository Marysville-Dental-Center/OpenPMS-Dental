Package N64-A3 of stage 3a of the .NET 10 move: item **A3** of the native 64-bit integration survey
([docs/specs/native64-survey.md](../specs/native64-survey.md), section 4 A3; row 8 and section 3.8), under owner decision 23
([docs/specs/net10-plan.md](../specs/net10-plan.md), section 11: native 64-bit first, the 32-bit helper as the fallback), on the pattern of
S3a-14n ([S3a-14.md](S3a-14.md), section "S3a-14n: native first"). Branch `net10/n64a3-1` from `main` (`e2fc2306f`). No schema change, no
package, nothing downloaded, no new DLL (the helper gains the framework's own `Microsoft.CSharp` reference). No test creates
`Mediadent.Application` or any real COM server, starts CADI, shows a window or changes a system setting.

Commits, in order: CodeBase (`3e1811c2c`: the chooser and the registry reading), the helper (`20cd313f8`: the Cadi module), the UI side
(`4d93ab787`: `CADI.cs` and the new `CADIInProcess.cs`), the test wiring (`0bb233e94`), the tests (`00bb046d8`), and this note with the
survey's and the plan's status.

## 2. The choice: each registry case

`CADIInProcess.IsChosen()` asks `NativeFirstChooser.Cadi.ChooseForComServer`, which reads the registration on the first call only; the choice
is then fixed for the process and written to `Logger\NativeFirst` once (the S3a-14n format: the piece, the path, the process's bitness, the
registration as `Describe()` gives it).

| Registration (`HKCR\CLSID\{clsid}`) | 32-bit process (today's x86 build) | 64-bit process (3b) |
|---|---|---|
| LocalServer32 in the 32-bit view (what the survey expects of CADI) | in process | in process: COM starts the 32-bit server program for a 64-bit caller and reaches it through IDispatch, which Windows marshals itself |
| LocalServer32 in the 64-bit view, or in both, or with an InprocServer32 too | in process | in process |
| InprocServer32 in the 32-bit view only | in process | **the helper** (logged; nothing is created in the program) |
| InprocServer32 in the 64-bit view only | in process (the vendor's error shows, as before; the helper is 32-bit too) | in process |
| InprocServer32 in both views | in process | in process |
| No class id for the ProgID, no server key, or a registry that cannot be read | in process, **choice not fixed**: creating the object reports what it did before ("Unable to open CADI. Verify it is installed and try again." when `GetTypeFromProgID` gives null), and the next click reads the registry again (CADI may be installed since) | the same |

## 3. The HRESULTs

`CADINativeWindow.SendData` checks the failure of the activation and of every call in one exception filter ahead of main's catches:
`catch(Exception ex) when(CADIInProcess.IsRetriedInHelper(ex,isCadiReached))`. `ChooseHelperAfterFailure` takes these, also inside a
`TargetInvocationException`:

| HRESULT | Meaning here |
|---|---|
| `REGDB_E_CLASSNOTREG` 0x80040154 | the class is not registered for this bitness |
| `CO_E_SERVER_EXEC_FAILURE` 0x80080005 | CADI's server program could not start |
| `E_NOINTERFACE` 0x80004002 | CADI's interface cannot be reached from this process (also an `InvalidCastException`, whose HResult is that value: a failed QueryInterface of the object) |
| `TYPE_E_LIBNOTREGISTERED` 0x8002801D | CADI's type library is not registered for this bitness |

- **64-bit process, nothing reached CADI yet** (the activation failed, or the first call, `OleClientWindowHandle`, did, on an object made in
  this window's life): the helper is chosen and logged, the window is closed (an object that was made is released), `SendData` returns
  false, and `CADI.cs` sends the same call to the helper **once, now**, without a message.
- **64-bit process, a call had reached CADI** (a later call failed, or the object came from an earlier click): the helper is chosen and
  logged **for the next click on**; this click shows main's message ("Unable to access CADI. Verify it is installed and try again." for a
  `COMException`), as before.
- **32-bit process** (today's build): the filter is false and nothing changes or is logged; main's catches show main's messages. Its helper
  is 32-bit too and could reach nothing this process cannot.
- **Any other failure** (E_FAIL, access denied, `ArgumentNullException` for a missing ProgID, a non-COM error): main's catches, the choice
  unchanged.

Like S3a-14n's lead note for Schick: a `CO_E_SERVER_EXEC_FAILURE` sends CADI to the helper until the program restarts, even when the failure
was passing; the log line names the HRESULT, so it can be told apart.

## 4. The in-process path compared with main

Call for call as main's `CADINativeWindow` (the tests compare all three paths with a copy of main's code, section 6):

```
Type.GetTypeFromProgID("Mediadent.Application"); Activator.CreateInstance(progType)   (first call, or after the window closed)
OleClientWindowHandle(hWnd as Int32, 1, WM_CLOSE 0x10 as UInt32, 0, 0)                 (0 = success, else "Unable to communicate with CADI...")
OleBringToFrontApp()                                                                  (only with a patient)
OleBeginTransaction()
OleSetPatientName("LName, FName")
OleSetPatientDateOfBirth(days since 1899-12-30 as Double)
OleSetPatientBiologicalAge(Age as Int32)
OleSetPatientSex("F" or "M")
OleLoadPicLib(image folder combined with the PatNum or ChartNumber)
OleEndTransaction()
```

The window is main's: a `NativeWindow` made with `new CreateParams()` (no parent: a hidden top-level window, never shown; the survey calls it
message-only, and it is kept exactly as it was), its handle passed as an int, `WM_CLOSE` from CADI releasing the object
(`Marshal.ReleaseComObject`) and the window, and the next click making both again. The object lives between clicks, as before. A
`COMException` drops the object without a release; any other failure releases it; the three messages are main's.

What differs, none of it a call to CADI:
- The two program properties (PatNum or ChartNumber, the image folder) are read before the object is made; main read them between
  `OleBeginTransaction` and `OleSetPatientName`. CADI's calls and their values are the same.
- The registry read of section 2, once per process, read only, and one log line.
- The new first catch, which a 32-bit process never takes.

So **in today's x86 build CADI runs in the program's process exactly as on main**.

## 5. The fallback: the helper's Cadi module

`CadiModule` repeats main's calls with the values the program worked out (`CadiCommands.EncodePatient`/`DecodePatient`), in the same
order, with main's window in the helper (made on the first `SendData`, never in the constructor) and main's three messages. The CADI object
and the window are **kept between calls**, as `CADI.cs`'s static window kept them, until CADI's `WM_CLOSE` arrives (the helper pumps its
thread's messages between requests, S3a-14 section 6) or a call fails; the next `SendData` makes both again.

The program's side (`CADI.SendDataToHelper`) calls `Helper32Client.Default.CallPumping` with a 5-minute timeout and `isReactivating:false`:
the helper may bring CADI to the front (`OleBringToFrontApp`; `CallPumping` allows the helper to set the foreground window), the program
keeps painting with its windows disabled while CADI starts, and CADI stays in front afterwards. What CADI's calls threw in the helper comes
back as a Remote failure with its message, which `SendData` shows and logs as before; a failure of the helper itself (missing, not
starting, not answering, ended) shows "Unable to open CADI." with the helper's message. When the 5 minutes pass, the helper is ended (CADI
keeps running: COM started it, not the helper) and the next click starts a new helper, whose module makes a new object, as after a restart
of the program before.

## 8. Notes for the lead

- **A 64-bit server that activates but whose calls fail later** with another HRESULT (DISP_E_*, RPC_E_*) is not sent to the helper; no such
  case is known. A `RuntimeBinderException` ("System.__ComObject does not contain a definition for ...", an object without IDispatch) is not
  one of the four either; for CADI, whose interface is pure IDispatch, it is not expected.
- **An InprocServer32 with a DLL surrogate** (an AppID with `DllSurrogate`) could run out of process for a 64-bit caller; the registry rule
  sends such a 32-bit-only registration to the helper anyway, which works too.
- **Strings** cross the helper's protocol as UTF-8; a name with a lone surrogate fails with the protocol's message on the helper's path only
  (S3a-14f item 2), as for Schick.
- **Release notes:** nothing for users; the x86 program behaves as before, so `docs/release-notes/next.md` is unchanged.
- **For 3b:** the x64 build reaches CADI's (expected) out-of-process server from its own process with no code change; launch check C3.

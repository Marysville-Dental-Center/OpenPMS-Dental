([docs/specs/native64-survey.md](../specs/native64-survey.md), section 4; rows 9, 10, 12 and 16 with their notes 3.9, 3.10, 3.12 and 3.16),

## 1. What changed

### A2: the plug-in loaders

| Where | Change |
|---|---|
| `CodeBase/Utilities/PortableExecutableFile.cs` (new) | Reads a DLL or EXE without loading it: the PE header's machine and PE32/PE32+, the CLI header's flags (ILONLY, 32BITREQUIRED, 32BITPREFERRED), the metadata version string, the assembly's `TargetFrameworkAttribute` (CustomAttribute, MemberRef and TypeRef tables) and the core library it references (AssemblyRef: `System.Private.CoreLib`, `System.Runtime`, `netstandard`, `mscorlib`). The .NET Framework has no `System.Reflection.Metadata`, and the program ships no Mono.Cecil, so this is a small reader of ECMA-335 II.22-II.25 (all 45 table row sizes, so any row is found). It never throws for a malformed file. `CanLoadInProcess(machine)` is the binder's rule: an any-CPU assembly loads everywhere, any other image only in a process of its machine type. |
| `OpenPmsDentalBusiness/Plugins/PluginImageCheck.cs` (new) | `GetRefusalReason(dllPath,pluginName)`: null when this process can load the plug-in, otherwise a clear reason naming it: not a PE file, a native DLL, 32-bit only in a 64-bit process, 64-bit only in a 32-bit one, or a framework the process cannot host. On the .NET Framework: a `.NETCoreApp` plug-in and .NET Standard 2.1 or later are refused. On .NET (3b): a `.NETFramework` plug-in is refused with decision 16's message ("ask its author for a build for .NET 10.0, net10.0-windows, any CPU or x64"), and a .NET newer than the process's. Without a `TargetFrameworkAttribute` the core library tells (mscorlib: .NET Framework; netstandard: .NET Standard; System.Runtime 5 or later: .NET). A framework the file does not tell, and a file that cannot be opened, are not refused (LoadFile then reports as before). `GetLoadErrorText(ex,...)`: the clear text for a `BadImageFormatException` and a `FileLoadException` (also wrapped in a `TargetInvocationException`); any other exception keeps its message. |
| `OpenPmsDentalBusiness/Plugins/Plugins.cs` | New `LoadPlugin(dllPath,pluginDllName,programNum,host,out error)`: the check, then exactly the old steps (`Assembly.LoadFile`, the type `[file name].Plugin`, `Activator.CreateInstance`, `Host=host`) and the same `PluginContainer`. The Middle Tier's `LoadAllPlugins` uses it; its empty `catch` is gone: every refusal or load error is written to the log (`Logger`, sub folder `Plugins`) naming the plug-in. `LogProblem` and `GetProblemsLogged` (the last 100, for the tests: `Logger` writes nothing in a unit test process). `HookMethod`, `HookAddCode` and `LaunchToolbarButton`: a `DllNotFoundException` or `BadImageFormatException` from a hook (also wrapped) is logged once per plug-in and error, naming the plug-in and the hook; `HookException` still gets every exception, as before. |
| `WpfControlsOD/Bridges/PluginLoader.cs` | The program's loader goes through `Plugins.LoadPlugin` too. On a refusal or a load error its message box shows "Error loading Plugin:" with the plug-in's name and the reason, as before (only the text after the line break is clearer for the two explained exceptions); no message box on the Middle Tier, as before. |

A loadable plug-in loads as before: same file, same steps, same container, same `Host`.

## 2. The bitness rule, and a correction to the survey

The survey (row 10 and 3.10) says a plug-in that is "Required32Bit, Preferred32Bit or x86" gets the refusal. The x64 run of
`PluginLoadTests.EachBitness_RefusedExactlyWhenThisProcessCannotLoadIt` showed that a **64-bit .NET Framework process loads an IL-only
DLL with both 32BITREQUIRED and 32BITPREFERRED**: it is "any CPU, 32-bit preferred" (C# allows that platform for an exe only, so such a DLL
is rare). The first version refused it and the test failed in x64; the rule now follows the runtime (commit `560f67d26`): only
32BITREQUIRED without 32BITPREFERRED, a mixed-mode x86 image or a PE32+ image of another machine is refused. This is also the rule of
S3a-14n's `PeImageInfo` (branch `net10/s3a14n-1`). Whether CoreCLR's binder treats such a DLL the same is not proven here (3b): if it does
not, `LoadFile` throws `BadImageFormatException`, which `GetLoadErrorText` explains.

The runs' records (`N64aPluginBitness.<bitness>.txt` next to the test assembly):

| Plug-in | x86 run: refused / LoadFile fails | x64 run: refused / LoadFile fails |
|---|---|---|
| any CPU | no / no | no / no |
| x86 (32BITREQUIRED) | no / no | yes / yes |
| x86 with 32BITPREFERRED | no / no | no / no |
| x64 (PE32+) | yes / yes | no / no |

## 5. Launch checks for a person (test PC, never at the office)

Nothing here was started. On a test PC with the x86 program of this branch (and later the x64 program of 3b) and a test database:

1. **Plug-in, loadable.** Build `PluginExample` (or any plug-in) for any CPU; set it as a program link's plug-in DLL, enable the link,
   restart. It loads as before (its button and hooks work); `Logger\Plugins` has no line for it.
2. **Plug-in, wrong bitness.** Rebuild it for x64 (in the x86 program; for x86 in the 3b x64 program) and restart: the message box
   "Error loading Plugin:" names the DLL and says "64-bit only, and this program is a 32-bit process" (or the reverse) and what to ask
   the author; the same line is in `Logger\Plugins`. The program starts normally.
3. **Plug-in, not an assembly.** Point the link at a text file renamed `.dll`: "it is not a program library (the file has no PE header)".
4. **Plug-in, framework (3b).** In the x64 .NET 10 program, a plug-in built for .NET Framework 4.8 gets decision 16's message and is not
   loaded; the rebuilt `PluginExample` (net10.0-windows) loads (plan section 7, "Plugins").
5. **Trojan.** With the Trojan link enabled, add `INSTALLDIR` under `HKLM\SOFTWARE\TROJAN BENEFIT SERVICE` with the 64-bit regedit only
   (no WOW6432Node key): the startup plan update and the insurance plan window's Trojan import now find the folder. Remove it and add the
   key as `HKLM\SOFTWARE\Trojan` instead: also found. With no key, the plan window still shows its "Registry entry is missing" message.
6. **Word.** On a PC with Word: letter merge print and chart letters work as before. On a PC with a broken Word registration (for example
   the class key removed in a throwaway VM, or after a 32-to-64-bit Office move that left orphaned keys), the letter merge shows "Microsoft
   Word is installed, but its registration in Windows is broken ..." instead of the raw COM text, and `Logger\Word` has the HRESULT.
7. **DirectX.** Open the Chart module once with the DirectX chart: `Logger\ToothChart` has one "DirectX: d3dx9_43.dll loaded from ..."
   line naming SysWOW64 for the x86 program (System32 for the x64 one).

# Port note: S4-1 (MSTest 4: the framework swap)

Package S4-1 of stage 4 of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S4-1 row): branch `net10/s41-1` from
`main` (`5737519bf`). Every test project, NoHqTests, the legacy UnitTests and UnitTestsCore move from MSTest v1
(`Microsoft.VisualStudio.QualityTools.UnitTestFramework` from the Visual Studio folder) to MSTest 4.5.3 from its NuGet packages, with the
VSTest adapter and the VSTest SDK. The test runs stay VSTest runs (`vstest.console.exe` of Build Tools 2026 with `/Platform:x86`, through the
test runner and the lane's `-Test`), and no test run sends telemetry. No program code, no schema change; nothing was downloaded; no program was
started.

Commits: `f237a7e50` (packages, shared props, targets, analyzer levels, the compile fix and the fixture fixes), `9924096c0` (the
project-file reader and the coverage path maps), `069622b36` (TestTelemetryTests), `36478ae4c` (LibraryBindingTests), `67bd60b2a` (the
sales tax test of UnitTests), and this note with the plan's status.

## 3. The API changes, by kind

Before starting, the code was checked against what MSTest 4.5.3 no longer has, by reflection on `MSTest.TestFramework.dll` 4.5.3 and by
grep over `tests\`, `UnitTests\`, `UnitTestsCore\`, `NoHqTests\` and the tools' tests:

| v4 change (v1-to-v3 and v3-to-v4 guides) | Uses in the code | What S4-1 did |
|---|---|---|
| `[ExpectedException]` removed | 1 (`tests/VPEARL2Tests/PearlApiClientLoggingTests.cs`) | `Assert.ThrowsExactly<ArgumentNullException>`: exactly that type, as `[ExpectedException]` required (it did not allow derived types) |
| `Assert.ThrowsException` / `ThrowsExceptionAsync` removed | 0 of MSTest's | none: the 24 files that mention it have their own helpers ("MSTest v1 has no Assert.ThrowsException"), which compile and keep their exact-type checks |
| `Assert.*` overloads with a message and `params object[]` removed | 0 (no compile error) | none |
| `Assert.AreEqual(object, object)` gone (generic `AreEqual<T>` only) | 0 that fail to compile | none: every call infers one type, as it already did under v1 (the generic overload was the better one there too) |
| `TestTimeout` enum removed; `[Timeout]` | 0; 2 `[Timeout(60000)]` (`tests/BPERIOTests/ContrPerioTests.cs:262,378`) | kept as they are: v4's `[Timeout(int)]` without `CooperativeCancellation` stops waiting for the test after the time, as v1 did; cooperative cancellation would need the test to watch `TestContext.CancellationToken`, which it does not, so a hang would never time out |
| `ClassCleanupBehavior` removed (v4: always at the end of the class) | 0 uses; 160 `[ClassCleanup]` in 160 files | section 4 |
| `DataTestMethod`, `DataRow`, `DynamicData`, `TestContext.Properties`, the old `TestContext` folders, custom `TestMethodAttribute`/`TestClassAttribute` | 0 each | none |
| `PrivateObject` | 2 (UnitTests, `UserControlTasksTests.cs`) | none: MSTest.TestFramework.Extensions 4.5.3 still has it for .NET Framework |
| `AssertFailedException`, `AssertInconclusiveException`, `UnitTestAssertException` | 17, 6 and 6 uses | none: same types, same use |

What the analyzers found (section 5), fixed in the code:

- 2 TestInitialize and 1 TestCleanup with an invalid layout (MSTEST0008, MSTEST0009) in the legacy UnitTests: `AdjustmentsTests.SetupTest`
  and `TearDownTest` (`protected static`) and `ChartModulesTests.SetupTest` (`private`). MSTest v1 never ran them; MSTest 4 refuses such a
  class at run time. They are public instance methods now, so they run before and after each test, as written. With SetupTest running,
  `Adjustments_CreateAdjustmentForSalesTax_UsesClinicProvIfNoSalesTaxDefaultProv` failed: under v1 every provider number was 0 and it passed

- 1 shadowing (MSTEST0036): `UserodsTests.Cleanup` (TestCleanup) hid `TestBase.Cleanup` (AssemblyCleanup); renamed `CleanupUserodsTest`.

So: 1 compile error (1 file), 3 fixture methods and 1 name (3 files), 1 test that never checked what it says (1 file).

## 4. ClassCleanup: at the end of each class

MSTest 4.5.3 has no `ClassCleanupBehavior` and no run setting for it (checked in `MSTestAdapter.PlatformServices.dll`): a class's
`[ClassCleanup]` runs after its last test. Under MSTest v1 every ClassCleanup ran at the end of the assembly's run. Decided: the v4 timing,
end of class, for all 160; nothing restores the old timing. Why it is safe here: every scratch database belongs to one class or to the
assembly (`[AssemblyInitialize]`/`[AssemblyCleanup]`, 56 and 58 uses, unchanged), the helpers were written for "MSTest may run another
class's ClassInitialize in between" (`ServerTestDb`, `ReportTestDb`, MiddleTierMockTests' `ScratchDbCopy`, which makes a new copy for a
later class), and a class's database is now dropped sooner, not later. The databases of the server were listed before the first test run of
this package and after the last: the same 34 (none of this package's runs left one; the older leftovers of other work are untouched). The
MariaDB accounts the tests make (MiddleTierMockTests' SELECT-only account) are gone too. The plan's gate check (two Full runs in a row, no
leftover `scratch_*` database) is the coordinator's.

## 6. Telemetry: none

MSTest.TestAdapter 4.5.3 depends on Microsoft.Testing.Extensions.Telemetry, which brings Microsoft.ApplicationInsights. Checked in the
binaries: under VSTest the adapter has no telemetry sender (`MSTestDiscoverer` and `MSTestExecutor` hand `MSTestEngine` none) and references
neither assembly; the telemetry extension serves only a Microsoft Testing Platform program, whose generated entry point registers it
(`TestingPlatformBuilderHook` 98058041-...), and it and MSTest's platform telemetry are off with `TESTINGPLATFORM_TELEMETRY_OPTOUT` or
`DOTNET_CLI_TELEMETRY_OPTOUT` set to 1; vstest.console sends telemetry only when `VSTEST_TELEMETRY_OPTEDIN` is 1. What is set, for every test
project:

- the projects are no platform programs (`EnableMSTestRunner`, `IsTestingPlatformApplication`, `GenerateTestingPlatformEntryPoint`,
  `TestingPlatformDotnetTestSupport` false), so no entry point is generated and nothing could register the extension;
- `Directory.Build.targets` removes the extension's registration item and, after `ResolvePackageAssets`, the compile and copy-local files of
  Microsoft.Testing.Extensions.Telemetry and Microsoft.ApplicationInsights: no output folder holds telemetry code;
- the lane sets `DOTNET_CLI_TELEMETRY_OPTOUT=1` for its builds and `-Test` runs already (`tools\Initialize-BuildEnvironment.ps1`).

The test, `tests/ProjectFileTests/TestTelemetryTests.cs` (4 tests): every test project of the solution filter has the four switches false,
MSTest's registration and not the telemetry one; no built test output folder holds either telemetry assembly and no test assembly carries
the platform's `Microsoft.Testing.Platform.Application` metadata; the adapter next to the test assembly references neither; and the run is a
VSTest test host with `VSTEST_TELEMETRY_OPTEDIN` not 1. The environment variables of the runners are S4-2's (section 10).

## 7. Other build changes the packages brought

- **The project-file reader** (`tests/ProjectFileTests/ProjectFile.cs`, which the S1-T gate checks use) reads the packages' build files too.
  Two of their constructs stopped every test project's evaluation: Microsoft.CodeCoverage's targets test `$(NETCoreSdkVersion)`, which the
  reader now gives an SDK-style project as the pinned SDK's (10.0.114, as `Microsoft.NETCoreSdk.BundledVersions.props` sets it; a classic
  project leaves it not modelled), and Microsoft.Testing.Platform.MSBuild fills `_TestingPlatformConfigurationFileInput` from
  `$(MSBuildAllProjects)`, which MSBuild computes from the files it imported: that item type is not modelled in such a project (GetItems,
  GetItem and HasItem throw for it; GetAllItems and GetItemsMentioning leave it out). A bump of the SDK changes the reader's 10.0.114 with the
  rest of its 10.0.114 facts.
- **No coverage path maps**: Microsoft.CodeCoverage's `MsCoverageReferencedPathMaps` target built every project reference once more before
  each test project's compile and wrote `.msCoverageSourceRootsMapping_<assembly>`, with the build machine's source folders, into each test
  output folder. No coverage is collected here, so `DisableMsCoverageReferencedPathMaps` is true for every test project.
- **New files in the test output folders**: `MSTest.TestFramework.dll`, `MSTest.TestFramework.Extensions.dll`, `MSTest.TestAdapter.dll`,
  `MSTestAdapter.PlatformServices.dll`, `Microsoft.Testing.Platform.dll`, `Microsoft.Testing.Extensions.MSBuild.dll`,
  `Microsoft.Testing.Extensions.TrxReport.Abstractions.dll`, `Microsoft.VisualStudio.TestPlatform.ObjectModel.dll`,
  `Microsoft.TestPlatform.CoreUtilities.dll`, `Microsoft.TestPlatform.PlatformAbstractions.dll`, `Microsoft.VisualStudio.CodeCoverage.Shim.dll`,
  `System.Reflection.Metadata.dll`, `System.Collections.Immutable.dll` (and no longer the v1 framework, which the test host took from the
  Visual Studio folder). No program folder changes; nothing new ships.
- **LibraryBindingTests** maps every package of the lock files: the 13 of batch B are "packages that bring no library file", each with its
  reason, as Mono.Cecil already is (test tools of the test projects only, which no program references and "Required dlls" never held; the
  telemetry extension and Application Insights are kept out of every output folder). Microsoft.CodeCoverage's `build\netstandard2.0` (the
  collector and its own System.Memory, System.Text.Json and the like, copied on publish only) is a folder no build copies from, so the check
  that such a package holds no file of a library file's name skips it. The list's comment asks for the lead's agreement to new entries
  (section 11).

## 8. How MSTest 4 runs the tests here

Seen in a probe test of this package (not committed): under vstest.console 18.11 with `/Platform:x86`, MSTest 4.5.3 runs each test on an STA
thread that is no thread-pool thread, as the MSTest v1 adapter did (the WinForms, WPF and TWAIN tests rely on it; the 21 places that start
their own STA thread keep doing so), in an application domain of its own for the test assembly (with its generated `.dll.config`), with the
current folder the test assembly's `bin\Debug`. Tests of a class run in the order of the source; no parallel execution (no `[Parallelize]`).

The two outcome differences against the stage 2 record (section 9), neither from MSTest 4:

- **ProjectFileTests, `EveryProjectOfTheSolutionFilter_EvaluatesTheItemsMSBuildRecorded`**: passed in the stage 2 gate, which set
  `OPMS_CHECK_PROJECT_BASELINE=1` with a recorded baseline; inconclusive (skipped) in a Targeted run without them, as under v1. Recording a
  baseline runs MSBuild outside the lane, so it is the coordinator's gate step.
- **DbConnectionSecurityTests, `Script_DryRun_ShowsThePlan_AndChangesNothing`**: fails because `tools\Enable-LocalDbTls.ps1` refuses its dry
  run on this machine: "REFUSED: <the MariaDB installation folder>\opms-dev-tls exists. Run -Revert, or look at it and remove it." That folder
  is the TLS set-up of the local server (DB-TLS-ENV, running in parallel; it is not readable without elevation). The same test, and the new
  `TestNetwork_DryRun_ListsEveryStep_AndChangesNothing`, fail the same way with `main`'s DB-TLS-ENV merge on top of this branch (a trial
  merge, built and run, then aborted: it merges without a conflict and compiles under MSTest 4). Run again after the server's TLS set-up is
  finished or reverted.

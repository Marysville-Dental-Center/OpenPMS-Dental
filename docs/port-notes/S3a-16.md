# Port note: S3a-16 (`Direct2dWrapper` x64 build)

Package S3a-16 of stage 3a, wave 3, of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-16 row, decision 19):
branch `net10/s3a16-1` from `main` (`f6fa21d95`). The program stays x86 on .NET Framework 4.8. This package makes the native
`Direct2dWrapper.dll` build for x64 without touching the x86 program: the x64 configurations no longer copy their DLL into the program's
folder, the x64 compile refuses pointer truncation, and the solution's `Any CPU` platform builds the Win32 configurations as `x86` does. No C++
source changed, no schema change, no package, no download, no new DLL; no program was started.

Commits: `ac81dec74` (the project and the sln lines), `fa113d52b` (the tests), and this note with the plan's status line. Review fix on
`net10/s3a16-2`: a missing x64 DLL makes its tests inconclusive, never failed (section 3); the gate's two lane commands enforce the x64
build (section 4).

## 1. What changed

### 1.1 `Direct2dWrapper/Direct2dWrapper.vcxproj`

- `Debug|x64` and `Release|x64`: the `PostBuildEvent` (`xcopy "$(TargetDir)Direct2dWrapper.dll" "..\OpenPmsDental\bin\Debug\" /Y`, and
  `bin\Release\` for Release) is removed. The x64 DLL stays in its own output folder, `Direct2dWrapper\bin\x64\$(Configuration)\` (unchanged,
  `OutDir` of both x64 property groups), with its intermediate files in `Direct2dWrapper\x64\$(Configuration)\` (unchanged, ignored by
  `.gitignore`).
- `Debug|x64` and `Release|x64`: `ClCompile` gets `<TreatSpecificWarningsAsErrors>4311;4312;%(TreatSpecificWarningsAsErrors)</TreatSpecificWarningsAsErrors>`,
  which MSBuild passes to cl.exe as `/we4311 /we4312` (checked in the build log). C4311 is a pointer truncated to a smaller integer type
  (https://learn.microsoft.com/cpp/error-messages/compiler-warnings/compiler-warning-level-1-c4311), C4312 an integer widened into a pointer
  (https://learn.microsoft.com/cpp/error-messages/compiler-warnings/compiler-warning-level-1-c4312).
- A comment above the `Debug|x64` item definition group says why (the program is x86 until S3b-4).
- Unchanged: the `Win32` configurations (their `OutDir` `bin\$(Configuration)\` and their copy into `..\OpenPmsDental\bin\Debug\` and
  `bin\Release\`), the v143 toolset of all four configurations, the sources, the version resource.

### 1.2 `OpenDental.sln` (the lead's file: these four lines only, for the lead's review)

The project's (`xDirect2dWrapper`, `{50C36CEE-5A29-4836-8853-6BE157B3DCF3}`) `Any CPU` solution mappings, lines 637-638 and 641-642, now map
to `Win32` as the `x86` ones (639-640, 643-644) do:

```
		{50C36CEE-5A29-4836-8853-6BE157B3DCF3}.Debug|Any CPU.ActiveCfg = Debug|Win32
		{50C36CEE-5A29-4836-8853-6BE157B3DCF3}.Debug|Any CPU.Build.0 = Debug|Win32
		{50C36CEE-5A29-4836-8853-6BE157B3DCF3}.Release|Any CPU.ActiveCfg = Release|Win32
		{50C36CEE-5A29-4836-8853-6BE157B3DCF3}.Release|Any CPU.Build.0 = Release|Win32
```

They read `Debug|x64` and `Release|x64` before, so a solution build for `Any CPU` put the 64-bit DLL beside the 32-bit program (its x64
post-build copy). Both files keep their CRLF line ends (`tools/Test-NoEolFlips.ps1`: none flipped). No solution platform builds the x64
configurations now; the gate builds them from the project (section 4).

## 2. First step: the x64 configurations build with the installed v143 toolset

Before any change, through the lane script (`-Solution Direct2dWrapper\Direct2dWrapper.vcxproj -Platform x64 -NoRestore`, Release, then
Debug): both built, 0 errors, 15 warnings each. The compiler is MSVC 14.44.35207 of Build Tools 2026 (18), `bin\HostX86\x64\CL.exe`, so the
x64 compiler of the v143 component is installed. The warnings:

- 14 x C4244 (`int` to `FLOAT`), `D2DWrapperHwnd.cpp` lines 508, 511, 520 and 536: integer pixel values passed as floats. Not about pointers;
  the Win32 build has the same 14.
- 1 x C4267 (`size_t` to `UINT32`), `D2DWrapperHwnd.cpp:574`: `wcslen(text)` passed as `DrawTextW`'s `UINT32` length. Only in the x64 build
  (`size_t` is 64-bit there); a text length never comes near 2^32, so it is no defect and was left alone (C4267 is not one of the two warnings
  the row makes errors).
- No C4311 and no C4312, so no C++ fix was needed. After the change, with `/we4311 /we4312`, both x64 configurations still build with 0
  errors and the same 15 warnings (rebuilt with `-Rebuild`).

The first-step builds also showed the defect this package removes: each copied the x64 DLL into `OpenPmsDental\bin\Release\` and
`bin\Debug\` ("1 File(s) copied"). Those two copies in this worktree were deleted; the slnf build (Debug|x86) and a Release|Win32 build of the
project then put the x86 DLLs back.

## 3. The test: `tests/ReleaseFlowTests/Direct2dWrapperX64Tests.cs` (new file)

- `X64Dll_IsAnX64File`: `Direct2dWrapper\bin\x64\Debug\` and `bin\x64\Release\Direct2dWrapper.dll` have PE machine 0x8664.
- `ProgramFolder_HasTheX86Dll`: `OpenPmsDental\bin\<the tests' configuration>\Direct2dWrapper.dll` (bin\Debug from the lane) has machine 0x14C
  and is byte for byte the Win32 build's DLL of that configuration (`Direct2dWrapper\bin\Debug\`).
- `ProgramFolder_OtherConfiguration_HasTheX86Dll`: the same for `OpenPmsDental\bin\Release\` (the folder Build-Release.ps1 stages from);
  inconclusive while no Release DLL is there (the lane builds Debug only; the gate's Release dry run builds Release).
- `X64Exports_EqualTheWin32Exports_AndHoldEveryImport`: the export names of each x64 DLL equal those of the Win32 DLL (same configuration when
  built, else the other: the exports do not depend on it), and every entry point the program imports from `Direct2dWrapper.dll` is among them.
  The imports are read with Mono.Cecil from the built program (`OpenPmsDental.exe`; every P/Invoke method whose module is
  `Direct2dWrapper.dll`, all in `OpenPmsDental.UI`), and cross-checked with the `DllImport`s of `OpenPmsDental/UI/Direct2d/Direct2d.cs` read
  from its source with the comments removed (one block of commented-out imports is there). Today: 66 imports, 66 exports in both bitnesses,
  the same names (extern "C" cdecl names are undecorated on x86 and x64, so the tables compare as they are).
- `PeExports_ReadsMachineAndNames`: the PE reader itself (machine and the export directory's name table, PE32 and PE32+), on kernel32.dll of
  the test process's bitness and on a managed DLL (no exports).
- `Project_X64CopiesNothing_AndTreatsPointerTruncationAsErrors`: the x64 groups have no post-build step and no command, have `4311` and `4312` in
  `ClCompile`'s `TreatSpecificWarningsAsErrors`, and keep `bin\$(Platform)\$(Configuration)\`; the Win32 groups still copy into
  `..\OpenPmsDental\bin\<Configuration>\`; all four keep v143.
- `Solution_MapsEveryPlatformToWin32`: the project's eight mapping lines in `OpenDental.sln` are exactly the `Any CPU` and `x86` ones to Win32.

A missing x64 DLL makes `X64Dll_IsAnX64File` and `X64Exports_EqualTheWin32Exports_AndHoldEveryImport` inconclusive with
"... is not built: build Direct2dWrapper x64 (the gate does).", as the row asks, also when `OPMS_REQUIRE_BUILD_OUTPUT=1`: they do not use
the build-output rule of S1-T (`tests/ProjectFileTests/BuildOutput.cs`), because the lane script sets that variable for every test run and
neither the slnf build nor any lane step builds the x64 DLL, so the rule would fail these two tests in every worktree's lane test run. The
gate enforces the x64 build instead through the two lane build commands of section 4, each of which must exit 0. The missing Win32 DLL and
the program folder's Debug copy (both built by the slnf build) still follow the build-output rule. The existing `InstallerTests.Direct2dWrapper_EachConfigurationBuildsIntoItsOwnFolder`
and Build-Release.ps1's native-file check (`$NativeFiles`: x86, no debug C runtime) are unchanged and still pass.

## 4. The gate step (for the lead)

At every gate, after the slnf build (Debug|x86) and before the Full run with `-RequireBuildOutput`, build the two x64 configurations of the
project through the lane script, from the root being gated:

```
powershell -NoProfile -ExecutionPolicy Bypass -File <the lane script> -Root <root> -Solution Direct2dWrapper\Direct2dWrapper.vcxproj -Platform x64 -Configuration Debug -NoRestore
powershell -NoProfile -ExecutionPolicy Bypass -File <the lane script> -Root <root> -Solution Direct2dWrapper\Direct2dWrapper.vcxproj -Platform x64 -Configuration Release -NoRestore
```

Each must end with exit 0 and "0 Error(s)" (exit 98: the lane is busy, run it again); these two commands are what enforces the x64 build at
the gate. They copy nothing, so they can run before or after the Release dry run. Without them, `X64Dll_IsAnX64File` and
`X64Exports_EqualTheWin32Exports_AndHoldEveryImport` are inconclusive in every run, `-RequireBuildOutput` or not (section 3), so a gate that
skipped the two commands would not be caught by the tests: the commands' exit codes are the check. The Release dry run (Build-Release.ps1) is what fills `OpenPmsDental\bin\Release\`
for `ProgramFolder_OtherConfiguration_HasTheX86Dll`.

## 5. What S3b-4 does later

At the switch to net10.0-windows x64 (S3b-4, its row): the x64 configurations copy the DLL into the program's output folder (the copy this
package removed comes back, now matching the program's bitness), and the Win32 configurations go, since no build uses them after the switch;
the `x86`/`Any CPU` solution mappings and the lane step of section 4 follow. The tests of section 3 change with it: the program folder's copy
becomes 0x8664 and the Win32 comparison goes (the import check against the x64 exports stays). The project stays on v143. In the same
stage S3b-7 (its row) moves Build-Release.ps1's source folder for `Direct2dWrapper.dll` to `Direct2dWrapper\bin\x64\Release` and its
`$NativeFiles` check to PE machine 0x8664.

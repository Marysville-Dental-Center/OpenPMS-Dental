# Port note: S3a-15 (the tooth chart's DirectX and OpenGL engines on x64)

Package S3a-15 of stage 3a, wave 3, of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-15 row, decision 19):
branch `net10/s3a15-1` from `main` (`a4e9c33ba`). The row's decision stands as it was taken from the repository on 2026-11-08: the DirectX
and OpenGL engines stay on x64, with today's fallback (DirectX, OpenGL, Simple 2D) as the safety net, and the chart is not moved to 2D on
purpose. This package adds the tests that hold the decision in both bitnesses and runs them in the lane's x64 test build. **The x64 run
found no fault**: `SparksToothChart/ToothChartWrapper.cs` and `CodeBase/Controls/OpenGLWinFormsControl.cs` do not change. No shipped code
changes, no schema change, no package, no download, no new DLL; no window was shown and no program was started.

Commits: `212a92969` (the new test file and the bitness fix of one existing test), `b1a1dff20` (the record line of the D3DX test), and this
note with the plan's status line and the release notes.

## 1. The checks

New `tests/BINATests/ToothChartEngineBitnessTests.cs`, next to `ToothChartFallbackTests.cs`. Every test runs in the bitness of the test
process; the lane runs BINATests as x86 (the test runner) and as x64 (its x64 test build).

| Test | What it holds |
|---|---|
| `EngineLibraries_AreILOnlyAndNot32BitRequired` | `SharpDX.dll`, `SharpDX.Direct3D9.dll`, `SharpDX.Mathematics.dll`, `Tao.OpenGl.dll` and `Tao.Platform.Windows.dll`, the copies in `Required dlls` and those in the test folder (byte for byte the same): the CLI header is IL-only, has no 32-bit-required or 32-bit-preferred flag, and the PE is the PE32 of an AnyCPU file. Read twice, with Mono.Cecil (from a copy of the bytes) and with the CLR's own header reader (`AssemblyName.GetAssemblyName`, `ProcessorArchitecture.MSIL`), which loads nothing. |
| `EngineLibraries_LoadInThisProcess` | The five load by the names SparksToothChart and CodeBase reference and all their types load: a 32-bit-required library would throw `BadImageFormatException` in the x64 run. |
| `EngineLibraries_CallOnlyWindowsFilesOfBothBitnesses` | Their module references are `kernel32`, `user32`, `gdi32`, `ole32`, `winmm`, `d3d9`, `opengl32`, `glu32` (Windows), `d3dx9_43.dll` (the DirectX End-User Runtime, its own test) and Tao.OpenGl's `libGL.so` and `libdl.dylib` (Linux and macOS only); anything else fails. Each Windows file is in the native system folder as an x64 PE (machine 0x8664) and in SysWOW64 as an x86 PE (0x14C). |
| `Handles_ArePassedAsIntPtr` | A scan with Mono.Cecil of every native declaration (P/Invoke) of the five libraries, of `SparksToothChart.dll` and of CodeBase's `OpenGLWinFormsControl`: no window, device, rendering context or module handle is an `int`. The one exception is Tao's joystick `Winmm.joySetCapture(int hwnd)`, which no code calls (asserted). Then the signatures of the calls the charts make: SharpDX's `PresentParameters.DeviceWindowHandle` and `Device(..., IntPtr hFocusWindow, ...)`; Tao's `wglCreateContext`, `wglMakeCurrent`, `wglDeleteContext`, `wglGetCurrentContext`, `Gdi.SetPixelFormat`, `Gdi.SwapBuffersFast`, `User.GetDC` and `User.ReleaseDC`; `OpenGLWinFormsControl._DescribePixelFormat`, `GetHDC` and its `deviceContext` and `renderContext` fields; `PIXELFORMATDESCRIPTOR` is 40 bytes in both bitnesses. And in the source: `ToothChartDirectX.cs` hands `control.Handle` to `PresentParameters` and `Device` as it is, `OpenGLWinFormsControl.cs` to `User.GetDC`, and no file of SparksToothChart or `OpenGLWinFormsControl.cs` casts a handle to a number or calls `ToInt32()`/`ToInt64()` on one. |
| `DirectXRuntimeCheck_LoadsTheD3dxOfThisBitness` | When `d3dx9_43.dll` is in the system folder of the process's bitness (System32 for x64, SysWOW64 for x86), `IsDirectXRuntimeAvailable()` is true; the file the process then loads is a PE of its own bitness (read from the loaded module's path). Without the file it is Inconclusive with the reason (the DirectX chart falls back to OpenGL there). |
| `DirectX_StartsOnAHiddenFormOrFallsBack`, `OpenGL_StartsOnAHiddenFormOrFallsBack`, `Simple2D_StartsOnAHiddenForm` | On an STA thread, a borderless form whose window handle is created and which is never shown (no `Show`, `ShowDialog` or `Visible`; asserted not visible), a chart made as `ToothChartRelay` makes one (hardware graphics, no saved pixel format, and for DirectX the device format the program picks with `GetPreferredDirectXFormat`), started through `DrawMode`, which goes through `StartFirstWorkingMode`. The mode that came up and its picture (`GetBitmap`, 400x300) are recorded in `ToothChartEngineModes.<x86 or x64>.txt` next to the test assembly. The mode that came up must be the one asked for or one of its fallbacks; Simple 2D must start and draw. A mode this computer cannot start, or starts without drawing, or (DirectX) for which no device format works, is Inconclusive with the reason and the fallback messages, after the mode it fell back to has drawn; never a failure. |

`ToothChartFallbackTests.DirectXRuntimeCheck_FindsTheInstalledFile` looked for the D3DX file in SysWOW64 because "this test process is
32-bit"; it now takes the folder of the process's bitness, so it holds in the x64 run on a computer that has only one of the two runtime
parts. The only change to an existing test.

## 2. The x64 test build

The lane's x64 test build of BINATests worked as it is: BINATests references only libraries (CodeBase, DataConnectionBase,
OpenPmsDentalBusiness, SparksToothChart), no program project, so no separate test project was needed. Command: the lane with
`-Projects BINATests -X64Test -TestTimeoutMinutes 5 -Test tests\BINATests\bin\x64\Debug\BINATests.dll`.

One thing to know when running it: `ProprietaryBinariesRemovedTests.BuiltProgram_ReferencesNoneOfTheRemovedBinaries` reads the x86
program's `OpenPmsDental\bin\Debug\OpenPmsDental.exe`; the lane sets `OPMS_REQUIRE_BUILD_OUTPUT=1`, so in a worktree where the program is not
built yet that test fails in the x64 run (as the rule says) instead of going inconclusive. After the full x86 build it passes.

## 3. The modes this build PC started

The build PC (Windows 11, 64-bit, the DirectX End-User Runtime in both bitnesses: `d3dx9_43.dll` in System32 and in SysWOW64) started
every mode in both bitnesses, with no fallback:

| | x86 (runner) | x64 (lane's x64 test build) |
|---|---|---|
| D3DX | SysWOW64 file loaded, PE machine 0x14C | System32 file loaded, PE machine 0x8664 |
| DirectX | came up DirectX, drew 400x300; device format `0;Hardware;64;D16;X8R8G8B8;FourSamples` (format search 0.9 s) | came up DirectX, drew 400x300; the same device format (search 1.0 to 1.1 s) |
| OpenGL | came up OpenGL, drew 400x300; pixel format 1 | came up OpenGL, drew 400x300; pixel format 1 |
| Simple 2D | came up Simple 2D, drew 400x300 | came up Simple 2D, drew 400x300 |

So on this PC the fallback path did not run with the real engines; it is covered by `ToothChartFallbackTests` (fake starters, both
bitnesses) and runs for real on any PC without the runtime or without a working OpenGL driver, where these tests report it.

## 5. Found, not changed (no x64 fault)

- **A DirectX device that cannot be made does not count as a failed start.** `ToothChartDirectX.InitializeGraphics` returns without a
  device when `CreateDevice` gives null (and does nothing with no device format), so `StartFirstWorkingMode` sees DirectX as started. The
  program covers this as before: at start-up `ToothChartRelay.ChooseStartupDirectXFormat` searches a working format (each tried on an
  invisible chart with a picture, `TestDirectXFormat`) and stores OpenGL when none works, and File > Graphics tests a chosen format the
  same way. The same in both bitnesses; the new DirectX test reports this case as Inconclusive ("no DirectX device format works").
- `OpenGLWinFormsControl.ReadFrontBuffer` pins its pixel array with a `GCHandle` it never frees. Nothing calls it (the one call, in
  `ToothChartWrapper.GetBitmap`, is inside a comment block; the OpenGL chart reads its picture with `GetBitmapOfOpenGL`). A later cleanup.
- Tao's `Winmm.joySetCapture` takes its window as `int`; nothing calls it (the scan pins that).

## 6. The 3b launch check on an x64 workstation (section 6 of the plan)

Not run here (no program is started by this package). On a 64-bit test workstation with the x64 build of stage 3b, a test database and a
test patient with charted work (fillings, a crown, an extraction, a planned procedure):

1. **DirectX.** With the DirectX End-User Runtime installed (`d3dx9_43.dll` in System32), File > Graphics on DirectX: the Chart module's
   tooth chart draws as on the bridge release (teeth, restorations, the X of a completed extraction, selection with the mouse, the pen and
   eraser on the Draw tab). Help > About shows a 64-bit process. File > Graphics saves a DirectX format only after its test passes: the
   chosen one is accepted.
2. **OpenGL.** File > Graphics on OpenGL (hardware, then software): the chart draws and the mouse selects; the pixel format list fills.
3. **Simple 2D.** File > Graphics on Simple 2D: the chart draws, with free text and text procedures.
4. **Fallback.** On a workstation without the DirectX End-User Runtime's 64-bit part (a clean VM, or rename System32's `d3dx9_43.dll` on a
   test VM only): with DirectX chosen, the Chart module opens without an error message and shows the OpenGL chart; the ToothChart log has
   one line naming `d3dx9_43.dll`. OpenGL normally starts everywhere (Windows' own software OpenGL included); where it cannot, the chart
   is Simple 2D, again without a message.
5. The printouts that carry the chart picture: the Treatment Plan printout, a sheet with a tooth chart, the big chart window and the
   Patient Dashboard's chart, each once in DirectX mode.

## 7. Notes for the lead

- **For S3b-3 (SharpDX and Tao on .NET 10).** These runs prove the five libraries in a 64-bit .NET Framework 4.8 process. On .NET 10 they
  load as .NET Framework libraries (SharpDX 4.0.1 targets .NET Framework 4.0, Tao 2.0; Tao.Platform.Windows references System.Windows.Forms
  and System.Drawing). When BINATests moves to net10.0-windows in 3b, these tests run there unchanged and are the first check of that; the
  launch check of section 6 is the real one.
- The release notes say that a computer where DirectX or OpenGL cannot start uses the fallback (new section "The tooth chart: ready for
  the 64-bit version").

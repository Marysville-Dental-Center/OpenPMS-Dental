# Port note: S3a-14 (Schick CDR, Topaz and Guru through the 32-bit helper)

Stage 3a, wave 3 of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-14 row; decisions 19 and 20; open point
O-14): branch `net10/s3a14-1` from `main` (`7b1c76c55`). The program is 64-bit after stage 3b, and Schick CDR DICOM's automation objects,

no system setting changed.

program's own process whenever it can run there, and the helper's module only when it cannot.

Public documentation only, read on 2026-11-15; nothing downloaded, no sign-in. Topaz's FAQ is a PDF whose text was read from the PDF itself

**Schick CDR DICOM.** No public developer documentation of CDR DICOM's automation interface was found. What is public: CDR DICOM's client is
its own program, `CDRDicom.exe`, beside `CDRServer.exe` (Patterson's support article "Schick CDR Dicom Files Install Locations",
https://pattersonsupport.custhelp.com/app/answers/detail/a_id/7111/~/schick-cdr-dicom-files-install-locations, as the search engine shows it;
CDR DICOM 4.5 Quick Start, https://pattersonsupport.custhelp.com/euf/assets/Answers/11005/CDRDicom_4_5_QuickStart.pdf, "CDR Client
(cdrdicom.exe)"), installed under `Program Files (x86)` from 5.4, so a 32-bit program. What the interop in `Required dlls` says (read here
with reflection, no CDR installed): type library `CDRDicom` 1.1 `{DBD30F40-2455-11D5-81BA-00B0D0403E92}`, the application class
`CDRDicom.Application` with CLSID `{E7D0A248-0C4C-11D6-8294-00B0D0403E92}`; its application, exam document and event interfaces are
dispinterfaces (`InterfaceIsIDispatch`), which the system's own `IDispatch` proxy marshals in either bitness; `CDRDATALib.ICDRPatient`
(`{8D82B9C6-374C-48F9-AE2A-A51FB7F44752}`) is a dual interface, which across processes uses the type-library marshaler and so needs CDR's
type library registration where a 64-bit caller looks. Creating the application starts CDR when it is not running (`Schick.cs:50-53`
before), which fits an out-of-process server (`LocalServer32`), and Microsoft documents that "an out-of-process 32-bit COM server can
communicate with a 64-bit client" (https://learn.microsoft.com/en-us/windows/win32/winprog64/process-interoperability). **Result:** a
64-bit way is likely and would need nothing new on the workstations, but it is not proven: nothing public says the class is registered as a
`LocalServer32` rather than an in-process DLL, or that `CDRDATALib`'s type library is registered for 64-bit callers. A test PC with CDR
DICOM answers it (section 10, items S1 to S3). Until then the helper module is built and used.

**Topaz.** Topaz's developer FAQ, "Do I need separate versions of SigPlusNET for 32-bit and 64-bit Windows?": "The current version of
SigPlusNET is 'Any CPU' compatible, meaning that it will run appropriately in either 32-bit or 64-bit mode depending upon your .NET
project's platform." (https://topazsystems.com/information/SoftwareDevFAQ.pdf). Topaz's SigPlusNET page: the DLL "is built with .NET
Framework 4.7.1", version 2.1.5.6 of September 25, 2023, supports .NET applications newer than 4.7.1 "including .NET Core", ".NET Core
applications require the System.IO.Ports library to support serial devices", and the installer puts the DLL under Program Files
(https://www.topazsystems.com/itextnet.html). One more fact from this repository: `UnitTests/UnitTests/SignatureBoxWrapperTests.cs`
(Open Dental's own test) says "The 32-bit version of the SigPlusNET.dll handled text encoding differently than the 64-bit version", which is
why `FillSignatureEncodings` tries every encoding. **Result:** a 64-bit `SigPlusNET.dll` exists (the current one is AnyCPU), but the 64-bit
way needs (a) the current SigPlusNET on every workstation (Topaz's download, the office's; an older installed version may be x86 only),
(b) the System.IO.Ports package for serial pads on .NET 10 (a new package, not approved), (c) the check that stored signatures still read
in a 64-bit process (the encoding fallback exists for that). The helper module needs none of this; it stays the recommendation, with the
in-process 64-bit control as the owner's later choice.

**Guru.** No public documentation of `MedVisorInterface.dll`, `MVStart` or `MVSendPatient` was found (searches on 2026-11-15). Open Dental's

## 3. Schick CDR

`OpenPmsDentalHelper32/Schick/SchickModule.cs` is `Schick.cs`'s `ShowExam`, `LoadExamWindow`, `CreateExam` and `OnExamClosed` moved line for
line, with the static fields as the module's fields (they lived as long as the program; they live as long as its helper now). One command,
`ShowExam`, with the patient's last name, first name and id (PatNum or ChartNumber, as the program property says), exactly the arguments
`ShowExam(pat,patID)` used. The calls, for a patient CDR has:

```
new CDRDicom.Application()
app.CreateExamDocument()
exam1.add_OnClose(CDRDicom.IExamDocumentEvents_OnCloseEventHandler)
exam1.Visible=true
exam1.hWnd
SetForegroundWindow(0x12345)
exam1.LoadPatient("Synthetic","Patient One","1001")
```

and for one it has not: `app.Quit()` (which fires OnClose), a new exam document, `exam2.Patient` with its `LastName`, `FirstName` and
`IDNumber` set, and `exam2.NewExam(false)`. The exam window stays open for the next patient as before; OnClose reaches the module between
two requests because the helper pumps its messages (section 6).

The program's side (`Schick.cs`) keeps `SendData` unchanged (the patient check, the id property, version 4's message) and calls the helper
with `Helper32Client.Default.CallPumping` and a 30-minute timeout (CDR starts when it is not running, and creating an exam waits for the
user). Any failure of CDR still shows "Error launching Schick CDR Dicom."; a failure of the helper itself (missing, not answering, ended)
adds the helper's message. `CallPumping` calls `AllowSetForeground` first (`AllowSetForegroundWindow` for the helper's process id; it starts
the helper first), which is needed because Windows lets only the foreground process bring a window to the front, and the program, where the
user just clicked, is that process; before, the program called `SetForegroundWindow` itself.

**The program's thread during the call (S3a-14's review).** Before, the same work was an out-of-process COM call from the program's STA
(`new CDRDicom.Application()` starting CDR, `LoadPatient`, `NewExam(false)`), and COM's modal loop kept the program's windows painting
meanwhile. A plain `Helper32Client.Call` waits in `Task.Wait`, which dispatches no paint or input message, so the first version of this
package froze the program while CDR started or its create-exam window waited for the user, and Windows marked it "Not responding".
`Helper32Client.CallPumping` (in CodeBase since the review; it was `TopazWrapper.WaitWithThreadWindowsDisabled`, section 5.3) runs the call on
another thread and waits for it on the program's thread with `Application.DoEvents` every 15 ms, with the thread's visible enabled windows
disabled, as a modal window of the program disables them. So the program keeps painting and Windows does not mark it "Not responding"; a
second click on the Schick button, or any other input, cannot start another call while the first holds the client. One difference from
before: COM's modal loop let the program's windows take input during the call; now they take none until CDR answers (the user answers CDR's
create-exam window first). Schick passes `isReactivating:false`: CDR's exam window stays open and in front, so the program's window that was
active is not activated again (the signing window passes `true`, as it closes with the call). A Topaz box painted meanwhile shows the picture
it has (`Helper32Client.IsCallPumping`), since a call of its own would wait for the helper; any other call to the helper from the program's
thread during that time (none is known: the windows take no input) waits for the Schick call to end.

**When the 30 minutes pass** (CDR's create-exam window left open, or CDR hung while starting): the client ends the helper process (`TimedOut`)
and `SendData` shows "Error launching Schick CDR Dicom." with the helper's message ("did not answer Schick ShowExam within 1800 seconds. It
was ended and is started again on the next call."). CDR itself keeps running: COM started it, not the helper, so it is not in the helper's
job object. Everything the helper held goes with it: the Schick module's application object and exam window reference (the next click
starts a new helper, whose module makes a new `CDRDicom.Application` and exam document, as after a restart of the program before), and every
Topaz control. A Topaz box that shows a stored signature makes its control again on its next call (section 5.2). A signature signed in a box
of a window that is still open and not saved yet is lost, as after a crash of the helper (section 5.2); since S3a-14f saving that window
fails with "Topaz signature pad software could not be reached:" instead of storing no Topaz signature (section S3a-14f, item 1). The
program's windows are enabled again when the call returns with the failure.

The interop's methods that return a VARIANT come back as `dynamic` with embedded interop types, which needs `Microsoft.CSharp`; the module
casts them through `object` instead (`(CDRDicom.ExamDocument)(object)_cdrApp.CreateExamDocument()`), the same conversion without the
runtime binder.

## 4. Guru

`OpenPmsDentalHelper32/Guru/GuruModule.cs` declares `MVStart` and `MVSendPatient` of `MedVisorInterface.dll` and has `ToCPlusPlusStructure`
and `DestroyCPlusPlusStruct` moved unchanged from `Guru.cs`. The program's `Guru.SendData` still fills `MVPatient` with `Tidy` from the
patient and the program properties (and still updates the patient's image folder), then sends it: `MVStart` first (its return value back;
a missing `MedVisorInterface.dll` comes back as the helper's `System.DllNotFoundException`, which `Guru.cs` turns back into a
`DllNotFoundException`, so the message "Could not find MedVisorInterface.dll. Verify that Guru is installed." is shown as before), then
`MVSendPatient`. The patient crosses as the nine arrays' lengths and their characters as UTF-16 bytes (`GuruCommands.EncodePatient`), not as
text: `Tidy` cuts at 64 characters and can leave half a surrogate pair, which UTF-8 text would turn into U+FFFD. The helper rebuilds
`MVPatient` and calls today's `ToCPlusPlusStructure` on it.

Byte for byte: `ToCPlusPlusStructure` allocates 1320 bytes, and each `Marshal.Copy(char[],0,ptr,size)` copies `size` characters (2*size
bytes) while the pointer moves on `size` bytes, so each field's second half lies under the next field's start and the last field ends at
byte 921. Bytes 921 to 1319 are never written, today or now (uninitialised memory from `AllocHGlobal`); this package keeps the function as it
is, quirk included. `GuruModuleTests` compares the 921 written bytes with today's function for synthetic patients.

A DllImport loads its library on the first call, so building the module (at the helper's start) loads nothing. `MedVisorInterface.dll` is
found in the helper's folder (the program's folder in 3a), the system folders or the PATH, as in the program's process; after 3b the helper
lives in `Helper32\`, so a `MedVisorInterface.dll` copied into the program's folder would no longer be found there (launch check G3).

## 5. Topaz

### 5.1 The module

`OpenPmsDentalHelper32/Topaz/TopazModule.cs` keeps one `Topaz.SigPlusNET` control per signature box of the program, by id (the helper's
process id and a count). Its commands (`TopazCommands.cs`): `Load` and `Create` (the path the program found; the control type is loaded once
per path, with `TopazWrapper.GetControlType`'s messages of before: "<path> has no Topaz.SigPlusNET control." and "<path> could not be
loaded: ..."), `Release`, `Call` (the control's public method by name with typed values: int, long, short, bool, double, string, null; the
old `TopazWrapper.Call` moved here, the parameter-count match and the argument conversion included, and what the method threw is rethrown as
it is, so it reaches the program with its type and message), `CanSetAutoKeyBytes` and `SetAutoKeyBytes` (the reflection on the private `Sig`
field and its `SetAutoKeyData(byte[])` that `FillSignatureEncodings` did), `Picture` (the control drawn at the box's size into a PNG with
`Control.DrawToBitmap`, as `SignatureBoxWrapper.GetSigImage` drew it) and `Sign` (section 5.3). A control id the helper does not know (its
helper ended since) throws `TopazControlGoneException`. Each control gets its window when it is created (`Handle`), as it had one inside the
program's form.

### 5.2 The program's side

`TopazWrapper` keeps its public members. It still searches the program folder and Topaz's folders for `SigPlusNET.dll` (`GetSearchFolders`,
`FindAssemblyPath`); `IsInstalled` then asks the helper to load the file found (no file: no helper is started, which is the case of most
offices); `GetTopaz` returns a `TopazSignatureView` (new, `OpenPmsDentalBusiness/UI/TopazSignatureView.cs`), a control that stands where
Topaz's control stood (location, size, visibility, focus, events, `DrawToBitmap` as before) and whose `Topaz.SigPlusNET` lives in the helper.
Every `TopazWrapper` method makes the same calls in the same order with the same arguments, now through the view (`Call`), so stored
signatures and their checks do not change; the plug-in hooks get the view where they got the control. `SetTopazSigString` swallows what
Topaz threw (a Remote failure), as before, but not a failure of the helper itself; `FillSignatureEncodings` likewise. `ResetLoader` takes an
optional `Helper32Client` for tests. The helper's control is created on the first call of a view and released when the view is disposed.

The view shows the helper's picture of its control: after a call changed the control it asks for a new picture when it next paints (or is
drawn into a bitmap), at its own size. Showing a stored Topaz signature therefore asks the helper for its picture, and `GetSigImage` (sheets,
the WPF wrapper) gets the same picture. If the helper ended since the control was made (a crash in Topaz's code), the next call gets
`TopazControlGoneException`; the view then creates its control again and repeats the call. Every sequence of `TopazWrapper` starts from a
cleared pad, so a fill after a crash is correct; a helper that ended *between two calls of one sequence* without failing a call would lose
the sequence's state (not seen; a crash of the helper fails the call it happened in, which the program reports). The exception is a
signature the patient signed and the program has not saved or cleared: since S3a-14f the view does not make that control again silently
(section S3a-14f, item 1).

### 5.3 The signing window

Before, the patient signed on the pad and the strokes appeared in the box inside the program's window. Now `SignatureBoxWrapper`'s Topaz
button makes the same calls as before (`ClearTopaz`, `SetTopazEncryptionMode(0)`, `SetTopazState(1)`) and then `TopazWrapper.ShowSigningWindow`:
the helper shows its own small window, `TopazSigningWindow`, titled "Sign on the Topaz pad" (translated by the program), with the control at
the box's size on top and OK, Clear and Cancel below, centered over the program's window and owned by it. Clear clears the pad as
`ClearTopaz` did (`ClearTablet`, the logical size 2000 by 600); Cancel clears it and closes; OK closes and keeps the signature. The control
leaves the window before the window is disposed, so the signature stays in the helper for the program's later calls: when the form is saved,
`GetSignature(keyData)` sets the key string, the key data and the modes and reads `GetSigString` from the same control, as before. When the
window closes, the box stops capture as it did when the focus left it (`sigBoxTopaz_Leave`), and the box shows the picture sent back with
the reply. The signature data does not change; the window looks different (release notes).

While the window is open, the program's thread waits for the reply on another thread and dispatches its messages, with its visible windows
disabled as a modal window of the program disables them (WinForms disables only its own thread's windows for a modal window, and the
owner is another process's window), so the program keeps painting and cannot be used meanwhile; the window that was active is activated
again afterwards. A paint of a Topaz view during that time shows the picture it has (the helper is busy). The call waits up to 30 minutes.
`Helper32Client.AllowSetForeground` lets the helper's window come to the front. Since S3a-14's review the wait is
`Helper32Client.CallPumping(..., isReactivating:true)` in CodeBase, shared with Schick (section 3); the busy check is the client's
`IsCallPumping` instead of the view's own count, and a failure of the call comes as the `Helper32Exception` itself (the wait in
`TopazWrapper` let `Task.Wait` wrap it in an `AggregateException`, which `SignatureBoxWrapper`'s catch of `Helper32Exception` missed).

### 5.4 The Load and the 64-bit path

The helper loads `SigPlusNET.dll` with `Assembly.LoadFrom` from the path the program found, as the program did. In 3b the helper is a .NET
10 x86 process and `SigPlusNET.dll` a .NET Framework WinForms control (S3b-0 item 12 proves it loads, or reports it to the owner).

### 5.5 A failing helper

A helper failure (missing, not started, not answering, ended) while a stored Topaz signature is checked is not shown as "Invalid Signature":
Topaz could not check it. `SignatureBoxWrapper.FillSignature` and `ControlImages.FillSignature` show "Topaz signature pad software could not
be reached:" and the helper's message instead, and the signature counts as not valid, as for "not installed". A missing helper makes
`IsInstalled` false, with the helper's message as the load error ("Topaz signature pad software is not installed." and that line, as for a
`SigPlusNET.dll` that could not be loaded). The Topaz button shows the helper's message.

## 6. The helper's thread between two requests (the pumping choice)

S3a-13's note (section 12) left two ways: wait for the next request with a message-pumping wait, or release the vendor objects after each
call. **Chosen: the message-pumping wait.** Releasing after each call is not possible without changing what the program does: Topaz's
control holds the signature, its key and modes between the fill or the signing and the program's later `GetSignature` and
`GetNumberOfTabletPoints` calls, and Schick's exam window and application object are kept from one patient to the next by design (the
"reuse the exam window" behaviour of `Schick.cs`, and OnClose resetting it). Both live on the helper's STA thread, and both need messages
dispatched there while the helper is idle: Topaz's control owns a window; CDR's OnClose event is a COM call from CDR's process into the
helper's apartment, which is delivered as a window message, so a helper that did not pump would hold CDR in that call until the program's
next request; and a broadcast to top-level windows (`WM_SETTINGCHANGE` with `SendMessage`) would hang its sender.

How: the helper opens the pipe with `PipeOptions.Asynchronous`, and the request loop reads through `MessagePumpingStream`: every read is an
overlapped read (`BeginRead`), and while it waits, `MsgWaitForMultipleObjectsEx(QS_ALLINPUT, MWMO_INPUTAVAILABLE)` wakes for each message,
which `PeekMessage`/`TranslateMessage`/`DispatchMessage` dispatch; a `WM_QUIT` posted by vendor code is dropped (the helper ends only with its
pipe or its program). Writes go to the pipe as before. During a module's call the thread pumps as the vendor code pumps (COM's modal loop,
`ShowDialog`). On .NET 10, `BeginRead` on a pipe is a task with a wait handle, so the same code holds there.

The test `Pump_TheHelpersWindowsAnswerWhileItWaitsForTheNextRequest` (a hidden window on the helper's thread answers `SendMessageTimeout`
while the helper is idle) fails with the helper of S3a-13 (synchronous pipe, no pump: the call times out after 5 seconds) and passes with
this one; checked here by building the helper once with the old two lines. (A plain synchronous read on an overlapped pipe would also
dispatch sent messages, through the CLR's STA wait, but not posted ones, and not by design; the explicit wait does both.)

### 2. Text the protocol cannot encode

**Before.** The protocol writes strings with a strict `UTF8Encoding(false,true)`. A string with a lone surrogate (a note cut in the middle
of an emoji, which is the key data of a procedure or sheet signature) made it throw `EncoderFallbackException` while the request was built;
`Helper32Client.Call` caught only `IOException` and `InvalidDataException`, so the exception left the call unhandled (an `ArgumentException`
from the program's point of view). A reply with one would have ended the helper (its request loop caught neither).

**Chosen for Topaz: the string crosses unchanged.** On main `TopazWrapper.Call` passed the program's string itself to Topaz's method
(reflection, `methodInfo.Invoke(topaz,arrayConverted)`, a `string` argument not converted), so whatever Topaz does with a lone surrogate
(its own conversion to ANSI) happened inside Topaz. Replacing the surrogate with '?' before the call would give the same key only if
Topaz's own conversion also gives '?', which is not documented for `SetAutoKeyData` (deprecated) or `SetKeyString`. So the value crosses
as its UTF-16 code units: `TopazCommands.EncodeValue` writes a string that has a lone surrogate as type `u` with four hex digits per code
unit, `DecodeValue` rebuilds the identical string, and well-formed strings still cross as plain text (`s`), as before. Results go the same
way (a `GetSigString` or the stand-in's recorded calls). The helper's control gets the very string Topaz got in the program's process, so the
key data, and with it a stored signature's check, are unchanged. `FillSignatureEncodings`' key bytes were already computed in the program
and sent as bytes, and Guru's patient already crosses as UTF-16 bytes (section 4).

**For every other text: a `Helper32Exception` (Protocol).** `Helper32Client.Call` maps `EncoderFallbackException` to Protocol ("A text of
<module> <command> cannot be sent to the 32-bit helper program: ... Nothing was sent."). The message is built in memory before it is
written, so nothing reached the helper and the pipe stays in step; the next call goes to the same helper. The helper answers a reply it
cannot encode with the reason (a Remote `System.Text.EncoderFallbackException`) instead of ending. Note for the lead: a QuickBooks deposit
text or a Schick patient name with a lone surrogate now fails with that Protocol message; before S3a-13 and S3a-14 the vendor code got the
string as it was (QBFC, CDR). No such text is known; if one turns up, the module encodes it as Topaz now does.

### 1. The chooser

`CodeBase/Utilities/NativeFirstChooser.cs` (new): one `NativeFirstChooser` per vendor piece (`Topaz`, `SchickCdr`, `Guru`,
`QuickBooksDesktop`), each making **one run-time choice per program process**, on the piece's first use, written to the log once
(`Logger`, sub folder `NativeFirst`: the piece, the path chosen, the process's bitness and why) and returned by every later call:

- `InProcess`, the program's own process, when the piece can run at the process's bitness:
  - a **managed DLL** (`ChooseForManagedAssembly`, Topaz) whose PE and CLI headers (`PeImageInfo`, read from the file, nothing loaded) say
    IL-only without 32BITREQUIRED (any CPU; 32BITREQUIRED with 32BITPREFERRED counts as any CPU), or of the process's machine type (an x86
    32BITREQUIRED or mixed-mode assembly in a 32-bit process, an x64 one in a 64-bit process);
  - a **native DLL** loaded by name (`ChooseForNativeDll`, Guru) whose header has the process's machine type; the file is looked up where
    the loader looks (the program's folder, the system folder, which for a 32-bit process on 64-bit Windows is SysWOW64 for the loader and
    for file access alike, the Windows folder, the current folder, the PATH). When none is found the vendor's known build counts (Guru:
    x86), so the missing DLL is reported by the path that would have loaded it ("Could not find MedVisorInterface.dll");
  - a **COM class** (`ActivateComObject`, Schick CDR and QBFC) that activates from this process: the vendor code's own activation
    (`new CDRDicom.Application()`, `new QBSessionManager()`) is tried once through the chooser. Success chooses this process. A
    `COMException` with `REGDB_E_CLASSNOTREG` (0x80040154: an in-process server not registered for this bitness) or
    `CO_E_SERVER_EXEC_FAILURE` (0x80080005), also inside a `TargetInvocationException`, chooses the helper in a 64-bit process (null comes
    back and nothing more is activated here); any other failure is thrown and chooses nothing, so the next call tries again, as the vendor
    code did. An out-of-process (`LocalServer32`) server activates in either bitness.
- `Helper32`, the 32-bit helper's module (S3a-13, S3a-14), the fallback, otherwise.

**A 32-bit process always chooses itself** (`Decide`): its helper is 32-bit too and could run nothing the process cannot, so the vendor's
own error then shows as before (a not-registered QBFC gives QuickBooks' "Error: ..." of before S3a-13). In today's x86 .NET Framework build
every piece therefore runs in the program's process and the program behaves as `main` did before S3a-13 and S3a-14. A file whose headers
cannot be read stays in this process, where loading it says why. `ResetForTests` and `ForceChoiceForTests` serve the tests only.

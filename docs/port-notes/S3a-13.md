# Port note: S3a-13 (the 32-bit helper program and QuickBooks Desktop)

Stage 3a, wave 3 of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-13 row; decisions 19 and 20; open points
O-14 and O-15): branch `net10/s3a13-1` from `main` (`303533270`). The program is 64-bit after stage 3b, and QuickBooks Desktop's QBFC 10 is
32-bit only, so QBFC no longer runs in the program's process: a new 32-bit helper program, `OpenPmsDentalHelper32.exe`, runs it, and the

release, so the helper path is proven on the known runtime. S3a-14 adds Schick CDR, Topaz and Guru modules to the same helper without
changing the protocol (section 5).

no system setting changed.

## 3. The protocol

One source file, `OpenPmsDentalHelper32/Helper32Protocol.cs`, compiled into the helper and linked into CodeBase, so both ends read and write the
same bytes. Every type in it is internal.

- **Start.** On its first call, `Helper32Client` makes a pipe name, creates the pipe (section 4) and starts the helper with
  `--pipe <name> --parent <the program's process id>` (`UseShellExecute=false`, no window, the helper's own folder as working folder). The helper
  checks its arguments (anything else: exit code 2 at once, so a double-click does nothing), checks that the parent runs and started before it
  (a reused process id is refused, exit 3), connects within 30 seconds (exit 4 otherwise), checks with `GetNamedPipeServerProcessId` that the
  pipe's other end is its parent (exit 4), builds its modules and sends its **hello**: a magic string, the protocol version (1) and its process
  id. The client checks with `GetNamedPipeClientProcessId` that the connected process is the one it started, and that the hello has version 1
  and that process id. Each wait of the start ends after 30 seconds with `StartFailed`.
- **Messages.** A 4-byte little-endian length, then that many bytes: a kind byte (1 hello, 2 request, 3 reply) and the fields. A string is a
  presence byte and BinaryWriter's UTF-8 string (null and empty are kept apart), a string list a count (-1 for null) and its strings, a byte
  array a length (-1 for null) and its bytes. A length above 64 MB, a cut message or a wrong kind is a protocol error, never a large
  allocation.
- **Request**: module, command, string arguments, one byte field. **Reply**: ok, string results, one byte field, or the exception the module
  threw (its type's full name and its message).
- **One at a time.** The client sends one request and waits for its reply; a second caller waits on the client's lock. The helper answers in
  order on its one main thread.
- **Errors.** A module's exception comes back as `Helper32Failure.Remote` with the module's message as the exception's `Message`, so a window
  that showed `ex.Message` for a QBFC error shows the same text. An unknown module or command is `Remote` too.
- **Timeout.** Every call has its own timeout. A call not answered in time fails with `TimedOut` ("did not answer QuickBooks GetListOfAccounts
  within N seconds. It was ended and is started again on the next call."); the helper is ended, since it is stuck in that call, and the next call
  starts a new one. QuickBooks calls wait 30 minutes: QuickBooks asks the user to allow the program's access on its first connection to a
  company file, and the call waits for that answer, as it did in the program's process.
- **Crash.** A helper that ends during a call fails that call once with `Crashed` and its exit code ("ended during QuickBooks CreateDeposit (exit
  code -1). It is started again on the next call."), and the next call starts a new helper. A helper that ended between two calls is replaced
  on the next call without a message.
- **Missing.** No `OpenPmsDentalHelper32.exe` in the program's folder: `Missing`, "The 32-bit helper program OpenPmsDentalHelper32.exe was not
  found at <path>. Reinstall Open PMS - Dental or update it again to restore it." Nothing else is tried.
- **End.** The helper ends when the program closes the pipe (`Helper32Client.Default` is disposed at the program's exit: the pipe closes, the
  helper ends by itself, and is ended after 2 seconds, the time a process exit gives its handlers), when the pipe breaks, and when the
  program's process ends however it ends: the client puts the helper into a job object with `KILL_ON_JOB_CLOSE` (the program holds the only
  handle, which Windows closes with the process), and the helper also waits on its parent's process handle and ends itself when the parent is
  gone (for a program that could not make the job, for example inside a job that refuses it). The job has `SILENT_BREAKAWAY_OK`, so a process
  the vendor code starts (QuickBooks itself, a vendor's program) is not in it and is never ended with the program, and
  `DIE_ON_UNHANDLED_EXCEPTION`, so a crash of the helper shows no Windows error dialog; the helper also sets its own error mode
  (`SEM_FAILCRITICALERRORS|SEM_NOGPFAULTERRORBOX|SEM_NOOPENFILEERRORBOX`, this process only).
- **One helper per program process**, for the same user: `Helper32Client.Default` is per process, the pipe name carries the program's process id
  and 128 random bits, and the helper inherits the program's token (never elevated by itself: `asInvoker`).
- **The Host module** (`Host`): `Ping` returns the protocol version, the helper's process id, "0" for a 32-bit process and the runtime's
  version; `PipeSecurity` returns the pipe's owner and DACL in SDDL, read by the helper from its own end. For diagnostics and the tests.
- **Test modules.** `--test-module <assembly> <type> [<module name>]` (never passed by the program) loads a test assembly by name from the
  helper's own folder only: the name must end with `Tests` and be a plain name, its `.dll` must be in the helper's folder, it cannot replace
  the Host module, and its type's `public static string[] Handle(string command,string[] args,byte[] data,out byte[] dataReply)` answers the
  module's requests. The program's folder holds no test assembly, and whoever can write there can replace the program itself, so this loads
  nothing the program would not.

## 4. The pipe's security

The program creates the pipe before it starts the helper (`Helper32Client.Helper32Pipe.Create`, `CreateNamedPipe`):

- **Local only.** The name is in the local machine's pipe namespace (`\\.\pipe\OpenPmsDentalHelper32-<process id>-<32 hex>`), and the pipe mode
  has `PIPE_REJECT_REMOTE_CLIENTS`: a connection over the network (`\\server\pipe\...`) is refused whoever asks. The helper connects to `"."`
  only, and only to a name of this form.
- **First instance, one instance.** `FILE_FLAG_FIRST_PIPE_INSTANCE` and one instance at most: the create fails if any process made a pipe of
  that name first, and nobody can add a second end. The name has 128 random bits from `RandomNumberGenerator`, so no other process can guess it
  before the pipe exists.
- **Current user only.** The security descriptor is `O:<user SID>D:P(A;;GRGW;;;<user SID>)`: the current user owns it, the DACL is protected
  (nothing inherited) and its one entry allows read and write to the current user's SID. No Everyone, no other user or group, no anonymous or
  network entry. `Pipe_OnlyTheCurrentUserMayOpenIt` reads the descriptor back from the helper's end of the running pipe and checks exactly this.
- **Not inherited.** The handle is created with `bInheritHandle=0`, so no process the program starts gets it.
- **The right peer.** The client accepts only the process it started (`GetNamedPipeClientProcessId`); the helper accepts only its parent
  (`GetNamedPipeServerProcessId`) and allows `Identification` impersonation only.

`PipeOptions.CurrentUserOnly` (.NET Core 2.1 and later) would give a similar ACL on .NET 10 but does not exist on .NET Framework 4.8, whose
managed pipe API also has no way to ask for `PIPE_REJECT_REMOTE_CLIENTS` or `FILE_FLAG_FIRST_PIPE_INSTANCE`; so the pipe is created with the
Windows function directly (https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipew), which behaves the same on
both runtimes, and the client wraps the handle in a `NamedPipeServerStream` (`isAsync`, overlapped).

## 5. The module interface (for S3a-14)

`OpenPmsDentalHelper32/IHelper32Module.cs`:

```csharp
internal interface IHelper32Module {
	string Name { get; }                              //the request's Module, unique in the helper
	Helper32Reply Handle(Helper32Request request);    //Helper32Reply.Ok(results,data); throw for a failure
}
```

A module is one line in `Helper32Modules.CreateModules` (`Helper32Host.cs`); nothing in the protocol changes: its commands, their string
arguments and one byte field each way are its own. For S3a-14:

- **Threading.** The helper calls `Handle` on its one main thread, a single-threaded apartment kept for the whole process (`[STAThread] Main`):
  COM objects (QBFC's session manager here; Schick's `CDRDATALib`/`CDRDicom` objects) are created and called there, and a window (Topaz's
  signing window) can be shown there modally, which runs its message loop. `Apartment` in the tests checks the STA and the one thread.
- **State.** A module keeps its state in its own fields for the helper's lifetime, which is one program process (QBFC's static fields lived as
  long as the program; they live as long as its helper now). A restarted helper starts with fresh state.
- **Data.** The byte field carries a picture (Topaz's signature as an image) or a structure (Guru's `ToCPlusPlusStructure` bytes) as it is.
- **Owner window.** A module that shows a window over the program's gets the program's window handle as a string argument (the handle value);
  the window is the helper's, shown over the program's.
- **Timeout.** Each caller chooses its own (`Helper32Client.Call(...,TimeSpan)`); a call that waits for the user (a signature, QuickBooks' access
  question) waits long.
- **Commands file.** As `QuickBooks/QuickBooksCommands.cs`, a module's command names and argument order can live in one small file that the
  program's side links, so both name them alike.
- **Tests.** Compile the module's source into `tests/Helper32Tests` (as `QuickBooksModule.cs` is linked) and run it against a fake of the vendor
  interface; `QuickBooks/QbfcFake.cs` makes fakes of COM interfaces at run time (System.Reflection.Emit, also on .NET 10) and records each call.
- **Vendor scan.** Add the vendor references to `NoHqTests/Helper32VendorScanTests.cs`.

  before you accept. Also for the launch check: close the program while QuickBooks' prompt is open.
- **For S3a-14:**
  - A module loads its vendor code lazily, in `Handle`, never in its constructor. `Helper32Modules.CreateModules` builds every module when
    the helper starts, so a constructor that throws (a missing `SigPlusNET.dll`, no CDR installed) would also break QuickBooks. Write this
    in `IHelper32Module`'s summary.
  - Between requests the helper's STA thread waits in a synchronous pipe read and pumps no messages. If CDR or Topaz objects own a window
    on that thread, other programs' broadcasts (`WM_SETTINGCHANGE`) can hang while the helper is idle. Either wait with a message-pumping
    wait (overlapped read plus `MsgWaitForMultipleObjectsEx`), or release the vendor objects after each call. Check it at S3a-14's launch.
- **Later cleanups:**
  - **Build id.** The helper is not in `$BuildIdFiles` or `ForkReleases.ListBuildIdFiles`, so a release that changes only the helper keeps
    the old build id. Add it with the next change of either list.
  - **Test hook.** The shipping helper keeps the `--test-module` hook (guarded: a `*Tests` assembly in the helper's own folder only).
    Limit it to builds with a test define, or check that the folder is not writable, once the install-location policy is settled.
  - **QuickBooksDesktopHelperTests clean-up.** `tests/VendorDirectTests/Qbo/QuickBooksDesktopHelperTests.cs` should delete its copy in a
    nested `finally` and kill a copy still running first, as `HelperTestBase` does. Done in `net10/clean1-1` (CLEAN-1 item 21).
  - **Pipe rights.** They could be `FILE_GENERIC_READ|FILE_WRITE_DATA` instead of `GW`, which also allows creating another instance (for
    the same user, with one instance at most: harmless).

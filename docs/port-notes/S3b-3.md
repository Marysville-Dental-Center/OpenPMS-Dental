**Why the console tools and the test projects name `UseWindowsForms`.** A project that references the business library but has only
`Microsoft.NETCore.App` of its own asked the offline folder for System.DirectoryServices, System.Configuration.ConfigurationManager and
System.Security.Cryptography.Pkcs (>= 10.0.13), System.DirectoryServices.AccountManagement's dependencies (NU1101/NU1102). NuGet prunes the
packages a project's *own* frameworks hold (the framework reference that flows from CodeBase arrives too late for the restore), so these
were not pruned. With the Windows Desktop framework named, they are, as in the business library itself, and nothing is downloaded or
shipped twice. DevDbTool, AdoptionValidation, NoHqTests, SyntheticData.Tests, AdoptionValidation.Tests and BINATests name it; each run of
them gets the Windows Desktop runtime anyway, as the business library needs it.

**CodeBase (layer A), one change:** `MiscUtils.DistinctBy` is compiled for .NET Framework only. .NET has `Enumerable.DistinctBy`, which does
the same (a `HashSet` of the keys with the default comparer, the first item of each key in source order, deferred), and with both every call
in a file that imports System.Linq and CodeBase was ambiguous (CS0121, 16 calls in the business library; the program has more). No caller
named `MiscUtils.DistinctBy` as a static method.

## 3. OpenPmsDentalBusiness.XmlSerializers.dll from Microsoft.XmlSerializer.Generator

.NET Framework's SGen wrote the file in Release builds because the project had the Middle Tier's `WebReferenceUrl` item
(`GenerateSerializationAssemblies` Auto, `SGenUseProxyTypes`): it held only the ASMX proxy's serializers. SGen does not run for .NET, and
the proxy does not compile there. The set-up now (S3b-0 item 10's two findings):

- `GenerateSerializationAssemblies` **Off** (MSBuild's SGen task would otherwise run the .NET Framework sgen.exe for a .NET 10 assembly in a
  Release build), and the `WebReferenceUrl` item is gone (its only build effect was SGen; the `WebReferences`/`WCFMetadata` folder items stay
  for the vendor services' data classes).
- `<PackageReference Include="Microsoft.XmlSerializer.Generator" IncludeAssets="build" PrivateAssets="all" />`: the package's build
  targets only. Without `IncludeAssets` the compiler got the tool's own `dotnet-Microsoft.XmlSerializer.Generator.dll` (its `lib` folder) as
  a reference and every project above would copy it; `PrivateAssets` keeps it from the projects that reference this one.
- `<DotNetCliToolReference Include="Microsoft.XmlSerializer.Generator" Version="10.0.15" />`: the target runs `dotnet
  Microsoft.XmlSerializer.Generator`, a per-project CLI tool; without the item the host cannot resolve it and the build only warns.
  (CLI tool items take no central version, so the version is written here; it must follow `Directory.Packages.props` at each bump.)
- `SGenTypes`: the Middle Tier's envelopes, the twelve `DataTransferObject` classes that RemotingClient and DtoProcessor serialize for every
  request (`DataTransferObject.Serialize`/`Deserialize`): DtoGetDS, DtoGetTable, DtoGetTableLow, DtoGetSerializableDictionary, DtoGetLong,
  DtoGetInt, DtoGetDouble, DtoGetVoid, DtoGetObject, DtoGetString, DtoGetBool, DtoException (with Credentials and the `IXmlSerializable`
  DtoObject inside them). Without a list the generator takes every public type and stops at the first two that share an XML name (S3b-0).
  S3b-6, which replaces the transport, may revisit the list; the DTO classes themselves stay.

The target runs after every build, Debug too: it reads `obj\<configuration>\OpenPmsDentalBusiness.dll`, compiles
`obj\...\OpenPmsDentalBusiness.XmlSerializers.dll` (IL, AnyCPU) and copies it into `bin\<configuration>\`. The reference resolution of every
project above copies it next to the business library as a serialization assembly (it is in ServiceManager's and the HL7 service's output,
as SGen's file was in Release builds; Build-Release takes it from `OpenPmsDentalBusiness\bin\Release`).

**Pairing by MVID** (the A8 window check reads it the same way; read with Mono.Cecil): Debug, `OpenPmsDentalBusiness.dll` MVID
`1d12458a-b777-4c3d-b76c-d0de932b269b`, the serializer's `XmlSerializerVersionAttribute` `ParentAssemblyId = 1d12458a-...-d0de932b269b,;
Version = 1.0.0.0`; Release (a scoped Release build of the library) `09a31b02-6b8a-458d-9b10-237271c3e27b` and the same in the serializer's
attribute. Both pair: `ParentAssemblyId` is the MVID followed by a comma, which is what .NET's `XmlSerializer` compares (with the namespace;
not the Version, which the generator writes as 1.0.0.0 where SGen wrote 4.0.0.0). The serializer assembly is `OpenPmsDentalBusiness.XmlSerializers,
Version=24.3.63.0` (the parent's version), references System.Runtime, System.Xml.XmlSerializer and System.Xml.ReaderWriter 10.0.0.0 and the
business library, and holds the 12 typed serializers, `XmlSerializer1` and `XmlSerializerContract` (39,424 bytes Debug, 34,304 Release).

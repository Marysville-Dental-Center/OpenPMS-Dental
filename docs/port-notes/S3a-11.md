# Port note: S3a-11 (setup without the per-user mode)

**The owner's run (open point O-3: the owner runs every elevated script, never an agent).** At the gate, after the Release dry run
(`tools\Build-Release.ps1 -OutDir <dryrun>`), open Windows PowerShell with "Run as administrator", change to the repository folder `<repo>`,
and paste this one line, with `<dryrun>` the dry run's output folder and `<version>` the release version (`0.0` today):

    powershell -NoProfile -ExecutionPolicy Bypass -File "<repo>\tools\Test-Installer.ps1" -Setup "<dryrun>\OpenPmsDental-<version>-Setup.exe" -Staging "<dryrun>\staging"

It takes a few minutes (four silent installs, three uninstalls), prints one `ok` or `FAIL` line per check, then `N checks passed, M failed`
and `Exit code 0` (every check passed) or `Exit code 1`. Exit code 2: the PowerShell was not elevated, and nothing was changed. Exit code
3: the setup or the staging folder is missing, or the PC has a per-user or 64-bit view uninstall entry of the program; nothing was
installed. What it changes on the PC is in section 3; a setup built from this branch for the run is in section 5.

## 1. The setup (`installer/OpenPmsDental.iss`)

Setup always runs as administrator and installs for all users (decision 7, the owner: "Don't need 'Install for me only'"):

- `PrivilegesRequiredOverridesAllowed=commandline` is gone; `PrivilegesRequired=admin` stays. Inno Setup now ignores `/CURRENTUSER` and
  `/ALLUSERS` and asks for elevation as before.
- The `/CURRENTUSER` line of the command-line notes is replaced by a note that setup always installs for all users, so `{autoprograms}` and
  `{autodesktop}` are the common Start menu and desktop, and the connection settings tool can always run.
- The branches only a per-user install reached are gone: in `SetUpConnection` the new-connection branch that logged "needs the connection
  settings tool, which needs administrator rights" and showed the message instead of running the tool, and the upgrade's
  `if not IsAdminInstallMode then Exit;`; in `ShouldSkipPage` the security page's `(not IsAdminInstallMode)`; and the Event Log source's
  `[Registry]` entry's `Check: IsAdminInstallMode`. The entry keeps `Flags: uninsdeletekey`. The comments that said "administrative installs
  only" now say that setup is always elevated.
- Nothing else changes: an administrative install took exactly these paths before, so for the office's installs (always as administrator)
  the setup behaves as on `main`. The runtime part stays out (decision 20: the setup installs no runtime); S3b-7 adds the 64-bit install.

## 2. The test script (`tools/Test-Installer.ps1`)

It was a per-user test (`/CURRENTUSER`, no administrator rights, the uninstall entry under HKCU). It is now an elevated test:

- **Unelevated it refuses before any change.** The first statement after `param` checks the token for the Administrators role; without it
  the script prints that it needs an elevated PowerShell ("Run as administrator"), "Nothing was changed." and `Exit code 2`, and exits 2. It
  makes no folder, writes no log and reads nothing but its own token. Checked unelevated on the build PC, with arguments and without (the
  defaults would have made `installer\bin\install-test`): exit code 2 both times, no log folder, no `%TEMP%` test folder, the registry keys
  as before, no new file in the worktree; `InstallerTests.TestInstaller_RefusesToStartUnelevated_AndChangesNothing` runs the same refusal at every
  test run.
- **The checks that stop it unchanged** (exit code 3) come next, before its first change: the setup and the staging folder exist; no
  per-user (HKCU) or 64-bit view uninstall entry of the AppId (this setup makes neither).
- It still installs into new `%TEMP%` folders with `/DIR=`, silently (`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /NOICONS /MERGETASKS="!desktopicon" /PREREQS=skip`),
  now without `/CURRENTUSER`. `/MERGETASKS="!desktopicon"` (review fix) turns the desktop task off explicitly: the test installs share
  the AppId of an installation already on the PC, so setup restores that installation's tasks (`UsePreviousTasks`), and the task's
  `Flags: unchecked` applies only when there is none; without it, an installation set up with the desktop icon would have its common
  desktop shortcut overwritten by scenario A and deleted by the test uninstall. `/NOICONS` only skips the Start menu entry.
- It reads the all-users uninstall entry under `HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall\{D5640A25-...}_is1`
  (the setup is 32-bit; S3b-7 moves it to the 64-bit view): written, named "Open PMS - Dental" (no "(Current user)" any more), the version
  of the setup's file name, `Inno Setup: App Path` the test folder; and that there is no per-user entry.
- It checks the Event Log source key `HKLM\SYSTEM\CurrentControlSet\Services\EventLog\Application\OpenPMS-Dental` after each install
  (`EventMessageFile`, REG_EXPAND_SZ, unexpanded, as the `.iss` writes it) and that each uninstall deletes it (`uninsdeletekey`), with the
  uninstall entry.
- Scenarios A, B and C use a database server on this computer (`localhost:3307`, `127.0.0.1`, `localhost`), for which a silent setup runs
  no connection settings tool (A checks the log has no run of it). B's upgrade keeps the file (a loopback server too) and runs only the
  tool's `/check`, which passes without connecting; the script checks that the upgrade passes none of the page values.
- **New scenario D:** `/DBSERVER=dbserver.example.test:3307` and no `/DBCA`. Setup runs
  `OpenPmsDentalDbSettings.exe /server=dbserver.example.test:3307 /database=opms_test /user=opms_user /silent`; the tool refuses before it
  changes anything ("A database server over the network (...) needs the office CA certificate file (/ca=).", exit code 5,
  `EXIT_REFUSED`), and the silent setup ends with exit code 10 (`DbSettingsFailedExitCode`). The script checks the exit code, the four log
  lines (the run, the tool's result line, its exit code, "Setup exit code 10: ..."), that the files are installed, that
  `FreeDentalConfig.xml` is the one setup wrote (no password, no `SslCa`, no thumbprint), that the folder holds nothing the tool made, that
  the tool has ended, and the uninstall as in A. The tool never connects: it stops at the CA check, and no `/test` is given.
- **An installation already on the PC.** The build PC has 0.0 installed (`C:\Program Files (x86)\Open PMS - Dental`, its uninstall entry
  and Event Log source key; read only, 2026-11-15). The test installs use the same AppId and source name, so each test uninstall would
  delete that installation's two keys. The script saves both before the first change (in memory, and with `reg.exe export` as
  `uninstall-entry-before.reg` and `eventlog-source-before.reg` in the log folder) and writes them back at the end, also after a failure
  (`finally`). The shortcut check compares the program's shortcuts with those before (0.0 has one in the common Start menu): none new or
  changed. That installation's folder, files and shortcuts are not touched (setup's `/DIR=`, `[InstallDelete]` and the uninstall work in
  the test folder only).
- It never starts the program (the only `Start-Process` calls are the setup and the uninstaller; the only `&` call is `reg.exe export`)
  and never connects to a database.
- It prints one `ok`/`FAIL` line per check, the summary and `Exit code N`. An exception stops the scenarios with a FAIL line, and the
  clean-up still runs.

## 3. What the run changes on the PC

While it runs: four new folders `%TEMP%\OpenPmsDental-installtest-<a|b|c|d>-<id>\Open PMS - Dental` (the test program folders); the
uninstall entry above and the Event Log source key, which setup writes and each uninstall deletes; with an installation on the PC, that
installation is missing from Apps and its Event Log source is missing until the end. At the end: the script deletes the four parent folders
(with scenario B's A to Z folder, which it made), deletes anything an uninstall left of the two keys (and says so; a FAIL line has
already reported it), and writes back the saved keys of an installation that was there. It keeps the setup and uninstall logs and the two
`.reg` files in `-OutDir` (default `<dryrun>\install-test`). Setup installs no shortcut (`/NOICONS` for the Start menu; the script turns the desktop task off explicitly with
`/MERGETASKS="!desktopicon"` rather than relying on its unchecked default, which an installation already on the PC overrides), no Visual C++
runtime (`/PREREQS=skip`; setup only logs that it is missing), and nothing else: setup's own temporary folder and the uninstaller's copy
in `%TEMP%` are removed by Inno Setup.

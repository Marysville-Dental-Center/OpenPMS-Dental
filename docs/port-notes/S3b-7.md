## 1. What decision 22 removed

Owner decisions 21 ("skip Bridge release") and 22 ("nothing in prod has openpms install. Don't worry about migration") override the row.
So this package does **not** build or test the move from the 32-bit install: no search for the old uninstall entry in the 32-bit view, no

from one .NET 10 release to the next. The migration code already built stays with its tests (no-cut rule) and nothing was added to it:
S3a-5's PasswordVault copy, S3a-10's guards (the unreadable-manifest and other-runtime refusals, the forward switch) and S3a-10f's Recopy
offer. A v0.0 installation (32-bit, its uninstall entry in the 32-bit view) is a separate installation for the 64-bit setup; Test-Installer
leaves it alone and checks that its entry is unchanged.

## 3. The runtime part as built (decision 20)

**What the runtime files are.** `ForkReleases.GetRuntimeFileNames(folder)`: every file that a `.deps.json` at the top of the folder or in
`Helper32\` names as an asset (runtime or native) of a library of type `runtimepack` (`runtimepack.Microsoft.NETCore.App.Runtime.win-x64/10.0.15`
and the WindowsDesktop one; `win-x86` in `Helper32\`). That is exactly the list the SDK copied from the runtime packs' own
`data/RuntimeList.xml` (measured on this branch's build: 247 x64 files and 213 x86 files, equal to the packs' lists, the helper's
WindowsDesktop pack by its WindowsForms profile; `RuntimePartTests.ReleaseBuild_OneRuntimeVersion_...` compares the two). It works at run
time on any install, needs no list in the program, and a .NET Framework folder (no `.deps.json`) has none. Two programs that name a shared
runtime file at two versions, or a folder whose files are of two versions, are refused (`InvalidDataException`: "Run the setup").

**Its key.** `GetRuntimePart(folder)`: version, architectures (the program's first: `win-x64 win-x86`), every file's relative path, size
and SHA-256, and `Key=ComputeKey()` as S3a-10 defined it. The key changes with any runtime file and with the version, never with the program.

**Publish** (`ForkReleases.Publish`, the update server, direct connection only):
1. `GetRuntimePart` of the install folder. When the published runtime part (`GetPublishedRuntimePart`, row type 102) is the same
   (`IsSameAs`: key, version, architectures) its archive hash is reused and **no runtime row is written**.
2. Otherwise `BuildRuntimeArchive` zips the runtime files (each read once and checked against its listed size and SHA-256) and the runtime
   part's manifest without its archive hash, and `DocumentMiscs.ReplaceForkRuntime` deletes the old 102 and 103 rows, writes the segments
   (type 103, about 1 MB of base64 each) and then the manifest (type 102) last.
3. The program part as before (`GetReleaseFiles` leaves the runtime files and both manifests out), its manifest naming the runtime part with
   the five lines S3a-10 defined and a `Runtime` line for the version and architecture of the files, then `ReplaceForkRelease` (manifest
   last), then the `ForkProgramVersion` marker. Format 1, and only the keys of S3a-10 section 1: every reader parses it (the binding contract
   of S3a-10 section 7 holds; no new key, so no new format number).

The runtime part's own manifest (row 102 and `ForkRuntime.manifest` in its archive): `Format=1`, `Product`, `Runtime=Microsoft.NETCore.App
<version> <program's architecture>`, then `RuntimeVersion`, `RuntimeArchitectures`, `RuntimeArchiveSha256` (not in the archive's copy),
`RuntimeKey` and one `RuntimeFile` line per file. `ReleaseRuntimePart.ParseManifest` is strict (unknown key, another product, another format,
the .NET Framework, a version or architecture that does not fit, a key that does not match the files, a file twice, an unsafe path: all
`FormatException`). A .NET Framework build never reads type 102 or 103.

**Pull** (`PrefL.PullRelease` → `ForkReleases.DownloadAndVerify(folderUpdate, identity, Application.StartupPath)`):
1. The release for another framework or architecture is refused before anything is read (S3a-10).
2. The program part is downloaded and checked as before.
3. When the release names a runtime part whose key differs from the installation's (`GetInstalledRuntimeKey`: the key its own
   `ForkRelease.manifest` names, which UpdateFileCopier wrote after checking every runtime file; for a folder without one, a fresh install,
   the key over its runtime files; "" when unknown), the runtime part is downloaded into the same folder: the 102 row must be the one the
   release names (key, version, architectures, archive SHA-256), the joined 103 segments must match that SHA-256, the archive may hold only
   the listed runtime files and its own manifest, equal to the published one, and `ForkRuntime.manifest` is written into the folder
   (`IsRuntimeIncluded`). With the same key, **no runtime segment is read**.
4. `VerifyFolder(folder, IsRuntimeIncluded)`: every file of both parts with its size and SHA-256; a runtime file in a program-only
   download is "Not in the manifest". A runtime file of another version therefore never passes.
5. PrefL checks the architecture again on what was downloaded, says when a new .NET runtime comes with the release, and starts the copier.

**The copier's temp folder** (`PrefL.OpenFileCopier` → `ForkReleases.CopyFileCopier(source, %TEMP%\openpms-dental\ForkReleaseCopier,
folderRuntime)`): the copier's four files and every runtime file its own `.deps.json` names (about 214 of the x64 runtime), from the
download when the pull brought the runtime part, otherwise from the program folder, whose runtime then has the same version. The folder is
emptied first (never two copiers' files). A copier whose `.deps.json` names another runtime version than the runtime folder's
`OpenPmsDental.deps.json` is refused before anything is copied; a missing runtime file too. So the copier runs on one x64 runtime and holds
no file of the program folder while it replaces them.

**UpdateFileCopier** (`FormMain`): stops the program, CentralManager, DatabaseIntegrityCheck and ServiceManager by name as before, then
every other process whose program file is in the program folder or `Helper32\` (`KillProcessesInFolder`: the connection settings tool,
the helper, the HL7 service; a process whose path it cannot read is left, and the files-in-use check names what it holds). It checks the
download (with `ForkRuntime.manifest` present: that runtime part must be the release's, and the folder is checked with it), copies the files
of the top, `OpenDentalReplicationService\` and `Helper32\` (not `ForkRuntime.manifest`), then checks every runtime file of the program
folder against the release's runtime part (`VerifyFiles`) **before** it writes `ForkRelease.manifest`. If one does not match, it writes no
manifest and says "Run the setup of this release on this workstation as an administrator: it carries the full runtime" (no retry). So a
workstation never claims a release whose runtime files are of another version, and its next pull, finding no manifest, compares the key over
its real runtime files. The setup always carries the full runtime.

**Sizes** (S3b-0 item 13 and this branch's Release build): the runtime part is 460 files (247 x64 + 213 x86 in `Helper32\`), about 255 MB
on disk and about 110 MB zipped, published once per runtime version; the program part is 97 files.

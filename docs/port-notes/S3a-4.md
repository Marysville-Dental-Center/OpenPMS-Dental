# Port note: S3a-4 (golden outputs and known answers)

Package S3a-4 of stage 3a, wave 1, of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-4 row; section 3; the
risk table rows "Crypto", "RDL `<Code>` blocks", "Number formatting" and "Type names"; decision 14): branch `net10/s3a4-1` from `main`
(`818fe6015`). A new test project, `tests/GoldenOutputTests`, records what the program writes, byte for byte, with the .NET Framework 4.8
build, and compares every later build with that record. Stage 3b runs the same tests on .NET 10 and compares with the same files, as they are.
No program code changed, no schema change, no package added, nothing downloaded, no program started.

## 1. The fixture database

One scratch database per test run, `gold_<UTC start yyMMddHHmmss>_<process id>_<random>_main` on the local MariaDB (127.0.0.1:3306, root,
blank password), built the way the EFORM-PRINT tests build theirs (`GoldenDb.cs`): `db/init/new-database.sql` loaded statement by statement
into an empty utf8mb3 database, then `ForkMigrationRunner.Run()`, then the synthetic rows of `GoldenData.Seed()`. It is dropped when the run
ends (`GOLDEN_KEEP_DB=1` keeps it); leftovers of a crashed run are dropped by a later run after 12 hours; the helpers drop only names that start
with `gold_`. Only `GOLDEN_TEST_DB=skip`, no server, or a global `sql_mode` that is not blank (`GoldenDb.GetSkipReason`) makes the database
tests Inconclusive. Once the server has answered, a failure while building the database (`DropStale`, `CreateFromInitFile`,
`ForkMigrationRunner.Run`, `Cache.Refresh`, `Userods.GetUser`) or while writing the fixture rows fails every database test with the full
exception (it is not hidden as a skip): in 3b a difference in the init loader, the migrations or the cache refresh on .NET 10 is exactly what
the suite must report. The database is marked created just before its `CREATE DATABASE`, so `AssemblyCleanup` drops it even when a later
build step threw.

The rows (`GoldenData.cs`), all synthetic (example names, the 97000 ZIP range, 555 phone numbers, Z procedure codes, payer ID `ZZ123`, the
test NPI `1234567893`):

- the practice preferences every output reads (title, addresses, phones, the 837 switches `UseBillingAddressOnClaims`,
  `EclaimsSeparateTreatProv`, `EclaimsSubscIDUsesPatID`, `ClaimMedProvTreatmentAsOrdering`, the pay-to address, `BalancesDontSubtractIns`,
  `EasyNoClinics`), set explicitly so no default of the init file shows in an output;
- one provider; four procedure codes; an adjustment type and a payment type;
- family 1 (`Goldtest, Ava Q`): insurance (carrier, plan, subscriber, patient plan), three completed procedures of 57.25, 0.1+0.2 and
  1234.56 on 2025-03-10, a primary claim `GOLD0001` waiting to send with its three claim procedures, a treatment plan with three procedures,
  a payment plan;
- family 2 (`Goldzero, Ben`): a procedure of 0.10, an adjustment of 0.70 and a payment of 0.80 on three days (the near-zero case of
  `docs/port-notes/S3a-3.md`, section 4);
- two clearinghouses (`x837D_5010_dental` and `x837D_4010`) with a synthetic sender (TIN `991234567`), so the batches do not carry the
  program's built-in sender;
- the chart of accounts: the init file's default accounts are removed and five synthetic ones go in (one inactive, one whose name starts with
  `=`, names with a comma and with quotes), with four journal entries;
- two statements dated 2025-06-30: the family statement of family 1 and the limited statement of family 2 (its procedure, adjustment and
  payment split attached through `stmtlink`);
- a wiki list `goldensynthetic` whose cells hold `&`, `<`, `>`, quotes, non-ASCII letters, an en dash, an empty cell and a CRLF.

**Fixed dates.** Every row is dated in 2025, aging is computed as of 2025-06-30, and the statements are dated 2025-06-30, so no output depends
on the day the tests run.

**Fixed IDs.** Before any row goes in, each table the fixture writes to gets its own `AUTO_INCREMENT` base above every row the init file
brings (`provider` 9001, `patient` 9101, `procedurelog` 9701, `claim` 9801, `statement` 10301 and so on; the list is in `GoldenData.cs`), and
the rows always go in in the same order, so every primary key that shows in an output (account numbers, `REF*6R` line references, the SQL
`WHERE ProcNum = 9702`, the statement number) is the same in every run and on every PC.

**Culture.** Every test runs in en-US, taken with `CultureInfo.GetCultureInfo("en-US")` (read-only, without the test PC's regional
overrides), on the test thread and as the default of new threads (`Golden.UseUsEnglish`). The program chooses itself which outputs are
invariant (the X12 amounts, the SQL text, `SOut`) and which use the current culture (statement text and `.csv`, signature keys, the RDL
report's default text); the tests do not change that choice, they only fix the culture to en-US.

**What the fixture depends on.** The code of this branch and the init file at fork schema level 2026111401. The coordinator regenerates the
init file after merging the schema packages; a regenerated file adds tables and preferences and changes none of the rows or preferences the
outputs read (they are set explicitly), so the records should stay valid. If a later package does change an output on purpose, its owner
records the fixtures again **on the .NET Framework build, before the 3b switch** (section 3), and says why in its report; after the switch a
record can no longer be made, and every difference is a 3b finding.

## 2. The outputs, their fixtures and their normalisation

order mark, or `Golden.AssertBytes`). `.gitattributes` has `tests/GoldenOutputTests/Fixtures/** -text`, so git never converts the line ends
of these files (CRLF stays CRLF, LF stays LF) in any checkout, whatever `core.autocrlf` is. A difference fails with the first differing line
and writes this run's output to `GoldenActual\<fixture>.actual` next to the test assembly, for a diff.

## 3. Record mode

`OPMS_GOLDEN_RECORD=1` in the environment of the test run (vstest passes it on to the test host) makes every golden test write its fixture
instead of comparing. It is off by default. It writes into the source tree (`tests\GoldenOutputTests\Fixtures`, found by walking up from the
test assembly to the folder that holds `GoldenOutputTests.csproj`), never into the output folder, so the result is what git shows. It is
refused on any runtime but .NET Framework (the test fails with that message): the fixtures are the .NET Framework record, and a record made by
the .NET 10 build would hide exactly the differences the tests are for.

To record: build the .NET Framework build, run GoldenOutputTests once with `OPMS_GOLDEN_RECORD=1`, review `git diff
tests/GoldenOutputTests/Fixtures` (every changed line must have a reason), run once more without the variable (it must pass), and commit the
fixtures in their own commit.

## 4. The known answers

Every ciphertext is made by the test from a synthetic plaintext, with a test key or the program's own built-in key or encrypt function. No
real stored Open Dental or Open PMS - Dental password, connection string or signature is read, decrypted or committed. Each one is checked
both ways:

- **today's encryption gives the recorded ciphertext**, byte for byte (`KnownAnswers_EncryptGivesTheRecordedCiphertexts`, one fixture file);
- **the recorded ciphertext decrypts to the plaintext**, so a .NET 10 build also reads what the .NET Framework build wrote, even if its own
  encryption had changed:
  - `MiscUtils.Decrypt` (AES-128, the program's built-in key, zero IV) of a plaintext of more than one block with accented letters, the euro
    sign and a character outside the BMP, and of a one-character plaintext;
  - `CentralConnections.Decrypt` with the 16-byte test key `GoldenTestKey016`, the same two plaintexts;
  - a **stored signature**: the treatment plan's signature as the signature box stores it (`SignatureBox.SetAutoKeyData` with the plan's
    key hash, `SetPointList`, `GetSigString`), read back with `SetSigString` to the points as the box keeps them (each coordinate written with
    `"0.#"`, so 30.25 comes back as 30.3); a digital signature ("Digitally Signed by ...") read back to its text; the pay plan's signature as
    the eClipboard and portal path stores it (`TreatPlans.GetScaledSignature`, `SigBox.EncryptSigString` with the MD5 of the key data), read
    back to the same number of points; and a box keyed with another key reads nothing;
  - the **RDL data source reference file**: `DataSourceReference.Retrieve` of the committed `.dsr` (written by the .NET Framework build's
    `Create` with the test passphrase `golden test passphrase`: `PasswordDeriveBytes` with a random 16-byte salt, Rijndael with a 32-byte key)
    gives the synthetic connection string `Server=db.example.test;...;Password=not-a-real-password`; a file this build writes reads back too.

## 5. What 3b compares, and what it must do first

Stage 3b runs GoldenOutputTests on .NET 10 x64 without record mode, against these files as they are; every difference is a 3b finding to fix in
the program (or, with the owner, to accept and record in the report), never a fixture to rewrite. For the tests themselves to run there:

- **Code pages.** `PdfRead.ExtractText` decodes simple fonts with `Encoding.GetEncoding(1252)`: GoldenOutputTests needs the code-page provider
  registered in its test process, as `docs/port-notes/S3a-3.md` (section 4) lists for the other assemblies.
- **RDL `<Code>`.** The report's `<Code>` block is compiled by `VBCodeProvider` on .NET Framework; on .NET it must be Roslyn (S3b-2, decision 14),
  and `RdlReport_VbCodeFunctions_Pages` is the test S3b-2's row asks for ("the report output equals the S3a-4 record").
- **`MiscUtils.Encrypt`/`Decrypt`** are compiled under `#if !DOT_NET_CORE && !DOT_NET_STANDARD` in CodeBase; the net10 build of CodeBase must
  keep them (they are not .NET Core-only code).
- The test project itself: only its target framework and platform change (stage 3b retargets the test projects); the tests use no
  .NET Framework-only API (reflection on two private members, `Statements.WriteStatementToCSV` and `SignatureBox.listPointFs`, works the same).

**Differences already visible in the code** (left for 3b; nothing in this package changes program code):

- `Statements.WriteStatementToCSV` writes `statement.BalTotal`, `InsEst` and their difference with the double's default text
  (`$"\"{statement.BalTotal}\""`, current culture): .NET Framework writes 15 digits (`0.3`), .NET the shortest round-trip text
  (`0.30000000000000004`). `statement-limited-computed.csv` shows it.
- RdlEngine writes a double without a `Format` with `o.ToString()` (`RdlEngine/Definition/Style.cs`, `GetFormatedString`): `Code.Triple`
  of 0.30 is `0.9` on .NET Framework and `0.8999999999999999` on .NET. `rdl-code-report.txt` shows it (S3b-2 owns RdlEngine).
- The statement money texts of `SheetFiller` that S3a-3 left (section 4 of its note: the aging and balance static texts at 1091-1097, among
  others) show in the two statement PDFs.
- `PasswordDeriveBytes.GetBytes(32)` (the `.dsr` key) asks for more bytes than SHA-1 gives, which only the .NET Framework's own extension of
  PBKDF1 answers; whether .NET derives the same key is what `KnownAnswers_RdlDataSourceReference_ReadsTheRecord` shows on the 3b build.
- `wikilisthist.ListContent` carries `msdata:UseCurrentLocale="true"` and XML Schema types only (`xs:long`, `xs:string`), no .NET type names;
  the revert test proves the .NET Framework text reads back on .NET.

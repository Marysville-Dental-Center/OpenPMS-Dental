**The qbXML versions each QBFC accepts.** Intuit's SDK 15.0 release notes
(https://static.developer.intuit.com/resources/ReleaseNotes_QBXMLSDK_15_0.pdf, the table "the different versions of the QuickBooks Foundation
Class (QBFC) Library and the versions of the qbXML specification that support them") list each QBFC from 10 to 15 with every US version from
1.0 up to its own: QBFC10 "10.0, 9.0, 8.0, ... 1.1, 1.0", QBFC15 "15.0, 14.0, ... 1.1, 1.0". The release notes of 16.0 and 17.0 are not public at
the same address (403); the 64-bit SDK works "with QuickBooks Desktop 2022 and above"
(https://developer.intuit.com/app/developer/qbdesktop/docs/get-started/quickbooks-products-supported-by-the-desktop-sdk).

**The request versions are today's: 1.0 (the connection test), 8.0 (the account and class lists) and 9.0 (the deposit).** Every QBFC in the
table accepts them, they are "no lower than today's", and the QuickBooks releases that serve the 32-bit program serve them, so the requests
QuickBooks gets are the ones the 32-bit program sends. A higher version would add nothing these four calls use and would fail on a QuickBooks release
older than the QBFC. If QBFC 16 refused one of them (not expected from Intuit's table), `CreateMsgSetRequest` fails, which is a failed
connection: the helper takes the call (section 6).

## 3. Why late-bound

The SDK is not installed on the build PC and must not be, and no interop of QBFC 15 or later is in `Required dlls`; an early-bound path would
need both (the survey's first plan, "a new embedded interop"). Late-bound calls through IDispatch need neither: the member names are QBFC's
(the same in QBFC 10 and 16, as Intuit's samples show), and IDispatch converts the arguments. What a late-bound caller cannot take from
QBFC 10 is the **enum values**: QBFC numbers `ENResponseType` in order (QBFC 10: `rtClassQueryRs` 1038, `rtAccountQueryRs` 1082), and each
version adds response types, so the values differ between versions. They are read by name, once per process, from the activated session
manager's own type library (`ComTypeLibEnums`): `roeContinue`, `omDontCare`, `asActiveOnly`, `rtAccountQueryRs`, `rtClassQueryRs`. A type
library without one of them is a failed connection (section 6). The arguments keep QBFC 10's automation types: the versions as `short`
(VT_I2), the enums as `int` (VT_I4), the date as `DateTime` (VT_DATE), strings, and the request as the COM object.

## 4. The calls, compared with the QBFC 10 path

`QuickBooksLateBound.cs` is `QuickBooksInProcess.cs` with `dynamic` for each QBFC type and the enum values from the type library; the
tests run every connecting scenario of `QuickBooksModuleTests` on today's code, the helper's module, the QBFC 10 in-process path and the
late-bound path, and require the same calls with the same values in the same order, the same session count and the same result or message.
The deposit with a class, pinned:

```
session.CreateMsgSetRequest("US",9,0)                (String, Int16, Int16)
request.Attributes.OnError=roeContinue               (Int32)
session.OpenConnection("","Open Dental")             (String, String)
session.BeginSession("<company file>",omDontCare)    (String, Int32)
request.AppendDepositAddRq()
...TxnDate.SetValue(date)                            (DateTime)
...DepositToAccountRef.FullName.SetValue("Checking")
...Memo.SetValue(memo)
...DepositLineAddList.Append()
...DepositInfo.AccountRef.FullName.SetValue(income account)
...DepositInfo.Amount.SetAsString(amount "F")
...DepositInfo.ClassRef.FullName.SetValue(class)     (only with a class and class references on)
session.DoRequests(request)                          (the COM object)
session.EndSession()
session.CloseConnection()
responses.Count, responses.GetAt(0), responses[0].StatusCode, responses.Count
```

The connection test (1.0, an empty request), the account list and the class list (8.0, `AppendAccountQueryRq` / `AppendClassQueryRq` with
`ActiveStatus.SetValue(asActiveOnly)`, then the response walk: status 0 and warnings above 0, a detail, the expected response type, a
FullName) are the same. The quirks are kept too: a failure ends the session and closes the connection by the flags as they are, and the flags
are not reset there.

`OpenConnection("","Open Dental")` is kept: it is today's call (the package text names `OpenConnection2`, which neither QBFC 10 path calls;
call-for-call parity decides). Intuit's samples call `OpenConnection2(appId, appName, connType)`; if QBFC 16 refused `OpenConnection`, that
is a failed connection and the helper takes the call.

**One session manager per connection**, as `new QBSessionManager()` made one: the first by the chooser's walk, the next ones by the chosen
ProgID directly. Nothing is released by hand, as before.

## 5. The choice, case by case

One choice per program process, written to `Logger\NativeFirst` once (the S3a-14n format), from the chooser of the process's bitness:

| Program | Case | Path | Logged |
|---|---|---|---|
| 32-bit (today's x86 build) | any | `QuickBooksInProcess` (QBFC 10) exactly as on main: `QuickBooksLateBound.Is64BitProcess` is false, nothing else of this package runs | QBFC 10's line, as before |
| 64-bit | the newest listed ProgID registered for 64-bit (an InprocServer32 in the 64-bit view, or a LocalServer32 in either) activates | this process, late-bound | "... in the program's process (64-bit process); QBFC16.QBSessionManager.1 activated in this process (QBFC16.QBSessionManager.1 ({clsid}) has InprocServer32 ...)" |
| 64-bit | a ProgID registered nowhere, or only as a 32-bit InprocServer32 | skipped without activating; the next older one | in the line's "before it: ..." |
| 64-bit | the registry cannot be read | the activation decides | |
| 64-bit | the activation fails with REGDB_E_CLASSNOTREG, CO_E_SERVER_EXEC_FAILURE, E_NOINTERFACE (also an InvalidCastException) or TYPE_E_LIBNOTREGISTERED, also inside a TargetInvocationException (N64-A3's rule) | the next older ProgID | "...: activating it here failed with 0x..." |
| 64-bit | none activates | **the helper's QBFC 10 module**, for the rest of the process | "in the 32-bit helper program (64-bit process); none of ... activated in this process: <each reason>" |
| 64-bit | the activation fails otherwise (E_FAIL, access denied) | thrown by the chooser; a failed connection: the helper (section 6) | "connecting failed in this process with ..." |

A 64-bit program never tries QBFC 10 in its own process (a 32-bit in-process server); QBFC 10's chooser is not touched there, so the
process logs one QuickBooks choice. The 32-bit program's chooser (`QuickBooksDesktop`) and its log line are unchanged.

## 6. The fallback

- **None activates:** the helper's QBFC 10 module (S3a-13), as a 64-bit program used it before this package.
- **A failed connection on the 64-bit path:** any failure up to and including `BeginSession` (creating the session manager, reading its enum
  values, `CreateMsgSetRequest`, setting `OnError`, `OpenConnection`, `BeginSession`): today's clean-up runs (`EndSession` / `CloseConnection`
  by the flags), `ChooseHelperAfterConnectionFailure` moves the process to the helper (logged with the failure and the earlier choice), the Try
  method returns false and `QuickBooks.cs` makes **this call once more in the helper**; every later call goes to the helper. Nothing had
  reached QuickBooks' data (no request was sent), so nothing is done twice.
- **A failure after the connection** (`DoRequests`, the response walk, a deposit status above 0) is QuickBooks' answer: it shows as before
  (thrown; `TestConnection`'s "Error: ...") and is never repeated in the helper, so a deposit QuickBooks may have taken is not sent twice; the
  choice stays.
- **What that rule also catches:** a wrong company file, QuickBooks not running or the user refusing access fail at `OpenConnection` or
  `BeginSession` as well. The helper then makes the same call and shows QuickBooks' message as before, and the helper stays chosen until the
  program restarts (as S3a-14n's lead note says of CO_E_SERVER_EXEC_FAILURE for Schick). The log line names the failure, so this can be told
  apart from a QuickBooks release the 64-bit QBFC cannot serve. QuickBooks authorizes an integrated application per program: on the helper's
  path it may ask again for `OpenPmsDentalHelper32.exe` (S3a-13 section 12).

## 9. Notes for the lead

- **Only QBFC 16 is listed.** No public page gives the ProgIDs of QBFC 15, 17 or 18, and its one source is developers' threads, not Intuit.
  On a PC with only QBFC 17 or 18 (and no QBFC 16) the 64-bit program uses the helper until L1 adds their lines. Intuit's 17.0 installer
  carries QBFC 16 too, so a workstation set up with it has QBFC 16.
- **`OpenConnection`, not `OpenConnection2`** (section 4): today's call kept for parity.
- **The connection fallback is broad** (section 6): a user-side failure at connect time moves the process to the helper for its lifetime.
  Narrowing it to the HRESULTs of "QuickBooks too old" needs those codes from a test PC.
- **Release notes:** none for x86 users: the 32-bit program behaves as on main, so `docs/release-notes/next.md` is unchanged.
- **For 3b:** the x64 program gets the 64-bit path with no code change; launch checks L1, L3 and L4. Who installs the 64-bit QBFC runtime
  (our setup or the office) is still the owner's question (survey section 5).

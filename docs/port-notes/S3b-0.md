  the SDK writes only those two and CA1416 is 0; `AssemblyInfo.cs` and `SharedAssemblyInfo.cs` stay the only source of the other attributes.
- CodeBase and ODCrypt otherwise compile unchanged on net10.0-windows x64. The other warnings of the cold build (one line each): SYSLIB0021
  (`SHA256CryptoServiceProvider` in `CodeBase/Crypto/HmacSha256.cs`, `AesCryptoServiceProvider` in `SecretBox.cs` and `MiscUtils.cs`),
  SYSLIB0023 (`RNGCryptoServiceProvider`, `ODCrypt/CryptUtil.cs`), SYSLIB0057 (`new X509Certificate2(byte[],...)`,

## Item 6: DentalXChange answers under HttpClient

Proven with a caveat.
- **The recorded envelopes:** `tests/VDXC2Tests/SoapEnvelopeTests.cs`, compiled unchanged into the spike's tests against S3a-6's clients built
  for net10.0, passes on .NET 10: all 32 of its tests (every DWS, DEA, NewCrop, ITS and DCI operation against its recorded request,
  headers and parsed result, the faults and errors). One needed the code-page provider: without `Encoding.RegisterProvider(
  CodePagesEncodingProvider.Instance)`, `NotXml_IsAnError` fails with `NotSupportedException` ("No data is available for encoding 1252"),
  because `SoapCaller` reads a body without a charset in the ANSI page (`ODEncodings.GetAnsiEncoding`). The spike's test assembly registers
  the provider in an `[AssemblyInitialize]` (`spike/SpikeTests/AssemblySetup.cs`), as the S3b-5 row plans; the program gets it from
  `ODInitialize.Initialize()` (S3b-2). Every `Main` that does not call `ODInitialize` and sends or reads such text needs it too.
- **The HTTP stack:** the fixtures hold no HTTP headers of the live service (the recordings are of requests, request headers and parsed
  results). So `HttpParsingTests` sends the DCI answer (Apache Axis, rpc/encoded with multiRef) to the real `DciSoapClient` through
  `SoapCaller`'s own `HttpClient` (SocketsHttpHandler, no test handler) from a local server on 127.0.0.1 that writes raw HTTP responses:
  read: a clean HTTP/1.1 answer with Content-Length, chunked (as Axis on Tomcat sends), HTTP/1.0 without length closed by the server, a status
  line without a reason phrase, a 500 with a SOAP body, bare LF line ends, a space before a header's colon, a control character in a header
  value, a folded header line, two equal Content-Length headers; refused (`WebException` from `HttpRequestException`): a header name with a
  space, and HTML before the status line ("Received an invalid status line"). A connection that the server closes after a keep-alive answer
  without saying so (the reused-connection case behind the old "protocol violation, Section=ResponseStatusLine" comment in `app.config`) is
  retried on a new connection: both calls read (2 connections). `HttpParsingTests.Item6_DciAnswer_ThroughSocketsHttpHandler` asserts each of
  the 12 outcomes (read, or refused with `WebException`) and the two reads of the stale connection, so a change in the handler's tolerance
  fails the test.
- **Launch check L6:** one DentalXChange test call (DWS `lookupEligibility` or DCI) from the .NET 10 build with the office's test credentials
  (the owner's), as the DentalXChange checks of section 6 do; a refused header shows as the `WebException` text above.

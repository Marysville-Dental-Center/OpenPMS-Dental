## 2. vstest and the MSTest 4 adapter

- **The adapter next to each test assembly.** vstest.console loads the test adapters it finds in the test assembly's folder (files named
  `*.TestAdapter.dll`); the build copies `MSTest.TestAdapter.dll` there with `MSTestAdapter.PlatformServices.dll` and the platform
  assemblies (S4-1, section 7). The runners pass no `/TestAdapterPath`. Before an assembly is run, the runner checks that
  `MSTest.TestAdapter.dll` is next to it; an assembly without it is reported as `exit=NOADAPTER` and not run (vstest would find no test in
  it and end with exit code 0). TestTelemetryTests' `EveryBuiltTestProject_HasTheMSTestAdapterNextToIt` checks that every built test
  project of the solution filter has the five files next to it, each the same version as the ones next to ProjectFileTests.
- **`/Platform:x86`** is kept: the test host is `testhost.x86.exe` (`ThisRun_IsAVSTestRun_WithVSTestTelemetryOff`). S3b-1 changes it to
  `/Platform:x64` with the switch.
- **vstest.console 18.11 runs the MSTest 4 adapter**: every log of this package starts with `VSTest version 18.11.0 (x64)` and lists the
  tests of the MSTest 4 assemblies with their outcomes; `TheMSTestAdapter_UsesNoTelemetryAssembly` checks that the adapter next to the test
  is the MSTest 4 adapter (it references Microsoft.Testing.Platform). No run settings are needed (S4-1, section 8).

## 3. The counts: both summary formats

vstest prints its summary in one of two formats, and the runner reads both (`Get-VsTestCounts`):

- the block of vstest.console (the one every run here prints), with a line only for a count that is not zero:

  ```
  Total tests: 139
       Passed: 138
      Skipped: 1
   Total time: 27.2629 Seconds
  ```

- the one-line summary of `dotnet test` and of newer vstest, one per test assembly, which are added up:

  ```
  Passed!  - Failed:     0, Passed:   138, Skipped:     1, Total:   139, Duration: 27 s - ProjectFileTests.dll (net48)
  ```

Before S4-2 the runner took the first `Total tests:`, `Passed:` and `Failed:` anywhere in the output, so a test's own output above the
summary could stand in for it (the adoption rehearsal prints `Total: 6.6 s`, which the old `Total:` fallback would have read as 6), and an
assembly whose tests are all inconclusive had `passed=?`. Now:

- the last block counts, and only its own lines; a count the block leaves out is 0 (WindowChecksTests: `passed=0 skipped=29`);
- without a block, the one-line summaries count;
- without either, the counts are `?`; a run that ends with exit code 0 and no summary is `exit=NOSUMMARY`, one whose summary counts no
  test is `exit=NOTESTS`; both make the run not ok (`DONE ok=False`). vstest's own non-zero exit code is kept as it was.

Each result line now has `skipped=`: `<assembly> exit= total= passed= failed= skipped= seconds=`. `NOTBUILT`, `NOADAPTER` and `TIMEOUT`
lines have it too. No workflow script reads the result lines (section 8); `Show-Summary` and `-WaitOnly` read them as before.

Checked on the record: the new parser was run on the logs of the 61 most recent results files in the test results folder, the stage 2
gate's Full run under MSTest v1 among them (411 assembly logs): for every one, total, passed and failed are those the old runner wrote, and
skipped is total minus passed minus failed. TestRunnerScriptTests checks the parser on sample output (section 6).

## 4. `-CompareWith`: the discovered counts against an earlier run

`-CompareWith <results file>` adds, after the run and before the `DONE` line, one `COMPARE` line per assembly of this run:
`COMPARE <assembly> same total= passed= failed= skipped=`, `COMPARE <assembly> differs total 129->208, passed 129->208` or
`COMPARE <assembly> new ...`. A Full or Core run then adds `COMPARE <assembly> missing total= passed= failed= skipped=` (the earlier
file's counts) for each assembly of the earlier file that this run has no result line for: a test project dropped from
`OpenDental.Local.slnf` (a merge that loses its line) is never discovered, so it gets no `NOTBUILT` line either, and without this its
tests would vanish from the comparison unnoticed. A Targeted run leaves most assemblies out on purpose and lists no `missing` line (nor
should a Core run be compared with a Full record: its slow assemblies would be `missing`). The last line is
`COMPARE same= differs= new= missing=`. The earlier file may be one of the old runner (no `skipped=`: skipped is
then total minus passed minus failed, and its `passed=?` is 0). It changes no result and no exit code. For the stage 4 gate the earlier
file is the stage 2 gate's Full run (`stage2-full.txt`, MSTest v1), the record S4-1's table compares with (its v1 column is that file,
assembly by assembly: checked, all 119 the same).

## 5. No telemetry from a test run

S4-1 (section 6) left the runners' environment to S4-2. Now:

- **Both runner copies** (`Set-TestRunEnvironment`, called once before the first vstest is started, so vstest and every test host inherit
  it): `TESTINGPLATFORM_TELEMETRY_OPTOUT=1` (the Microsoft Testing Platform parts of MSTest 4), `DOTNET_CLI_TELEMETRY_OPTOUT=1` (the .NET
  tools; MSTest's platform telemetry reads it too), `VSTEST_TELEMETRY_OPTEDIN` removed (vstest.console sends telemetry only when it is 1; it
  is not set to 0, it is taken out, so an opt-in that the caller's environment had does not reach vstest), and `OPMS_TEST_RUNNER=run-tests.ps1`,
  which tells a test that a runner started it. `-RequireBuildOutput` sets `OPMS_REQUIRE_BUILD_OUTPUT=1` in the same place.
- **The lane's `-Test`**: the lane sets its environment with the repository's `tools/Initialize-BuildEnvironment.ps1`, which had
  `DOTNET_CLI_TELEMETRY_OPTOUT=1` and now also sets `TESTINGPLATFORM_TELEMETRY_OPTOUT=1` and removes `VSTEST_TELEMETRY_OPTEDIN`. So the
  lane needs no change for a root with this helper (every branch since S1-0).
- **TestTelemetryTests** (ProjectFileTests): `ThisRun_ByARunner_HasTheTelemetryOptOuts` requires both opt-outs to be 1 in the test host's
  environment when a runner started it (`OPMS_TEST_RUNNER` set, or `OPMS_REQUIRE_BUILD_OUTPUT=1`, which the lane's test runs have); a run from
  an editor's test window is inconclusive. `ThisRun_IsAVSTestRun_WithVSTestTelemetryOff` still requires `VSTEST_TELEMETRY_OPTEDIN` not 1 in
  every run. TestRunnerScriptTests checks the two scripts themselves.
- `TheMSTestAdapter_UsesNoTelemetryAssembly` now covers every adapter and platform assembly the build copies next to a test assembly:
  `MSTest.TestAdapter.dll`, `MSTestAdapter.PlatformServices.dll`, `Microsoft.Testing.Platform.dll`, `Microsoft.Testing.Extensions.MSBuild.dll`
  and `Microsoft.Testing.Extensions.TrxReport.Abstractions.dll`: each is there and references no assembly whose name has "Telemetry" in it
  and no Application Insights assembly (all five pass).

Once the lead's runner is swapped in (section 9), a ProjectFileTests run by the old lead runner with `-RequireBuildOutput` would fail
`ThisRun_ByARunner_HasTheTelemetryOptOuts` (the old runner sets no `TESTINGPLATFORM_TELEMETRY_OPTOUT`); without `-RequireBuildOutput` the
test is inconclusive under the old runner.

## 8. The workflow scripts

Grep of the lead's tools folder (`.git/od-tools`: the `*.js` workflow scripts, the `*.py` helpers and `lead/*.ps1`) for `vstest`,
`run-tests` and the lane's `-Test`/`-TestOnly`, and for code that reads the result lines (`exit=`, `total=`, `passed=`, `failed=`,
`DONE ok`):

- **No script calls vstest itself.** `agent_timing.py` and `run_stats.py` only classify a logged command line as a test step when it names
  vstest or the runner; `plan64.js` mentions vstest in a task text (the x86 test platform of the bitness survey).
- **Every test step calls the lead's runner** with `-Root`, `-Mode`, `-Include`, `-Out` and, in the gate scripts (`lead/stage2-gate.ps1`,
  `lead/wrapup-gate.ps1`), `-RequireBuildOutput`; the task texts of the `*.js` scripts name the same command. The new runner keeps all of
  these parameters, so none of them needs a change.
- **No script reads the result lines**: the merge and gate scripts print the runner's last lines (`Select-Object -Last 6` to `-Last 40`).
  With `-CompareWith` the `COMPARE` lines come just before `DONE`, so a gate script that shows only the last 6 lines shows the comparison's
  end and `DONE`; the full lines are in the results file.

So no workflow script was changed. The stage 4 gate's Full run should add `-CompareWith` with the stage 2 gate's results file (section 9).

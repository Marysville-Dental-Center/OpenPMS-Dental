## 7. Plug-ins (decision 16) and the section 7 test

`PluginLoader` (the program) and `Plugins.LoadAllPlugins` (the Middle Tier) load through `Plugins.LoadPlugin`, which asks N64-A's
`PluginImageCheck.GetRefusalReason` before `Assembly.LoadFile`; on .NET a plug-in whose `TargetFrameworkAttribute` (or, without one, its core
library mscorlib) names the .NET Framework is refused, logged and shown by `PluginLoader` ("Error loading Plugin:" with "The plug-in X (path) is
not loaded: it is built for .NET Framework 4.8, and this version of the program runs on .NET 10.0, which does not load .NET Framework
plug-ins. Ask its author for a build for .NET 10.0 (net10.0-windows, any CPU or x64)."). That check existed; this package extends it rather than
duplicating it:
- **System.Reflection.Metadata.** `CodeBase.PortableExecutableFile` reads the metadata version, the core library and the
  `TargetFrameworkAttribute` with `PEReader`/`MetadataReader` on .NET (`ReadMetadataWithMetadataReader`, from the same bytes, nothing loaded;
  the attribute's constructor as a MemberRef of a TypeRef or a MethodDef of a TypeDef); its own tables reader stays for a .NET Framework build.
  N64ATests' `OutputFolder_ReaderAgreesWithCecil` checks it against Mono.Cecil 0.11.6 on every DLL and EXE of its .NET 10 output folder.
- **A runtime difference found by the x64 run:** CoreCLR maps an image with 32BITREQUIRED **and** 32BITPREFERRED ("any CPU, 32-bit preferred")
  into an x86 process only (`Assembly.LoadFile` in a 64-bit .NET 10 process throws `FileLoadException`, "The assembly architecture is not
  compatible with the current process architecture"), where the .NET Framework also maps it into a 64-bit process (N64-A). `CanLoadInProcess`
  takes the process's runtime (`CanLoadInProcess(machine,isNetFrameworkProcess)`; the one-argument form uses this process's), and
  `GetRefusalReason` refuses such a plug-in in a 64-bit .NET process: "... it is a .NET assembly for any CPU, 32-bit preferred (which .NET loads
  into a 32-bit process only), and this program is a 64-bit process. Ask its author for a build for any CPU (AnyCPU) or x64."

**The test of section 7** is `tests/N64ATests/PluginDecision16Tests.cs`. N64ATests references CodeBase, DataConnectionBase, the business library,
WpfControlsOD and SparksToothChart, all .NET 10 now, so it names `$(ODTargetFramework)` ahead of S3b-5 (x64, win-x64, framework-dependent, NLS,
Mono.Cecil 0.11.6, `UseWindowsForms`, `BuildOutput.cs` linked):
- `Process_IsDotNet10_X64`.
- `NetFrameworkPlugin_GetsTheClearMessage_AndIsNotLoaded`: a synthetic any-CPU plug-in with `.NETFramework,Version=v4.8`: the reader gives the
  attribute, `LoadPlugin` returns no plug-in, the error is the message above word for word, it is logged, and no `AssemblyLoadContext` of the
  process holds an assembly from that file.
- `RealNetFrameworkAssembly_IsRefused_WithoutLoadingIt`: `System.Xml.Linq.dll` of the 64-bit .NET Framework 4 folder (IL only, no attribute,
  mscorlib): refused as ".NET Framework 4.0", not loaded.
- `RebuiltPluginExample_Loads`: the lane's `PluginExample\bin\<configuration>\PluginExample.dll` (`.NETCoreApp,Version=v10.0`, PE32+ 0x8664)
  passes the check and loads through `LoadPlugin` as the program loads it: `PluginExample.Plugin`, a `PluginBase`, version 7.1.0.0, its `Host`
  setter running its own conversion (`ConvertPluginDatabase.Begin`) against a scratch database `s3b4_plugin_<time>_<pid>` with a synthetic
  `preference` table: afterwards its version row says 7.1.0.0 and its table `jss_dev_myveryuniquetable` exists; the database is dropped.
  Inconclusive without a local server; with `-RequireBuildOutput` a missing PluginExample build fails.

The existing N64ATests moved with it: the synthetic plug-in writer (`TestSupport.WritePlugin`) builds its references to `void`, `string` and
`TargetFrameworkAttribute` by name in the module's mscorlib, because importing them in a .NET process names System.Private.CoreLib (the
images are now the same whichever runtime writes them); `EachBitness_...` and `LoadableFileWithoutPluginType_...` write plug-ins for the run's
own framework and accept .NET's `FileLoadException` for a wrong bitness; `ProcessFramework_IsThisRunsFramework` and `BitnessRule_BothProcesses`
pin both runtimes' rules; `Synthetic_X86Preferred_...` pins the 32-bit-preferred difference.

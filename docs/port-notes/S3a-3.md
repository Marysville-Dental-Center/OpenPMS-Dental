# Port note: S3a-3 (encodings and numbers)

Package S3a-3 of stage 3a of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-3 row of wave 1): branch
`net10/s3a3-1` from `main` (`f19da99ce`). Every change is a no-op on .NET Framework 4.8 and makes the code give the same bytes and the
same text on .NET 10. No schema change, no project file change, no new package; nothing was downloaded; no program was started. The
code-page provider is not registered here: on .NET Framework every code page is built in, and the registration is one line in
`ODInitialize` and each `Main` in stage 3b (plan, section 8, item 8).

Commits: `907789379` (the ANSI code page), `fd0143107` (the numbers), `2c9e62a2d` (the tests), `0aa6b939a` (the float fix the
before/after test found), and this note with the plan's status line.

## 1. Two helpers in CodeBase

- **`ODEncodings.GetAnsiEncoding()`** is `Encoding.GetEncoding(CultureInfo.CurrentCulture.TextInfo.ANSICodePage)`, the formula of the
  plan, in one place. `Encoding.Default` is the ANSI page of the Windows system locale on .NET Framework and UTF-8 on .NET
  (https://learn.microsoft.com/en-us/dotnet/api/system.text.encoding.default).
- **`ODNumberText`**, for numbers that a machine reads back:
  - `ToStringNoNegativeZero(value,format,provider)`: `value.ToString(format,provider)`, except that a negative value (or -0.0) whose text
    has no digit but zeros is written as zero without a sign. .NET Framework does this for every standard and custom format; .NET Core
    3.0 and later write `-0.00` and `-0`
    (https://learn.microsoft.com/en-us/dotnet/core/compatibility/3.0#floating-point-formatting-and-parsing-behavior-changed). The rule
    is: when `|value|` formats as `0.0` formats, return the text of `0.0`.
  - `ToStringG15(double,provider)` and `ToStringG7(float,provider)`: the digits `ToString()` gives on .NET Framework (15 and 7
    significant digits), without negative zero. On .NET `ToString()` gives the shortest text that round-trips (`0.1+0.2` is
    `0.30000000000000004` there, `0.3` here).
  - `GetParsedAsNetFramework(value,text,provider)`: a parsed value as .NET Framework returned it. .NET Framework threw
    `OverflowException` for a number too large for the type and returned infinity only for the exact infinity symbol of the format
    (after trimming); .NET returns infinity for both. So: an infinity the text did not spell as the symbol throws `OverflowException`;
    a negative zero is 0 (.NET Framework never parsed a double to -0.0: `"-0"` and `"-1e-400"` gave +0), except that a float keeps the
    -0f .NET Framework gave for a negative number too small for a float but not for a double (`"-1e-320"`: .NET Framework parsed a
    double and cast it).

Decimals (`claimFeeBilled`, `SOut.Decimal`) need only the explicit culture: .NET writes a decimal that rounds to zero without a sign, as
.NET Framework does, and decimal formatting has no shortest-round-trip change.

**Culture.** The X12 and RAMQ numbers now use `InvariantCulture`, as the plan says for claim files. That is byte-identical for every
culture with a period as its decimal separator (en-US, en-CA, en-GB and the others the before/after tests run). In a comma culture
(fr-CA, de-DE) the old text had a comma, which neither format allows (`125,50` in an X12 amount; `0125,5` and `125,50` in the RAMQ
digit fields, which RAMQ reads as digits), so there the change is a fix, not a no-op; the pins record it. **The signature keys keep the
current culture**, deliberately: every stored treatment-plan and pay-plan signature was made with the current culture's text, and an
invariant key would stop matching every signature stored in a comma culture. Under NLS (decision 4) the culture data are the same on
.NET 10, so only the digits and the negative zero had to be fixed there. The tests prove the keys equal the old ones in en-US, en-CA,
fr-CA and de-DE.

**The ANSI page.** `Encoding.Default` on .NET Framework is the ANSI page of the system locale; the new code takes the current culture's
(the program sets the culture from its language and region setting). The two agree wherever the culture and the system locale share
their ANSI page: 1252 for every English and Western European culture. A culture without an ANSI page reports 0, and page 0 is the
system's default page on .NET Framework, as before. On a PC whose program culture and system locale had different pages (say a Russian
program culture on an English Windows), the new code follows the culture; no such office is known.

**Kept as it was, for the owner:** RAMQ's TOT_DEM writes the claim total with `ToString()` and drops the period, so 125.50 is `001255`,
the same digits as 1255.00, while MNT writes `012550`. This looks like an old bug; S3a-3 keeps the text (the row asks for "G15 where
text must match today"), and `Pins_RamqDigits` records it.

## 3. Proofs

All on .NET Framework 4.8 (the before/after tests are the .NET Framework record and say Inconclusive on .NET, where the pins hold).

- **The three fixed tests** build the expected bytes with code page 1252 and set the culture, with no guard on the computer's code page:
  `ProcCodeImportTests.DecodeFileBytes_Utf8AndAnsi` (en-US, set by its TestInitialize), `OtherCodesTests.DecodeFileBytes_Utf8Utf16AndAnsi`
  (en-CA; the `if(Encoding.Default.CodePage==1252)` guard is gone), `ODZipTests.CreateArchiveFile_WritesAReadableZipFile` (en-CA).
- **BINBTests `NumberTextTests`.** Pins (both runtimes): `(-0.0)` and `Math.Round(-0.004,2)` with `"F2"` give `0.00`, `-0.005` gives
  `-0.01`, `0.1+0.2` gives `0.3`, `16777217f` gives `1.677722E+07`, `SIn.Double("1e400")` is 0, `SIn.Float("1e40")` throws, `"-0"` is
  +0, the culture's infinity symbol is still infinity, `GetParsedAsNetFramework` turns the infinity .NET returns for an overflow into
  `OverflowException`; the culture's ANSI page for eight cultures (1252, 1250, 1251, 1253, 932) and the 1252 bytes of a text with
  e-acute, the euro sign, an en dash and u-umlaut. Before/after: `ToStringNoNegativeZero` equals `ToString` for 3,044 fixture doubles (amounts, values around rounding to
  zero, -0.0, the type's edges, NaN, infinities and 3,000 seeded random values of every size) in eleven formats (`F2 f2 f F N2 C 0.00
  0.00# 0.00## G15 G`) and six cultures (en-US, en-CA, fr-CA, de-DE, en-GB, invariant), more than 200,000 comparisons; `ToStringG15`
  equals `ToString()` and `ToStringG7` equals `float.ToString()` (2,016 fixture floats); `SOut.Double` (all three forms and 2, 3 and 4
  decimal places) and `SOut.Float` equal the replaced expressions in five cultures; `SIn.Double` (both forms) and `SIn.Float` equal a
  copy of the replaced code, bit for bit (so -0.0 counts) and exception for exception, for about 850 texts (overflows, underflows, infinity
  spellings, NaN, separators of both kinds, the culture's symbols, the G15 and R texts of 400 fixture values) in five cultures;
  `ODEncodings` equals `Encoding.Default` (all 256 bytes both ways) in the computer's culture and in every specific culture with the
  system's ANSI page.
- **BCLAIMTests `ClaimNumberTextTests`.** Before/after for 2,022 fixture amounts in en-US, en-CA and en-GB: every replaced X12 expression
  (both versions) and both RAMQ fields equal the new code; the CTP04 float for 1,000 quantities. Pins: periods and no negative zero, and
  the fr-CA texts that change.
- **BTPTests and PayPlanTests `SignatureKeyTests`.** Before/after: the treatment-plan key data for 302 fixture plans and the pay-plan key
  data for 2,010 fixture plans equal the replaced code in en-US, en-CA, fr-CA and de-DE. Pins: the key with -0.004, -0.0 and 0.1+0.2 as
  .NET Framework writes it.
- **NoHqTests `AnsiEncodingScanTests`.** No `Encoding.Default` outside comments in the C# projects of `OpenDental.Local.slnf` that ship
  (not `tests\`, `tools\`, `third-party\`, `UnitTests`, `UnitTestsCore` or NoHqTests).
- **The float fix.** The first run of the SIn before/after test failed for `"-4.94065645841247E-324"`: .NET Framework gives -0f there
  (it parses a double and casts it), and the first version of `GetParsedAsNetFramework` made every float zero positive. Fixed in
  `0aa6b939a`, with a pin.

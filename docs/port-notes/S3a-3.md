## 1. Two helpers in CodeBase

- **`ODEncodings.GetAnsiEncoding()`** is `Encoding.GetEncoding(GetACP())`, with `GetACP` from kernel32: the ANSI page of the Windows
  system locale. `Encoding.Default` on .NET Framework asks `GetACP` too, so this is an exact no-op on net48 for every thread culture and
  every user format; on .NET `Encoding.Default` is UTF-8
  (https://learn.microsoft.com/en-us/dotnet/api/system.text.encoding.default), and the pages other than UTF-8, UTF-16, UTF-32, ASCII and
  Latin-1 need the code-page provider that 3b registers. (The first version took `CultureInfo.CurrentCulture.TextInfo.ANSICodePage`,
  the plan's first formula; the review replaced it, see "The ANSI page" below.)
- **`ODNumberText`**, for numbers that a machine reads back:
  - `ToStringNoNegativeZero(value,format,provider)`: `value.ToString(format,provider)`, except that a negative value (or -0.0) whose text
    has no digit but zeros is written as zero without a sign. .NET Framework does this for every standard and custom format; .NET Core
    3.0 and later write `-0.00` and `-0`
    (https://learn.microsoft.com/en-us/dotnet/core/compatibility/3.0#floating-point-formatting-and-parsing-behavior-changed). The rule
    is: when `|value|` formats as `0.0` formats, return the text of `0.0`.
  - `ToStringG15(double,provider)` and `ToStringG7(float,provider)`: the digits `ToString()` gives on .NET Framework (15 and 7
    significant digits), without negative zero. On .NET `ToString()` gives the shortest text that round-trips (`0.1+0.2` is
    `0.30000000000000004` there, `0.3` here).
  - `GetParsedAsNetFramework(value,text,provider)`: a parsed value as .NET Framework returned it. .NET Framework threw
    `OverflowException` for a number too large for the type and returned infinity only for the exact infinity symbol of the format
    (after trimming); .NET returns infinity for both. So: an infinity the text did not spell as the symbol throws `OverflowException`;
    a negative zero is 0 (.NET Framework never parsed a double to -0.0: `"-0"` and `"-1e-400"` gave +0), except that a float keeps the
    -0f .NET Framework gave for a negative number too small for a float but not for a double (`"-1e-320"`: .NET Framework parsed a
    double and cast it).

Decimals (`claimFeeBilled`, `SOut.Decimal`) need only the explicit culture: .NET writes a decimal that rounds to zero without a sign, as
.NET Framework does, and decimal formatting has no shortest-round-trip change.

**Culture.** The X12 and RAMQ numbers now use `InvariantCulture`, as the plan says for claim files. That is byte-identical for every
culture with a period as its decimal separator (en-US, en-CA, en-GB and the others the before/after tests run). In a comma culture
(fr-CA, de-DE) the old text had a comma, which neither format allows (`125,50` in an X12 amount; `0125,5` and `125,50` in the RAMQ
digit fields, which RAMQ reads as digits), so there the change is a fix, not a no-op; the pins record it. **The signature keys keep the
current culture**, deliberately: every stored treatment-plan and pay-plan signature was made with the current culture's text, and an
invariant key would stop matching every signature stored in a comma culture. Under NLS (decision 4) the culture data are the same on
.NET 10, so only the digits and the negative zero had to be fixed there. The tests prove the keys equal the old ones in en-US, en-CA,
fr-CA and de-DE.

**The ANSI page.** `Encoding.Default` on .NET Framework is the ANSI page of the system locale ("Language for non-Unicode programs"),
which Windows reports through `GetACP`; the new code asks `GetACP` as well, so it gives the same encoding whatever the thread culture.
The program's culture is not a separate setting: `DateTimeOD.NormalizeApplicationShortDateFormat` (`CodeBase/Utilities/DateTimeOD.cs`,
lines 47-55, with the copy made at line 24) sets `Application.CurrentCulture`, `DefaultThreadCurrentCulture` and
`DefaultThreadCurrentUICulture` to a copy of the Windows culture (the user's regional format) with a four-digit-year short date. That
culture can have another ANSI page than the system locale (a Polish or Russian regional format on an English Windows), and on .NET a
culture without an ANSI page reports 0, which `GetEncoding` turns into UTF-8; the first version, which took the culture's page, would
have changed the bytes in both cases. With `GetACP` there is no such case.

**Kept as it was, for the owner:** RAMQ's TOT_DEM writes the claim total with `ToString()` and drops the period, so 125.50 is `001255`,
the same digits as 1255.00, while MNT writes `012550`. This looks like an old bug; S3a-3 keeps the text (the row asks for "G15 where
text must match today"), and `Pins_RamqDigits` records it. No claim has gone out with it: `Ramq.Launch` is not implemented (it sets
"Not implemented." and sends nothing). The release note (`docs/release-notes/next.md`, "Claim files: a period in every amount") tells
users that X12 837 and RAMQ amounts now have a period in every regional setting.

# Port note: UI-11 (the remaining background colours)

Why: docs/specs/ui-refresh-plan.md section 1 order item 8 and section 7's UI-11 rows. After UI-3 to UI-13, UI-PLAIN and UI-12F every window
(FormODBase and plain, every slice) was on the grid and in the look, but its designers and code still named literal colours that did not
come from a token: white module and setup pages, tab pages and group boxes in the old 252,253,254, Windows' grey on panels and tab pages,
and the code's resets to those colours. WPF's `ColorOD` still returned the old fixed palette. Restyle only: no size, place, text, name, event
or behaviour changes. Branch `ui/ui11-1` from `main` at dd1d262f8.

## 1. The scan and the rules

`tools/UiFit/colour_literals.py` reads every `.cs` file of the program's projects (OpenPmsDental, OpenPmsDentalBusiness, CodeBase,
SparksToothChart, WpfControlsOD, RdlDesign, ODR, ImagingDeviceManager and the plain exes of UI-PLAIN) and lists every literal `BackColor`
and `ForeColor` value: a named colour, a system colour, `Color.FromArgb` with numbers, `Color.FromName("...")`, `Color.FromKnownColor(...)`,
`Color.Empty`. In `InitializeComponent` a designer line names its control (`.` for the window) and the control's declared type; elsewhere
each `x.BackColor=...` in code names the expression before it (`(initializer)` in an object initializer), and every literal of its
right-hand side (up to the statement's `;`, or the initializer's next member) is a row of its own: both branches of
`butBF.BackColor=isChosen?Color.White:SystemColors.Control;` (fix round; before it, a literal in a `?:` and `Color.FromName` went unseen).
On `main` there were 1124 literals with the fix round's patterns (1095 with the first ones).

Each literal is decided by role (`decide` and `decide_code`):

| Role | Decision |
|---|---|
| A container that shows the window's background (the window or user control, Panel, PanelOD, SplitContainer and its panels, GroupBox, TabPage, TabControl, Label, CheckBox, RadioButton, UserControlReportSetup, EmailPreviewControl, ODDatePicker) in an old background: `SystemColors.Control`, `ControlLight`, `ControlLightLight`, `Window`, `Color.White`, `WhiteSmoke`, 252,253,254, 249,249,249, 250,250,250 | **mapped**: the designer line goes, so the control takes its parent's colour, which is `UiTheme.Surface` (FormODBase, FormFrame and UiPlainWindow set it) or the token of the container it sits in; in high contrast that is Windows' Window colour |
| The same containers' `ForeColor` in `ControlText` or `Black` | **mapped**: the line goes (the parent's text colour, the same picture) |
| A child of a container whose own colour stays | stays: on a coloured parent |
| A control that cannot show a transparent colour (UI.CheckBox, UI.GroupBox, a tab control: no `SupportsTransparentBackColor`) whose nearest coloured ancestor is `Color.Transparent` | stays (fix round): without its line WinForms draws Windows' grey there (UI.GroupBox white); remove the parent's Transparent line instead, as ControlAccount's tabMain and tabShow and FormClaimEdit's tabGeneral now do |
| Transparent, `Color.Empty` | stays: shows the colour behind it |
| Content (the screening tooth, signature boxes, the time bar, the perio chart, the tooth chart's text strip, drawn tables, print panels, sheets, pictures, charts, the camera and video views, the imaging dock) | stays, with the content's reason (section 1 of the plan: content keeps its colours) |
| An input's box in `Window` or `White` | stays: SurfaceRaised's value, `Window` is also its high-contrast partner; the input frame draws the box in it |
| An input in `Control`, `ControlLight`, `ControlLightLight` | stays: the read-only or locked state |
| A borderless caption box (a text box without a border used as a label) in an old background | stays in the designer; `UiLooks.SetCaptionBoxLook` gives it its parent's colour (section 2) |
| Text in red, dark red, firebrick, maroon, 192,0,0, blue, midnight blue, green | stays: a deliberate status colour |
| A stock button's `Control` face and `ControlText` text | stays: UiButtonLook reads Windows' button colours as the program's button |
| A coloured button or swatch | stays: UiButtonLook draws its colour (IsSwatch, IsOwnColours) |
| Grey block labels (LightGray), grid-title labels (ActiveCaption) and their caption text | stays: UiBlockLook and UiCaptionLook draw them |
| Thin dark panels (Black, ControlDark, ControlText, 64,64,64) | stays: UiSeparatorLook draws a divider as one Stroke line, UiBorderLook a frame |
| Data grid view cell styles | stays: UiLooks.SetDataGridViewLook reads Windows' defaults as the tokens |
| Code: a status colour and its reset to the default text colour; a read-only input's grey or editable box; the surface buttons' white while chosen; a tree item's or list item's state; the office's colour swatches | stays, with the reason |
| Whole files: RdlDesign (report content, section 7's UI-11 row), ODR, the business layer's grid and report drawing, SparksToothChart, the graph library (chart content; UiPlainWindow gives its classic grey the token), the reports, the allocator windows' own colours (UiLooks.IsOwnColours), FormODBase's and FormFrame's never-called designer methods, the tooltip, the combo picker's list, the splash screen, the fading popup | stays |
| Hand rows (`HAND`, `CODE_HAND`) | FormRpLaserLabels' label sheet preview (content), the swatches of FormApptEdit, FormApptTypeEdit, FormProcCodeEdit, FormProcApptColorEdit and the Chart's draw colour, and the other code sites named in the script |

`python tools/UiFit/colour_literals.py` writes the literals that stay into the UI-11 section of `tests/UiRefreshTests/Data/colour-literals.tsv`
(after UI-1's table: file, control, property, value, count, why; 857 rows, 897 literals after the fix round) and refuses while a literal has no rule or a
chrome literal is left; `--check` compares, `--inventory <file>` writes every literal with its type and decision (a work file), `--apply`
removes the mapped designer lines, `--windows <file>` writes the window types whose designer has one (the gallery's list).

**The test.** `NoHqTests.ChromeColourScanTests` reads the same lines with the same patterns (in C#, on its own) and fails on a literal the
section does not list (a new chrome literal: remove the designer line or use UiTheme in code; or list a colour that stays with its reason),
on a row the source no longer has as often, and on a row without a reason. Its `ChromeColours_NoOpaqueControlOnTransparentParent` (fix
round) fails on a designer that leaves a UI.CheckBox, UI.GroupBox or tab control without its own colour under a `Color.Transparent`
container: the scan cannot see a colour that is not written, and that control would draw Windows' grey. UI-1's `UiThemeScanTests` reads its table up to the section and
keeps the section when it writes the table again.

## 2. What changed

- **Designers** (94 files, 220 lines): the module pages (ControlAccount, ControlAppt, ControlChart, ControlManage, ControlTreat) and the 28
  preference pages lose their white, with their white group boxes, tab pages, split panels and check boxes; 44 tab pages and 16 group boxes in
  252,253,254 and 11 group boxes in 249,249,249 (FormFeeSchedTools, FormProvEdit, FormRecallList, FormRpUnearnedIncome, FormPath,
  FormLateCharges, FormArManager ...); tab pages in Windows' grey (FormPatientEdit, FormPayPlanDynamic, FormScheduleDayEdit) and white
  (FormClaimEdit, FormRpPatients, FormRpReferrals, FormASAP, FormErxSetup, FormEmailInbox); FormInsPlan's white plan panels;
  FormDatabaseMaintenance's tab control; the windows FormCentralUserEdit, FormPayPlanDynamic, FormWikiCompare (252,253,254) and the
  progress windows (ControlLight, which UiPlainWindow already replaced); UserControlDashboard; the email preview and report setup user
  controls; twelve default-text `ForeColor` lines. Each now takes its parent's token.
- **Code**: FormEhrSetup's Emergency Now panel, FormEmailInbox's search group and FormPreferences' search highlights reset to the parent's
  colour (`Color.Empty`) instead of Windows' grey or white; the Account module's service date check box (made in code) loses its white;
  the appointment book's header tip is `SurfaceRaised`.
- **Caption boxes**: `UiLooks.SetCaptionBoxLook` (attached by `UiLooks.AttachOne`, so FormODBase, LayoutManagerForms and UiPlainWindow
  all apply it): a `TextBoxBase` with `BorderStyle.None` in an old background (`UiPlainWindow.IsOldBackground`: Windows' grey or
  252,253,254; or the light Surface value a UI-12 hand row wrote) takes its parent's colour, on a transparent parent `Surface`. A framed box
  is an input and keeps its colour; so does a white or coloured caption box. FormBackup's and FormDatabaseMaintenance's notes, FormInsCatsSetup.
  Fix round: FormRpPatients' hint (a borderless box at the TextBox default Window, white on the page once its tab page lost its white) is
  read-only, so its default is Windows' grey and the caption look gives it the page's colour; EmailPreviewControl's three read-only
  caption boxes (user, sent or received, date) lose their `SystemColors.Window` line the same way. The look itself is unchanged: a
  borderless box at its default white can be an input inside a frame (FormPatientEdit's textZip, the report designer's editor), so the
  rule stays with the old backgrounds. Left as they were: FormInsPayFix's and FormLanguageAndRegion's white description boxes (editable,
  on the window, white on Surface since UI-3; not changed by this package).
- **Transparent tab pages** (fix round): ControlAccount's tabMain and tabShow and FormClaimEdit's tabGeneral lose their
  `Color.Transparent`: a UI.CheckBox cannot show a transparent colour, so the Show SuperFamily box and the Show tab's four boxes drew
  Windows' grey once their white went, and FormClaimEdit's group boxes drew white (UI.GroupBox's answer to a transparent parent). Each
  page now takes the tab control's colour, its parent's token, and its boxes with it.
- **FormExamSheets**: the sheet preview clears to the panel's own colour (its parent's token) instead of 252,253,254, the last code use of
  the old background (fix round; the designer line had gone, the paint code still drew the old colour).
- **ColorOD** (`WpfControlsOD/UI/ColorOD.cs`): its six colours are now properties that return the tokens by role (Background `Surface`,
  Control `SurfaceSubtle`, Gridline `Gridline`, Hover `RowHover`, Outline `StrokeStrong`, DisabledText `TextDisabled`), so they follow
  high contrast; `GetColorBackground()` returns the WPF `Surface`. Its users: the patient dashboard's insurance widgets (their background and the
  lines between their cells), the imaging module's collapse arrow panel, the integrity warning's fallback, the preference pages' "looks disabled"
  labels. The helpers (`Gray`, `Gray_Wpf`, `Mix`, `ToWpf`, `FromWpf`) stay; their numeric callers (the WPF button, check box and radio
  button disabled greys, the eForm fill's bevels, the sheet editor) are not palette colours: the WPF button templates belong to UI-OVF,
  the eForm and sheet colours are content.
- **High contrast**: every mapped control now reads its parent's token, which returns Windows' colours under a high-contrast theme, like
  the looks; the literals that stay are content, a state or a system colour (Window, Control, GrayText) that follows the theme itself.

## 3. Tests

- `NoHqTests.ChromeColourScanTests`: the scan against the section, and its rules on synthetic lines.
- `UiRefreshTests.ChromeColourTests`: `ColorOD` returns the tokens; a caption box takes its parent's colour (252,253,254, the Surface value,

(`main` at dd1d262f8, built x64) and after, drawn by `FitGallery` in the program's font (`OPMS_UI_FIT_GALLERY_FONT=program`) at 100%,

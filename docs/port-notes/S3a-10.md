## 1. (ii) The manifest keys

The format stays `Format=1`: a newer format number would make the bridge call the .NET 10 manifest unreadable, which is what this package
removes. The new lines are optional; a bridge release writes none of them. A build for another runtime writes the `Runtime` line
(section 2.2), and 3b's release adds the runtime part (S3b-7).

| Line | Value | Read as |
|---|---|---|
| `Runtime` | framework, version and runtime identifier, separated by single spaces: `Microsoft.NETCore.App 10.0.14 win-x64` | `ReleaseManifest.Runtime` (`ReleaseRuntime`). Framework and identifier: letters, digits, `.`, `-`, `_`; version: two to four numbers, written as `System.Version` writes them. Once. **No `Runtime` line** = the .NET Framework 4.8 build, x86 (`ReleaseRuntime.NetFramework48X86`, `.NETFramework 4.8 win-x86`): every release before the .NET 10 release. |
| `RuntimeVersion` | `10.0.14` | The runtime part's version; must equal the `Runtime` line's. |
| `RuntimeArchitectures` | `win-x64 win-x86` | The runtime identifiers of the runtime part's files (the x64 runtime beside the exes, the helper's x86 runtime in `Helper32\`), the program's first; the first must equal the `Runtime` line's; none twice. |
| `RuntimeArchiveSha256` | 64 hex | SHA-256 of the runtime part's own zipped archive (S3b-7 stores it in its own rows, `DocumentMiscType` 102 and 103). In both copies of the manifest: it is not this archive's hash. |
| `RuntimeKey` | 64 hex | `ReleaseRuntimePart.ComputeKey()`: SHA-256 (UTF-8) over `version|<version>\n` and, per file in path order (ordinal, ignoring case), `<path in lower case, backslashes>|<size>|<sha256 lower case>\n`. Two releases on the same runtime files have the same key, so the runtime part is published and pulled only when it changes (decision 20). Must match the files. |
| `RuntimeFile` | `sha256|size|relative path`, one per file | The runtime part's files, as `File` lines are: safe relative paths, none twice, none that a `File` line lists too. |

A runtime part line without the `Runtime` line, or a runtime part without all five kinds of line, is unreadable (`FormatException`), as is
every other malformed case in `RuntimeManifestTests.RuntimePart_Malformed_Throws` (19 cases).

**This install's runtime.** `ReleaseRuntime.GetRunning()`: `Environment.Version` below 5 is the .NET Framework (`.NETFramework 4.8`, the
target), otherwise `Microsoft.NETCore.App` at `Environment.Version` (the runtime's own version on .NET 5 and later); `win-x64` or `win-x86`
by `Environment.Is64BitProcess` (an x64 process under emulation on ARM64 counts as x64, which is what it runs). `GetRunningIdentity` sets it
as `ReleaseIdentity.Runtime`; an identity without one (read from the `ForkProgramVersion` marker) refuses nothing for its runtime.

**Same runtime** means the same framework and architecture (`IsSameFrameworkAndArchitecture`, ignoring case). The version is not compared:
a .NET 10 release on a newer 10.0.x patch is a normal self-update with a new runtime part (S3b-7).

## 2. The refusals and their messages

Both refusals keep the workstation on the build it runs: it neither publishes over the published release nor pulls it, shows why (not in a
silent run) and starts. That is what section 10 step 3 needs during the switch: a workstation not yet set up stays on the bridge release.

### 2.1 (i) A manifest that is not readable or names another product

Before: `GetPublishedManifest` returned null for a manifest that did not parse or named another product, and `Decide(null,...)` read that as
"nothing published", so the update server (named, or any workstation with a blank `WebServiceServerName`) offered to publish over it. A
pre-bridge update server would do that with the .NET 10 manifest (section 10 step 1). Now `Decide(manifest, errorPublished, ...)` returns
`ReleaseAction.RefuseUnreadable` for every role when the manifest is null with an error. Message (`ForkReleases.GetUnreadableMessage`):

> The published release manifest is not readable: *(the parser's reason, for example "Unknown release manifest format: 2")*
> This workstation neither updates from it nor publishes over it, and keeps running its own build. A newer version of the program may have
> published it: if a newer version was installed on the update server, run the new setup on this workstation too. Otherwise tell the person
> who looks after the program, and do not publish a release until they have looked at it.

For another product the first line is "The published release manifest is for another product (*name*)." Where it shows:

| Place | Before | Now |
|---|---|---|
| Startup, `PrefL.CheckProgramVersion` | offered to publish (update server), or nothing | the message; the program starts |
| Update Setup, Recopy (`CopyFromHereToUpdateFiles`) | published over it | the message; nothing published (returns false) |
| The version guard's pull (`CheckForkVersionGuard`, a database a newer release updated) | the guard's message only | the guard's message, a blank line, this message; exit with the guard's code, as before |
| Re-activation, `FormOpenDental.IsDbConnectionSafe` | `GetPublishedManifestOrMarker` built a manifest from the marker, so a restart was asked for whenever the marker named another build | `GetPublishedManifestOrMarker` returns null, `MayRunUnpublishedBuild(null)` is true: no restart that could not change anything |
| `DownloadAndVerify` | refused (unchanged) | refused (unchanged) |

### 2.2 (ii) A release for another runtime or architecture

`ForkReleases.GetRuntimeRefusal(manifest, identityRunning)`: the published manifest's runtime (`GetRuntimeOrDefault`) against the running
build's. In `Decide` it comes right after "same build id": the named update server does not offer to publish its old build over the .NET 10
release. `ReleaseAction.RefuseOtherRuntime`. One exception, the forward switch (`ForkReleases.IsForwardRuntimeSwitch`: the running build is
`Microsoft.NETCore.App` and the published release is `.NETFramework`, as a manifest without a `Runtime` line is), described after the tables.
Message, for the bridge release and the example manifest:

> The update server published 1.0 (build 444444444444, built 2027-02-01 12:00 UTC) for .NET 10.0.14 (win-x64), but this workstation runs on
> .NET Framework 4.8 (win-x86).
> This workstation cannot update itself to that release: run the new setup on it. Until then it keeps running 0.0 (build *...*), and
> nothing was changed on it.

| Place | Now |
|---|---|
| Startup, `CheckProgramVersion` | the message; the program starts |
| Recopy | the message; nothing published (except the forward switch below) |
| The version guard's pull | the guard's message and this message; exit with the guard's code |
| `PullRelease` → `DownloadAndVerify(folder, identityRunning)` | the same text as the one problem, before any segment is read; nothing is written |
| Re-activation | `MayRunUnpublishedBuild` is true for such a release: the workstation keeps running |

**The forward switch.** In section 10 step 3 of the plan the update server gets the .NET 10 setup first, and its first start publishes the
.NET 10 release over the bridge release. So when the running build is .NET and the published release is a .NET Framework one, `Decide`
applies its role rules as for one runtime and keeps only a Publish: the named update server (`ThisComputer`) publishes, and with a blank
`WebServiceServerName` a build known to be newer (`CompareBuilds<0`) publishes. Every pull and every other case is `RefuseOtherRuntime`; a
.NET 10 install never pulls a .NET Framework release. Nothing ever publishes a .NET Framework release over a .NET one, so the bridge side is
exactly as in the tables above. The update server's publish question gets one more line:

> The published release is for .NET Framework 4.8 (win-x86) and this build runs on .NET 10.0.14 (win-x64). Once this build is published, the
> workstations that still run the old release keep running it until the new setup runs on them.

A .NET 10 workstation that is not the update server (or that the role rules would have pull) gets instead:

> The update server published 0.0 (build *...*) for .NET Framework 4.8 (win-x86), but this workstation runs on .NET 10.0.14 (win-x64).
> This workstation does not go back to that release. It keeps running 1.0 (build *...*), and nothing was changed on it, until the release
> for its runtime is published: run the new setup on the update server and start the program there.

and the named update server whose .NET 10 build is older than the published .NET Framework release (never a downgrade) gets that message
and "This computer is the update server, but the published release is newer than this build, so this build does not replace it. Install a
newer release for .NET 10.0.14 (win-x64) on this computer."

Recopy makes the same exception: `GetRefusal(manifest, error, identity, updateServerRolePublishing)` takes this computer's role for a
publish and returns "" when `Decide` would publish; the version guard's pull passes no role and still refuses. `MayRunUnpublishedBuild` is
true for both outcomes, so neither restarts in a loop. `BuildRelease` writes the `Runtime` line for any build that is not .NET Framework
4.8 x86, so the release the .NET 10 update server publishes is refused by the bridge workstations ("run the new setup on it") instead of
being read as one of their own; a bridge release still writes none. The other direction stays a refusal for every role: a 3b install
(`Microsoft.NETCore.App ... win-x64`) refuses a .NET release for another architecture, and the bridge refuses the .NET 10 release. Tests:
`RuntimeManifestTests.Net10UpdateServer_PublishesOverTheBridgeRelease`, `Net10Workstation_NotTheUpdateServer_RefusesTheBridgeRelease`,
`ForwardSwitchOnly_NeverBackToTheNetFramework`, `BuildRelease_NamesTheRuntime_OfAnyBuildButTheBridge` and
`ReleaseForAnotherArchitecture_IsRefused`. S3b-7 still adds the runtime part (section 7) and should repeat the forward-publish case in its
targeted tests on the real .NET 10 build.

## 3. (iii) Pull copies every file UpdateFileCopier needs

Before: `OpenFileCopier` copied `UpdateFileCopier.exe` alone into the program's temp folder (`%TEMP%\openpms-dental`). The .NET 10 copier is
an apphost: `UpdateFileCopier.exe` with `UpdateFileCopier.dll`, `.runtimeconfig.json`, `.deps.json` and the runtime files beside it. Now
`ForkReleases.CopyFileCopier(source, %TEMP%\openpms-dental\ForkReleaseCopier)` empties that folder (so two copiers' files never mix) and
copies every present file of `ListFileCopierEndings`: `UpdateFileCopier.exe` (required; `FileNotFoundException` without it, shown as before
with "Unable to copy UpdateFileCopier.exe from ..."), `.exe.config`, `.dll`, `.runtimeconfig.json`, `.deps.json`. Today a release ships
the exe alone (Build-Release stages no `UpdateFileCopier.exe.config`, and the copier runs without it), so the folder holds the exe alone;
`FileCopierStartTests.EveryFileOfTheCopiersBuild_IsCopied` fails as soon as the copier's build writes a file that is not copied.
S3b-7 adds the runtime files (the copier's temp folder "with one x64 runtime").

The copier works in `%TEMP%\openpms-dental\updatefilecopier` (`local`, `source`) as before; `ForkReleaseCopier` is a sibling, which the
close-time clean-up of the temp folder may delete like any other folder there; it is made again at every pull.

## 4. (iv) The elevated copier starts through ShellExecute

`OpenFileCopier` starts the copier with `ForkReleases.GetFileCopierStartInfo(path, arguments)` (`UseShellExecute=true`) and sets
`process.StartInfo.UseShellExecute=true` again at the start, so the start states it where it happens (S3a-2's rule). `UpdateFileCopier/app.manifest`
asks for `requireAdministrator`; CreateProcess (`UseShellExecute=false`, the .NET default) refuses such a program with
`ERROR_ELEVATION_REQUIRED`, only ShellExecute asks UAC for consent. True is the .NET Framework default, so nothing changes today. A UAC
prompt that is cancelled ends the start with a `Win32Exception` (`ERROR_CANCELLED`), which the existing catch shows as "Unable to start the
update file copier" and exit code 305, as before. `process.WaitForExit()` works with ShellExecute (the process handle is kept). No other
process start is in `PrefL.cs` (`FileCopierStartTests` checks: one `new Process()`, its `UseShellExecute` set, no `Process.Start(`).

- `ForkVersionGuard.cs` is not this package's, so no new exit code: both refusals keep the program running; the guard's pull keeps the
  guard's exit code.
- 3b writes the runtime part (S3b-7, `ForkReleases.Publish`). This package writes the `Runtime` line for a build that is not .NET
  Framework 4.8 x86 (`BuildRelease`, section 2.2) and no runtime part.
- **Binding contract for S3b-7 and later (lead, at the merge, from the reviews).** The parse is strict: Format 1 is frozen in practice.
  An unknown key, or a runtime part without all five lines (`RuntimeVersion`, `RuntimeArchitectures`, `RuntimeArchiveSha256`, `RuntimeKey`,
  `RuntimeFile`), makes every install that has this package refuse the release as unreadable, so it gets the unreadable message rather than
  "run the new setup", and loses self-update for that release. S3b-7 writes only the keys defined in section 1, in the program-part
  manifest. A new key needs a new Format number and the new setup on every PC, and S3b-7 says so in its own port note.
- **The bridge stays x86.** `BuildRelease` writes `Runtime=.NETFramework 4.8 win-x64` for a bridge build that runs as an x64 process,
  and every bridge and v0.0 workstation would then refuse it. A bridge Release build must stay `PlatformTarget` x86
  (`Directory.Build.props`). The gate's Release dry run and `ApphostResourceTests` are where to see it.
- **No v0.0 install may remain before the .NET 10 publish** (plan section 10, step 3). v0.0 reads a manifest it cannot parse as
  "nothing published", so a 0.0 workstation would publish over the .NET 10 release. The bridge release note already says to uninstall 0.0
  first.
- Wording for 3b: on the forward-switch publish, `PrefL.PublishRelease` asks "so the other workstations update to it when they start?",
  but the bridge workstations need the new setup. Word that question differently when `IsForwardRuntimeSwitch` is true (S3b-7).
- `ApphostResourceTests` reads whatever `OpenPmsDental\bin\Release` holds. Run it only after the gate's Release dry run, never against
  older Release output.

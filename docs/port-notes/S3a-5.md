# Port note: S3a-5 (PasswordVault to Windows Credential Manager)

Package S3a-5 of stage 3a, wave 1, of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-5 row): branch
`net10/s3a5-1` from `main` (`ed9914827`). The saved Middle Tier logins move from the Windows Runtime `PasswordVault` to the Windows
Credential Manager, through `advapi32.dll` (`CredWriteW`, `CredReadW`, `CredDeleteW`, `CredEnumerateW`, `CredFree`), behind the same public
interface. .NET 5 and later cannot consume `.winmd` files
(https://learn.microsoft.com/en-us/dotnet/core/compatibility/interop/5.0/built-in-support-for-winrt-removed), so `PasswordVaultWrapper.csproj`
drops its `Windows.winmd` reference and `Required dlls/Windows.winmd` is deleted. No schema change, no package, nothing downloaded, no
target framework change; no program was started.

Commits: `c1224366d` (the spec, section 1 of this note as first written), `a0fdb1932` (the library), `1d2d45f33` (the tests), and this
note with the plan's status line, the release-note line and the README.

## 1. The public interface (unchanged)

`PasswordVaultWrapper.WindowsPasswordVaultWrapper` keeps its name, its namespace and its four public static methods with the same
signatures; each now calls `CredentialStore.Default`:

| Method | Before (PasswordVault) | Now (Credential Manager) |
|---|---|---|
| `WritePassword(uri,username,password)` | `PasswordVault.Add`; throws for a blank password | `CredWriteW`, replaces the same login; throws `ArgumentException` for a blank user name or password, or a password over 1280 characters (the Credential Manager's 2560 bytes) |
| `TryRetrieveUserName(uri,out username)` | first entry of `FindAllByResource`; false on any error | the address's first saved user (oldest written first); false on any error |
| `RetrievePassword(uri,username)` | `Retrieve` + `RetrievePassword`; throws when there is none | `CredReadW`; throws `Win32Exception` 1168 ("Element not found") when there is none |
| `ClearCredentials(uri)` | removes the address's entries; threw "element not found" when there were none | deletes the address's logins; no error when there are none (no caller depended on the throw); also removes the old vault's entries of that address (section 3) |

The callers are not changed: `OpenPmsDentalBusiness/Data Interface/CentralConnections.cs` (TrySaveConnectionSettings and
GetChooseDatabaseConnectionSettings), `CentralManager/Db/CentralConfigHelper.cs` and `CentralManager/FormCentralManager.cs`.
`OpenPmsDentalBusiness/Misc/ForkRelease/ForkReleases.cs` and `tools/Build-Release.ps1` still ship `PasswordVaultWrapper.dll` (same name,
same version 1.0.0.0); the release keeps denying `*.winmd`.

New, internal (with `InternalsVisibleTo("BINBTests")`):

- `PasswordVaultWrapper/CredentialManager.cs`: the P/Invoke, generic credentials only (`CRED_TYPE_GENERIC`), persisted for this Windows
  user on this computer (`CRED_PERSIST_LOCAL_MACHINE`, never roaming). `IntPtr` fields throughout, so it is pointer-size safe for the x64
  switch. The secret buffer is zeroed before it is freed. `List(prefix)` asks Windows for `prefix*` and checks `StartsWith` again; a blank
  prefix is refused.
- `PasswordVaultWrapper/CredentialStore.cs`: the logins and the migration, with its names given to the constructor; `Default` holds the
  program's names.
- `PasswordVaultWrapper/OldPasswordVault.cs`: the old vault, read by reflection (section 3).

**Where a login is stored.** Target name `OpenPmsDental Middle Tier:<uri>|<username>`, the credential's own user name `<username>`, the
password as UTF-16. Users see these under Control Panel > Credential Manager > Windows Credentials > Generic Credentials. A login is found
by listing `OpenPmsDental Middle Tier:*` and keeping only the entries whose target name is exactly the one computed from the address and the
entry's own user name, so an address that is the start of another one (`https://mt.example.test` and `https://mt.example.test:8443/...`)
never finds the other's login. Several users per address are kept, as PasswordVault kept them.

## 2. The one-time migration and its record

On the first use of any of the four methods in a process, `CredentialStore.EnsureMigrated` looks for the record, the generic credential
`OpenPmsDental Middle Tier migration from PasswordVault` (user name `PasswordVault migration`). If it is there, nothing more happens. If not,
on .NET Framework:

1. The old vault is opened (section 3). If it cannot be opened, there is nothing to read: the record says so.
2. Its entries are listed by name only (`RetrieveAll` returns no passwords) and only those whose resource starts with
   `OpenDental Middle Tier:` (the name Open Dental and this program wrote) and has an address after it are kept. Only these are read further.
3. For each one: if the Credential Manager already has a login for that address and user (saved since), it is left alone ("already there");
   otherwise the vault's password is read and written as the login ("copied"); an unreadable or blank one counts as "failed".
4. The record is written, its secret being `yyyy-MM-dd HH:mm:ss UTC: Copied <n>, already there <n>, failed <n>[, PasswordVault not available]`.

If the vault cannot be listed (an error other than "not found", which means an empty vault), no record is written and the next process tries
again. Errors never reach the caller: the four methods then work on what the Credential Manager has. Two programs starting at once may both
copy; the writes are the same, so that is harmless. The old vault's entries are copied, not moved: an older release still finds them.

On .NET 10 (stage 3b) the old vault cannot be read: `OldPasswordVault.TryOpen` returns null under `#if NETFRAMEWORK`'s else branch and
`EnsureMigrated` writes no record there, so the bridge release (the last .NET Framework release, on every workstation before 3b) is what moves
the logins.

## 3. Reading the old vault without Windows.winmd

On .NET Framework the CLR finds Windows Runtime types through the operating system's own metadata (`C:\Windows\System32\WinMetadata`), so
no reference to the SDK's `Windows.winmd` is needed at run time, and none at compile time when the type is looked up by name:
`Type.GetType("Windows.Security.Credentials.PasswordVault, Windows.Security.Credentials, ContentType=WindowsRuntime")` (the same lookup
Windows PowerShell 5.1 uses), then `Activator.CreateInstance` and the methods `RetrieveAll`, `FindAllByResource`, `Remove`, `Add` (tests
only) and `PasswordCredential.RetrievePassword` / `Password` by reflection, with the vault's own exception unwrapped from
`TargetInvocationException`. So the reference could go in 3a; nothing waits for 3b.

`ClearCredentials` also removes the old vault's entries of exactly that resource (`OpenDental Middle Tier:<uri>`), best effort: without
that, a login cleared before the migration ran could be copied back from the vault.

## 4. What the tests touch (the owner's safety rules)

The tests run on the developer's own Windows account. `tests/BINBTests/CredentialStoreTests.cs` works only through `TestCredentialStore`,
a store whose names all start with a per-run prefix `OpenPmsDentalTest:<guid>:`: logins under `<prefix>cm:`, old-vault resources under
`<prefix>vault:` (and one under `<prefix>other:`, to prove other resource names are not copied), and the record `<prefix>record`. So:

- they create, read and delete only entries under that prefix; the Credential Manager listing is filtered by Windows (`<prefix>*`) and
  checked again by `StartsWith` before an entry is deleted; the old vault's entries are removed by the exact resources the test wrote;
- the migration under test lists the vault by name and filters by the test's resource prefix before it reads any password, as the program
  does with its own name;
- they never call the four public static methods (which would run the program's real migration on the account) and never read the program's
  names: `TheProgram_UsesItsOwnNames_ThroughTheSamePublicInterface` checks the names, the signatures and the delegation by reflection and
  by reading the source;
- every user name and password is synthetic; addresses use `*.example.test`;
- clean-up is in `Dispose` (a `using` block, so `finally`). After the runs, `cmdkey /list:OpenPmsDentalTest*` showed none.

The tests (all passed; the vault tests ran, not Inconclusive):

| Test | Proves |
|---|---|
| `Login_IsWrittenReadReplacedAndCleared` | write, read, replace, a second user, the target name, clear, "not found" after clearing, clearing nothing |
| `Login_IsFoundForItsOwnAddressOnly` | an address that starts another one finds nothing of it; clearing one leaves the other; a wrong user is not found |
| `BlankUserOrPassword_Throws_AndNothingIsWritten` | blank user, blank or null password and an over-long password throw and write nothing; 1280 characters fit |
| `Migration_CopiesTheVaultEntries_OnFirstUse_AndRunsOnce` | an entry written through PasswordVault is readable through the Credential Manager after the first use; the record; the vault entry stays; a later vault entry is not copied, in the same store or a new one (the next process), and the record is unchanged |
| `Migration_NeverReplacesALoginAlreadyThere_AndCopiesOnlyItsOwnResourceName` | a newer login wins; another resource name and the bare prefix are not copied |
| `Clear_AlsoRemovesTheOldVaultEntriesOfTheAddress` | the cleared address's vault entry is gone, the other address's stays |
| `Migration_WithoutAVault_RecordsThatThereWasNothingToRead` | no vault: the record says so and the logins work |
| `TheProgram_UsesItsOwnNames_ThroughTheSamePublicInterface` | the program's three names, the four signatures, the delegation to `CredentialStore.Default` |

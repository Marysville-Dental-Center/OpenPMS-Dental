# Port note: S3a-5 (PasswordVault to Windows Credential Manager)

Package S3a-5 of stage 3a, wave 1, of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-5 row): branch
`net10/s3a5-1` from `main` (`ed9914827`). The saved Middle Tier logins move from the Windows Runtime `PasswordVault` to the Windows
Credential Manager, through `advapi32.dll` (`CredWriteW`, `CredReadW`, `CredDeleteW`, `CredEnumerateW`, `CredFree`), behind the same public
interface. .NET 5 and later cannot consume `.winmd` files
(https://learn.microsoft.com/en-us/dotnet/core/compatibility/interop/5.0/built-in-support-for-winrt-removed), so `PasswordVaultWrapper.csproj`
drops its `Windows.winmd` reference and `Required dlls/Windows.winmd` is deleted. No schema change, no package, nothing downloaded, no
target framework change; no program was started.

Commits: `c1224366d` (the spec, section 1 of this note as first written), `a0fdb1932` (the library), `1d2d45f33` (the tests), and this
note with the plan's status line, the release-note line and the README. Fix round on `net10/s3a5-2`: `2618e46d1` (the library: a vault
that cannot be opened leaves no record), the tests that go with it, and this note's section 2 step 1, section 4 and section 5.

## 1. The public interface (unchanged)

`PasswordVaultWrapper.WindowsPasswordVaultWrapper` keeps its name, its namespace and its four public static methods with the same
signatures; each now calls `CredentialStore.Default`:

| Method | Before (PasswordVault) | Now (Credential Manager) |
|---|---|---|
| `WritePassword(uri,username,password)` | `PasswordVault.Add`; throws for a blank password | `CredWriteW`, replaces the same login; throws `ArgumentException` for a blank user name or password, or a password over 1280 characters (the Credential Manager's 2560 bytes) |
| `TryRetrieveUserName(uri,out username)` | first entry of `FindAllByResource`; false on any error | the address's first saved user (oldest written first); false on any error |
| `RetrievePassword(uri,username)` | `Retrieve` + `RetrievePassword`; throws when there is none | `CredReadW`; throws `Win32Exception` 1168 ("Element not found") when there is none |
| `ClearCredentials(uri)` | removes the address's entries; threw "element not found" when there were none | deletes the address's logins; no error when there are none (no caller depended on the throw); also removes the old vault's entries of that address (section 3) |

The callers are not changed: `OpenPmsDentalBusiness/Data Interface/CentralConnections.cs` (TrySaveConnectionSettings and
GetChooseDatabaseConnectionSettings), `CentralManager/Db/CentralConfigHelper.cs` and `CentralManager/FormCentralManager.cs`.
`OpenPmsDentalBusiness/Misc/ForkRelease/ForkReleases.cs` and `tools/Build-Release.ps1` still ship `PasswordVaultWrapper.dll` (same name,
same version 1.0.0.0); the release keeps denying `*.winmd`.

New, internal (with `InternalsVisibleTo("BINBTests")`):

- `PasswordVaultWrapper/CredentialManager.cs`: the P/Invoke, generic credentials only (`CRED_TYPE_GENERIC`), persisted for this Windows
  user on this computer (`CRED_PERSIST_LOCAL_MACHINE`, never roaming). `IntPtr` fields throughout, so it is pointer-size safe for the x64
  switch. The secret buffer is zeroed before it is freed. `List(prefix)` asks Windows for `prefix*` and checks `StartsWith` again; a blank
  prefix is refused.
- `PasswordVaultWrapper/CredentialStore.cs`: the logins and the migration, with its names given to the constructor; `Default` holds the
  program's names.
- `PasswordVaultWrapper/OldPasswordVault.cs`: the old vault, read by reflection (section 3).

**Where a login is stored.** Target name `OpenPmsDental Middle Tier:<uri>|<username>`, the credential's own user name `<username>`, the
password as UTF-16. Users see these under Control Panel > Credential Manager > Windows Credentials > Generic Credentials. A login is found
by listing `OpenPmsDental Middle Tier:*` and keeping only the entries whose target name is exactly the one computed from the address and the
entry's own user name, so an address that is the start of another one (`https://mt.example.test` and `https://mt.example.test:8443/...`)
never finds the other's login. Several users per address are kept, as PasswordVault kept them.

## 2. The one-time migration and its record

On the first use of any of the four methods in a process, `CredentialStore.EnsureMigrated` looks for the record, the generic credential
`OpenPmsDental Middle Tier migration from PasswordVault` (user name `PasswordVault migration`). If it is there, nothing more happens. If not,
on .NET Framework:

1. The old vault is opened (section 3). Only a Windows older than 8 (`OldPasswordVault.IsOsWithoutVault`: version below 6.2) has no
   vault; there nothing can ever be read, so the record is written at once and says so. On Windows 8 and later the vault always exists, so
   failing to open it (`TryOpen` returning null, or `Activator.CreateInstance` throwing: the Credential Manager service not started yet early
   in a logon, an RPC or COM error) is an error that may pass: **no record is written** and the next process tries again (one failed open per
   process). So one unlucky start cannot record the migration as done with nothing copied.
2. Its entries are listed by name only (`RetrieveAll` returns no passwords) and only those whose resource starts with
   `OpenDental Middle Tier:` (the name Open Dental and this program wrote) and has an address after it are kept. Only these are read further.
3. For each one: if the Credential Manager already has a login for that address and user (saved since), it is left alone ("already there");
   otherwise the vault's password is read and written as the login ("copied"); an unreadable or blank one counts as "failed".
4. The record is written, its secret being `yyyy-MM-dd HH:mm:ss UTC: Copied <n>, already there <n>, failed <n>[, PasswordVault not available]`.

Likewise, if the vault opens but cannot be listed (an error other than "not found", which means an empty vault), no record is written and
the next process tries again. Errors never reach the caller: the four methods then work on what the Credential Manager has. Two programs starting at once may both
copy; the writes are the same, so that is harmless. The old vault's entries are copied, not moved: an older release still finds them.

On .NET 10 (stage 3b) the old vault cannot be read: `OldPasswordVault.TryOpen` returns null under `#if NETFRAMEWORK`'s else branch and
`EnsureMigrated` writes no record there, so the bridge release (the last .NET Framework release, on every workstation before 3b) is what moves
the logins.

## 3. Reading the old vault without Windows.winmd

On .NET Framework the CLR finds Windows Runtime types through the operating system's own metadata (`C:\Windows\System32\WinMetadata`), so
no reference to the SDK's `Windows.winmd` is needed at run time, and none at compile time when the type is looked up by name:
`Type.GetType("Windows.Security.Credentials.PasswordVault, Windows.Security.Credentials, ContentType=WindowsRuntime")` (the same lookup
Windows PowerShell 5.1 uses), then `Activator.CreateInstance` and the methods `RetrieveAll`, `FindAllByResource`, `Remove`, `Add` (tests
only) and `PasswordCredential.RetrievePassword` / `Password` by reflection, with the vault's own exception unwrapped from
`TargetInvocationException`. So the reference could go in 3a; nothing waits for 3b.

`ClearCredentials` also removes the old vault's entries of exactly that resource (`OpenDental Middle Tier:<uri>`), best effort: without
that, a login cleared before the migration ran could be copied back from the vault.

### 7.1 Target names compare as Windows compares them

Windows reads, lists and deletes generic credentials by a target name without regard to case. It does not merge casings on a write,
though: probed on Windows 11 under a test prefix, `CredWriteW` with `...HTTPS://MT.EXAMPLE.TEST/X|USER` while `...https://mt.example.test/x|user`
exists keeps both, and `CredReadW`, `CredEnumerateW` and `CredDeleteW` then see only one of the casings (deleting it uncovers the next).
So the store now:

- compares target names and user names with `OrdinalIgnoreCase` (`ListLogins`, `RetrievePassword`, the prefix check in
  `CredentialManager.List`, the old vault's resource check in `ClearCredentials`): a differently-cased address or user finds its login;
- saves a login under the name it already has, in that casing (`GetSavedTargetName`: `CredReadW` on the computed name, then the casing it
  returns), never under a second casing that Windows would hide behind the first, so saving it again in another casing replaces it;
- deletes again until no casing is left (`ClearCredentials`, and the removal of an S3a-5 name, at most 20 rounds), so a casing that an
  S3a-5 store could have written next to another is cleared too.

### 7.2 The target-name rule

| Login (address, user) | Target name after the prefix | Form |
|---|---|---|
| `https://mt.example.test/ServiceMain.asmx`, `synthetic-user` | `https://mt.example.test/ServiceMain.asmx\|synthetic-user` | plain, as S3a-5 |
| `https://mt.example.test/a%20b`, `DOMAIN\user` | `https://mt.example.test/a%20b\|DOMAIN\user` | plain, as S3a-5 |
| `https://mt.example.test/a\|b`, `c` | `https://mt.example.test/a%7Cb%_c` | escaped |
| `https://mt.example.test/a`, `b\|c` | `https://mt.example.test/a%_b%7Cc` | escaped |
| `https://mt.example.test/a%20b`, `DOMAIN\x\|y` | `https://mt.example.test/a%2520b%_DOMAIN\x%7Cy` | escaped |

- **Plain** (address and user without `|`): `<prefix><uri>|<user>`, byte for byte the S3a-5 name. Nothing is escaped, a backslash and `%`
  included, so every login saved on the office computers is found as before.
- **Escaped** (a `|` in either): `<prefix>E(uri)%_E(user)`, where `E` writes `%` as `%25` and `|` as `%7C` and nothing else. It has no `|`
  after the prefix, while a plain name has exactly one, so the two forms never meet; inside it every `%` that `E` writes is followed by
  `25` or `7C`, so the first `%_` is the separator and no two logins share a name (also not case-insensitively: `25` and `7C` differ in
  any case). `TargetName_IsUnambiguousWithAPipe_AndUnchangedWithout` checks 18 tricky pairs.
- **Read fallback** for an escaped login: an entry under its S3a-5 name `<prefix><uri>|<user>` is found too, but only when that entry's own
  user name (the credential's user name field) is the login's. The S3a-5 name was ambiguous (`a|b` + `c` and `a` + `b|c` both gave
  `a|b|c`; Windows kept one of them), and the user name field tells which login it is. `RetrievePassword` reads the escaped name first,
  then checks the S3a-5 entry's user name (without its secret) before reading it; `GetUserNames` lists each user once;
  `WritePassword` writes the escaped name and then deletes the S3a-5 entry when it is this login's (another login's stays);
  `ClearCredentials` deletes both. So such a login moves to its escaped name on its next save. Before S3a-5f a `|` login of this kind
  would in practice not exist: Middle Tier addresses are URLs and the program's user names have no `|`.

### 7.3 The migration retries the entries that failed

Before, the record was written once and the migration never ran again, even with `failed` above 0. Now a try that leaves failed entries
writes a record with a second line naming them:

```
2026-11-15 10:00:00 UTC: Copied 1, already there 0, failed 1
Retry: 1 of 5 tries done; on the next start: 0123456789abcdef
```

Each entry is named by the first 16 hexadecimal digits of the SHA-256 of its vault resource and user name (never the password, and not the
address in clear; at most 50 are named, which keeps the record within the Credential Manager's 1280 characters). The next start reads the
record, lists the vault by name as before and tries again only the named entries: an entry saved in the Credential Manager since counts as
"already there", a copied one as "copied", the others stay named. The counts carry on (copied and already there add up, failed is what is
still failing), and the first line gains `, in <n> tries`. A try that leaves nothing to retry, or the fifth try whatever failed, writes a
record without the retry line: complete, and the vault is not read again. An S3a-5 record (no retry line) is complete, and so is a record
this release cannot read (a damaged one never makes every start read the vault). A start whose vault cannot be opened or listed keeps the
previous record and does not count as a try (as in section 2). An entry the vault got after the first try is not copied by a retry.

### 7.4 "Already there" without the secret

`CredentialManager.ReadInfo` calls `CredReadW` on the exact target and returns the user name and the time but leaves the secret blob
undecoded. The migration's check (`LoginExists`: the target in any casing, or the S3a-5 name with this user) uses only `ReadInfo`; the
migration code calls `CredentialManager.Read` nowhere (a test checks the source). No vault password is read for a login already there.

### 7.5 The tests clean up first, assert after

`TestCredentialStore.Dispose` lists `<prefix>*` again until it is empty (each round deletes what Windows shows, which may uncover another
casing; at most 20 rounds), deletes each entry on its own with its error caught, removes each resource it wrote to the old vault on its own,
and asserts once at the end that nothing failed. An entry not under the prefix is never deleted (and reported). The S3a-5f tests use
`FakeOldVault`, an old vault in memory, so they never touch the real vault.

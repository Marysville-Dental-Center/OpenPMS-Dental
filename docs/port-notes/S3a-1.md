# Port note: S3a-1 (no more Thread.Abort)

Package S3a-1 of stage 3a of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-1 row): branch `net10/s3a1-1`
from `main` (`3620550cb`). `Thread.Abort` always throws `PlatformNotSupportedException` on .NET 5 and later
(https://learn.microsoft.com/en-us/dotnet/core/compatibility/core-libraries/5.0/thread-abort-obsolete, SYSLIB0006). Every `Thread.Abort`
of the shipped code was in the files this package owns; all five are gone, replaced by cooperative cancellation that behaves the same for
the user on net48. No schema change, no new package or DLL, nothing downloaded, no program started.

Commits: `128b8f383` (ODThread), `59be00388` (the progress window, ProgressWin and the two Join callers), `57815ded6` (tests), `701ef46d9` (this
note with the plan's status line), then `main` (`818fe6015`: S3a-3, S3a-5 and S3a-9 merged) merged in as `5a8ba0175` (only the plan's
status lines met; both kept), and the final full build and Targeted runs on that merge.

## 1. ODThread: Join on timeout no longer aborts (`CodeBase/Utilities/ODThread.cs`)

| | Before | Now |
|---|---|---|
| `Join(timeoutMS)` reaches the timeout | `Thread.Abort` on the thread, returns false | returns false and never throws; the thread is asked to quit (`HasQuit` true, a wait for the next interval is woken up), becomes a background thread (so it cannot keep the process alive at exit) and finishes its current `WorkerDelegate` on its own |
| An exception from the thread after that | swallowed (`_wasAbortAttempted`) | swallowed the same way (`_hasJoinTimedOut`); the thread quits |
| Exit handler after a timed-out Join | did not fire (the abort ended the thread) | does not fire (kept as documented on `_exitHandler`) |
| A thread on an interval | aborted | quits instead of waiting out its interval and does not run again |
| `RunParallel` timeout (both paths) | its threads aborted mid-action | `RunParallel` still returns at the timeout; each thread runs the action it is in to its end in the background and starts no further action (the worker loops check `HasQuit`) |
| `QuitSync(timeout)`, `QuitSyncThreadsByGroupName`, `QuitSyncAllOdThreads` at exit | threads still running at the timeout were aborted | they are asked to quit and become background threads, which end with the process |

`_hasQuit` is now `volatile` (the worker reads it while another thread sets it). The `ThreadAbortException` test in
`WorkerExceptionHandler` stays (dead for ODThread's own threads; plan: such catches are removed after 3b). Doc comments of `Join`,
`HasQuit`, `QuitSync`, `QuitSyncAllOdThreads` and the three `RunParallel` summaries say the new behaviour.

## 2. The progress window (`WpfControlsOD/UI/Progress/FrmProgressAuto.xaml.cs`, `ProgressWin.cs`)

The four aborts (after success, after an exception, on cancel, and on Close after history) are gone.

| Case | What the user sees (unchanged) | How it works now |
|---|---|---|
| Success | the window closes by itself; `IsSuccess` | the worker reports through `Dispatcher.Invoke` and the thread ends by itself (no abort after the action) |
| Exception | the window closes; `ShowDialog` rethrows it (the inner exception if there is one) | `ExceptionGenerated` is set inside the Invoke on the main thread, so a cancel and a failure cannot both win |
| History mode, then Close | the window stays open with Done; Close is success | a `_isWorkDone` flag set on the main thread tells "done" from "still running" (the thread's `IsAlive` stays true for a moment after the action) |
| Cancel or X (where allowed) | the window closes as cancelled; `IsCancelled` | see below |
| X without a Cancel button | "Not allowed to stop ..." and the window stays | unchanged (ImagingTests' `Window_WritesCannotBeCancelledPartWay` relies on it) |

Cancel, in place of the abort (`CancelWorker`, on the main thread inside `FormClosing`):

1. The cancel is marked (`_isCancelRequested`). From then on the worker reports nothing to the window or to the caller: a later success,
   exception or history update is dropped, and the window shows no more progress.
2. `ProgressWin.CancellationToken` (new) is cancelled. An action can check it (`ThrowIfCancellationRequested`) or pass it on.
3. `ActionCancel` is invoked. It was set by three callers (`FormEmailAddressEdit.cs:640,723`, `FormEmailMessageEdit.cs:887`, each
   cancelling its own `CancellationTokenSource`) but the window never called it; those sign-in waits now stop on Cancel instead of
   after the window has closed.
4. A cancellation point for actions that report progress: a progress event (`ODEvent.Fire` with a string or a `ProgressBarHelper`)
   fired from the worker thread after the cancel throws `OperationCanceledException`, so a loop that reports each step stops at its
   next report, as close to the old abort as cooperation allows. The handler stays subscribed until the worker ends. Events from other
   threads are ignored, not thrown.
5. A bounded wait: up to `WorkerStopWaitMS` (1000 ms) for the worker to end. If it has not, `ProgressWin.IsWorkerStillRunning` (new) is
   true, the window closes as cancelled anyway, and the background thread finishes on its own; what it returns or throws is dropped.

The "Cancel" section at the top of `ProgressWin.cs` explains this for callers.

**Difference the user can notice (on purpose).** An action that neither checks the token nor reports progress is no longer stopped on
Cancel: the window still closes at once (after at most a second), but the action runs on in the background to its end, where the abort
used to stop it at any point (also part-way through a write). See section 6.

## 3. The two Join callers

- `FormOpenDental.cs` (`CloseOpenForms`, the forced close, 6752): the thread that closes a form waits on `Invoke` for the main thread,
  so its `Join(1000)` usually times out (it did before too, and the abort then cut the thread off). Now: after `Application.DoEvents`
  (which runs the queued `Close`), a timed-out Join gets one more `Join(1000)`, so that the thread has usually finished before the check;
  then, as before, a form that failed to close is disposed. A thread still running ends on its own (background). The second Join does not
  make an error reported (corrected in S3a-1b, section 8): once the first Join has timed out, ODThread no longer hands the thread's
  exceptions to its handler, so `hasError` stays false and nothing is submitted; since S3a-1b such an exception is logged
  (`ODCancellation.Log`). A form whose Close failed after the first Join is still disposed if it is not closed by the check.
- `ControlChart.cs` (836, inside the commented-out Apteryx download of `listViewImages_DoubleClick`, kept as comment): if the Join times
  out it now shows "The image did not finish downloading. Please try again." and returns, instead of showing and disposing a bitmap
  that may be null. No other line of `ControlChart.cs` changed (TC-5's TextBelow strip is untouched).

## 8. S3a-1b: no database write after a cancel (follow-up, branch `net10/s3a1b-1`)

Lead-assigned on 2026-11-15 after S3a-1's merge (`168bd2767`). With `Thread.Abort` gone, a cancelled action stopped only where it checked
`ProgressWin.CancellationToken` or fired a progress event; an action that did neither ran on to its end in the background after the
window had closed as cancelled, writes included. Lead decisions on S3a-1's questions: the progress-event cancellation point stays, the
one-second wait is fine, a worker still running is logged. No schema change, no new package or DLL, nothing downloaded, no program started.

### 8.1 The guarantee and how it is kept

**No database write starts for a progress window's action after the user cancelled it.** At most the command under way at the cancel
finishes, or the rest of a unit that the caller declared uncancellable (below). This is the new wording of the plan's risk item, which
asked for "no database write after cancelled" (`docs/specs/net10-plan.md`, stage 3a risks).

- `CodeBase/Utilities/ODCancellation.cs` (new; linked into `UpdateFileCopier.csproj` next to `ODThread.cs` and `ODFileUtils.cs`, which use
  it): the cancellation of the action a thread runs, held per thread (`[ThreadStatic]`). `Use(token)` sets it until disposed;
  `ThrowIfCancellationRequested()`; `RunUncancellable(action)` runs a unit that a cancel does not split; `GetTokenForChildThreads()`;
  `Log(line)` (Logger sub-directory `Cancellation`, plus the `LineLogged` event for tests). A thread that never had a token (the main
  thread, the Middle Tier server's threads, every ODThread that is not a RunParallel pool thread) has `CancellationToken.None` and is never
  stopped by it, so nothing changes outside a cancelled progress action.
- `FrmProgressAuto.DoWork` sets the window's token on its worker thread (the token that `ProgressWin.CancellationToken` gives).
- `DataConnectionBase/DataConnection.cs` `RunDbAction` (every command of `GetTable`, `GetList`, `NonQ`, `GetCount`, `GetScalar` and the
  static pref reads, retries included) checks first; its catch closes the connection. So the action's next database command after the
  cancel, read or write, throws `OperationCanceledException`, which `FrmProgressAuto` drops as before (not logged: it is the expected stop).
- `OpenPmsDentalBusiness/Remoting/RemotingClient.cs` `SendAndReceive` checks before every Middle Tier request, so a Middle Tier client
  sends nothing more for the action and the server writes nothing more for it (a request already sent runs to its end on the server).
- `ODThread.RunParallel` (all three paths) passes the caller's token to its pool threads, whose writes then stop as the caller's do; a pool
  thread starts no further action after the cancel, and RunParallel then throws `OperationCanceledException` on the caller, so the caller
  does not go on as if every action had run (item 3).
- Units: `ODCancellation.RunUncancellable(() => ...)` for a write and what belongs to it (its security log entry, the claim that records
  what a vendor was sent). Inside a unit the checks above do nothing, a progress event does not throw, and a RunParallel inside it gets no
  token; the next check after the unit stops the action. A cancel then never splits a write from its log entry.
- Cleanup writes: unlike under `Thread.Abort`, whose catch and finally bodies still ran and wrote, the database layer refuses a cleanup
  write in a catch or finally block after a cancel, so each such cleanup must be a unit. `ImageStore`'s imports (`Import`, all four
  overloads, `ImportForm`, `ImportImageToMount`, `ImportEobAttach`) insert the row, then save the file with its security log entry, and
  delete the row in their catch if that fails: that delete runs in `RunUncancellable` (fix round, `net10/s3a1b-2`).
- File and vendor loops check `ODCancellation.ThrowIfCancellationRequested()` (or the window's token) before each file or call, outside
  any catch that would swallow it.

Not covered, on purpose: threads that the action starts itself other than through RunParallel (none of the audited callers writes from
one); a transfer to cloud storage under way (it runs on its own task, which the abort did not stop either); a statement boundary inside a
business operation that is not a unit (for example `FeeScheds.CopyFeeSchedule` can be left with the target schedule part-copied, a
place the old abort could leave too, at any point). `ImageStore.Import` after a cancel during its file copy or cloud upload: the file's
security log entry is refused, the catch deletes the row (a unit, above) and the import throws, so no document row is left; the copied or
uploaded file stays in the patient's folder without a row, which "add missing files" picks up, as after the old abort (in-database
storage: nothing is left).

### 9.3 FrmProgressAuto: a worker that ends right after the wait (item 3)

`CancelWorker` decided "still running" from the `Join`'s timeout alone and then set `_isLoggingWorkerEnd`; a worker that ended between the two
had already passed its check in `DoWork`'s finally, so "still running" was logged and its end never was. Setting the flag before the `Join`,
as the note suggested, closes that gap but would log an end for every worker that stops within the wait as well. Instead the decision and the
worker's end meet under a lock (`_lockWorkerEnd`): the worker's finally sets `_isWorkerEnded` and reads the flag under it; `CancelWorker`, after
the `Join`, sets `IsWorkerStillRunning=!_isWorkerEnded` under it and, if still running, sets the flag and writes the "still running" line
there. So a worker that ends right after the timeout is not still running and nothing is logged, or it sees the flag and logs its end, always
after the "still running" line. `_isLoggingWorkerEnd` is no longer volatile. A private static hook (`_actionAfterJoinTimeoutForTests`, set by
reflection in M2MISCTests, null otherwise) runs between the timed-out `Join` and the decision, so a test can let the worker end exactly there.

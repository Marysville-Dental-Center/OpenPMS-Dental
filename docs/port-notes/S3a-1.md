# Port note: S3a-1 (no more Thread.Abort)

Package S3a-1 of stage 3a of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-1 row): branch `net10/s3a1-1`
from `main` (`3620550cb`). `Thread.Abort` always throws `PlatformNotSupportedException` on .NET 5 and later
(https://learn.microsoft.com/en-us/dotnet/core/compatibility/core-libraries/5.0/thread-abort-obsolete, SYSLIB0006). Every `Thread.Abort`
of the shipped code was in the files this package owns; all five are gone, replaced by cooperative cancellation that behaves the same for
the user on net48. No schema change, no new package or DLL, nothing downloaded, no program started.

Commits: `128b8f383` (ODThread), `59be00388` (the progress window, ProgressWin and the two Join callers), `57815ded6` (tests), and this
note with the plan's status line.

## 1. ODThread: Join on timeout no longer aborts (`CodeBase/Utilities/ODThread.cs`)

| | Before | Now |
|---|---|---|
| `Join(timeoutMS)` reaches the timeout | `Thread.Abort` on the thread, returns false | returns false and never throws; the thread is asked to quit (`HasQuit` true, a wait for the next interval is woken up), becomes a background thread (so it cannot keep the process alive at exit) and finishes its current `WorkerDelegate` on its own |
| An exception from the thread after that | swallowed (`_wasAbortAttempted`) | swallowed the same way (`_hasJoinTimedOut`); the thread quits |
| Exit handler after a timed-out Join | did not fire (the abort ended the thread) | does not fire (kept as documented on `_exitHandler`) |
| A thread on an interval | aborted | quits instead of waiting out its interval and does not run again |
| `RunParallel` timeout (both paths) | its threads aborted mid-action | `RunParallel` still returns at the timeout; each thread runs the action it is in to its end in the background and starts no further action (the worker loops check `HasQuit`) |
| `QuitSync(timeout)`, `QuitSyncThreadsByGroupName`, `QuitSyncAllOdThreads` at exit | threads still running at the timeout were aborted | they are asked to quit and become background threads, which end with the process |

`_hasQuit` is now `volatile` (the worker reads it while another thread sets it). The `ThreadAbortException` test in
`WorkerExceptionHandler` stays (dead for ODThread's own threads; plan: such catches are removed after 3b). Doc comments of `Join`,
`HasQuit`, `QuitSync`, `QuitSyncAllOdThreads` and the three `RunParallel` summaries say the new behaviour.

## 2. The progress window (`WpfControlsOD/UI/Progress/FrmProgressAuto.xaml.cs`, `ProgressWin.cs`)

The four aborts (after success, after an exception, on cancel, and on Close after history) are gone.

| Case | What the user sees (unchanged) | How it works now |
|---|---|---|
| Success | the window closes by itself; `IsSuccess` | the worker reports through `Dispatcher.Invoke` and the thread ends by itself (no abort after the action) |
| Exception | the window closes; `ShowDialog` rethrows it (the inner exception if there is one) | `ExceptionGenerated` is set inside the Invoke on the main thread, so a cancel and a failure cannot both win |
| History mode, then Close | the window stays open with Done; Close is success | a `_isWorkDone` flag set on the main thread tells "done" from "still running" (the thread's `IsAlive` stays true for a moment after the action) |
| Cancel or X (where allowed) | the window closes as cancelled; `IsCancelled` | see below |
| X without a Cancel button | "Not allowed to stop ..." and the window stays | unchanged (ImagingTests' `Window_WritesCannotBeCancelledPartWay` relies on it) |

Cancel, in place of the abort (`CancelWorker`, on the main thread inside `FormClosing`):

1. The cancel is marked (`_isCancelRequested`). From then on the worker reports nothing to the window or to the caller: a later success,
   exception or history update is dropped, and the window shows no more progress.
2. `ProgressWin.CancellationToken` (new) is cancelled. An action can check it (`ThrowIfCancellationRequested`) or pass it on.
3. `ActionCancel` is invoked. It was set by three callers (`FormEmailAddressEdit.cs:640,723`, `FormEmailMessageEdit.cs:887`, each
   cancelling its own `CancellationTokenSource`) but the window never called it; those sign-in waits now stop on Cancel instead of
   after the window has closed.
4. A cancellation point for actions that report progress: a progress event (`ODEvent.Fire` with a string or a `ProgressBarHelper`)
   fired from the worker thread after the cancel throws `OperationCanceledException`, so a loop that reports each step stops at its
   next report, as close to the old abort as cooperation allows. The handler stays subscribed until the worker ends. Events from other
   threads are ignored, not thrown.
5. A bounded wait: up to `WorkerStopWaitMS` (1000 ms) for the worker to end. If it has not, `ProgressWin.IsWorkerStillRunning` (new) is
   true, the window closes as cancelled anyway, and the background thread finishes on its own; what it returns or throws is dropped.

The "Cancel" section at the top of `ProgressWin.cs` explains this for callers.

**Difference the user can notice (on purpose).** An action that neither checks the token nor reports progress is no longer stopped on
Cancel: the window still closes at once (after at most a second), but the action runs on in the background to its end, where the abort
used to stop it at any point (also part-way through a write). See section 6.

## 3. The two Join callers

- `FormOpenDental.cs` (`CloseOpenForms`, the forced close, 6752): the thread that closes a form waits on `Invoke` for the main thread,
  so its `Join(1000)` usually times out (it did before too, and the abort then cut the thread off). Now: after `Application.DoEvents`
  (which runs the queued `Close`), a timed-out Join gets one more `Join(1000)` so that `hasError` is known; then, as before, a form that
  failed to close is disposed. A thread still running ends on its own (background).
- `ControlChart.cs` (836, inside the commented-out Apteryx download of `listViewImages_DoubleClick`, kept as comment): if the Join times
  out it now shows "The image did not finish downloading. Please try again." and returns, instead of showing and disposing a bitmap
  that may be null. No other line of `ControlChart.cs` changed (TC-5's TextBelow strip is untouched).

  returns at the timeout before the action ends, and the action then finishes on its own. `ODThread_CatchThreadAbortException`: `Join(0)`

  `ODThread_JoinTimeout_ReturnsFalse_ThreadFinishesOnItsOwn` (not stopped, background afterwards, exit handler not fired),

  unchanged.
- New `tests/M2MISCTests/ProgressWinTests.cs` (the row allows M2MISCTests; WPF on an STA thread of the test, the real window shown and
  closed by itself or by its X from a timer on its thread): success; an exception and an inner exception; cancel through the token
  (ActionCancel once, no "write" after the cancel beyond the one under way); cancel through the next progress event; an action that does
  not stop (closes after the bounded wait, `IsWorkerStillRunning`, its later exception dropped, the outcome stays cancelled); history mode

## 6. Callers that relied on Join or a timeout aborting, for their owners

These now get a thread that finishes on its own after the timeout instead of one that is cut off. None needs a change to build or run on
net48 or .NET 10; each owner should check that nothing after the timeout reads state the late thread still writes.

- `QuitSync` with a finite timeout: `FormEtrans834Import.cs:88` and `FormEtrans834Preview.cs:66` (`QuitSync(0)`),
  `FormFamilyBalancer.cs:261,310,381,448,496,499,502,505` (5000; the comments "before aborting" are now out of date),
  `UserControlDashboard.cs:250,265` (100).
- `JoinThreadsByGroupName`/`QuitSyncThreadsByGroupName` with a finite timeout: `CentralManager/FormCentralManager.cs:146,198`,
  `FormCentralPatientSearch.cs:234,254,288` (1 or 100 ms: "stop fetching immediately" is now "stop after the fetch under way").
- `QuitSyncAllOdThreads()` at exit: `FormOpenDental.cs:7053`, `CentralManager/FormCentralManager.cs:250` (threads still running become
  background threads and end with the process).
- `RunParallel` with a finite timeout: `FormClinics.cs:280`, `FormFinanceCharges.cs:353`, `FormProviderSetup.cs:525,562`,
  `Adjustments.cs:710`, `FeeScheds.cs:440`, `Procedures.cs:3204,3305`, `Recalls.cs:990`, `LargeTableHelper.cs:387,476`; after a timeout
  the caller goes on while the actions under way finish (an action that adds to a shared list without a lock could then race the
  caller; the abort raced it too).
- `ProgressWin` (131 `new ProgressWin()` in shipped code, 30 with `ShowCancelButton=false`): the plan's stage 3a risk "review each long
  action reachable from a ProgressWin for a check point" is not done here (outside Owns). Actions that report progress already stop at
  their next report; an action that writes without reporting progress and has a Cancel button should check `progressWin.CancellationToken`
  before each write or drop its Cancel button.

# Port note: S3b-8 (the 32-bit TWAIN path through the helper, and the 32-bit TWAIN manager in the setup)

Package S3b-8 of stage 3b of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md): decision 23, "TWAIN devices with only a
32-bit driver need a 32-bit TWAIN path through the helper. New, for 3b"; decisions 19 and 20; section 7's pointer-size row), on
`net10/s3b8-1` from `net10/switch` (`008291480`), 2026-11-16. The owner's answer in `docs/decisions/owner-questions.md`, "32-bit TWAIN manager: yes",
is the setup part. Built on the helper ([S3a-13.md](S3a-13.md), [S3a-14.md](S3a-14.md)), its x86 runtime in `Helper32\` ([S3b-4.md](S3b-4.md)),
the pointer-size-safe TWAIN code ([S3a-12.md](S3a-12.md)), native first ([N64-A.md](N64-A.md), `NativeFirstChooser`), the capture flow
([CAP.md](CAP.md), [docs/specs/imaging-capture-design.md](../specs/imaging-capture-design.md)) and the 64-bit TWAINDSM of the setup ([S3b-7.md](S3b-7.md)).
Public sources only: the TWAIN 2.5 specification and the TWAIN DSM source in the approved download; no disassembly. No schema change, no
package, nothing downloaded (the 32-bit `TWAINDSM.dll` is the one S3b-7 downloaded), no window shown, no real scanner, sensor, driver or
DSM touched: every test runs on the fake DSM.

## 1. What changed for the office

- **A TWAIN source with only a 32-bit driver works in the 64-bit program.** The device list (Setup > Imaging > Devices, a device, Twain Name)
  shows the sources of the 64-bit TWAIN manager as before, then those only the 32-bit manager lists, as `<name> (32-bit TWAIN)`. Such a
  source runs its whole TWAIN session in the 32-bit helper (`Helper32\OpenPmsDentalHelper32.exe`): the capture session (Mount/Acquire with a
  Twain Radiograph device) and Test capture work on it as on a 64-bit source, with the same images, bit depth, capture metadata, end
  reasons, safe stops, journal copies and quarantine; the source's own window shows as it does in the program's process.
- **Native first.** A source the 64-bit manager lists always runs in the program's own process, also when the device was set to its
  32-bit entry before the vendor shipped a 64-bit driver. A device name stored before S3b-8 (no marker) keeps working on whichever manager
  lists it: 64-bit first, else the 32-bit one.
- **The setup installs the 32-bit TWAIN manager too**: the TWAIN Working Group's `TWAINDSM.dll` 2.5.1 (x86) into `C:\Windows\SysWOW64`,
  when it is missing or older, as a shared file that the uninstall leaves in place, beside the 64-bit one in `System32`.
- **Not through the helper (a follow-up):** the older scanning calls (the `EZTwain` facade: the document scan, Twain Multi, the legacy
  Mount/Acquire loop that runs while the capture session is off or its settings are not saved, and Windows' "Select Source" dialog) run in
  the program's process only. A device set to a 32-bit-only source gets, there, "The TWAIN source "..." has only a 32-bit driver. In this
  64-bit program it runs through the 32-bit helper in the capture session only (...); install the source's 64-bit TWAIN driver to scan
  with it here." (section 9).

## 2. The design

```
 64-bit program                                                     32-bit helper (Helper32\, its own x86 runtime)
 ------------------------------------------------------------      ------------------------------------------------
 CaptureSessionController / FrmTestCapture
   TwainCaptureSessions.Create()  (ImagingCapture)
     TwainCaptureSessionRouter.Open(stored choice)
       1. TwainCaptureSession (in process, System32\TWAINDSM.dll) opens it, by the exact name; it waits for
          this process's sessions that are closing that source and enumerates on its own STA worker
       2. only if that DSM is missing or lists no such source: TwainSourcePath.ResolveNotNative
          does the 32-bit DSM list it (ListSources through the helper)?
                                   -> TwainHelperCaptureSession ===== named pipe (S3a-13) =====> TwainModule
                                        pump thread: commands in order, Poll          TwainHelperServer
                                        twin TwainCaptureSession (quarantine)           TwainCaptureSession (STA worker,
                                                                                         proxy window, SysWOW64\TWAINDSM.dll)
```

- **Where the code is.** Everything on both sides is `ImagingDeviceManager\Helper32\` (the program's library), compiled into the helper from
  its source as the rest of the library's TWAIN code (`OpenPmsDentalHelper32.csproj` links `ImagingDeviceManager\**\*.cs` but the `EZTwain`
  facade and `PdfPageWriter`, and ImagingCapture's metadata parser): the helper references no project, so it keeps its own x86 runtime, and
  the session it runs is the program's own `TwainCaptureSession`, which S3a-12 made pointer-size safe. Its TWAIN structures have their x86
  sizes there (checked from the running helper, section 8).
- **The choice** (`TwainCaptureSessionRouter` and `TwainSourcePath.ResolveNotNative`, decision 23's rule as `NativeFirstChooser.Decide`
  has it): at each open, from what the managers have then, decided by opening, never by enumerating outside a session (section 2.1). An
  in-process session opens the source on the program's own DSM, by the exact name (the whole stored text first, then its name without the
  marker): open, or failed there for any reason but "no DSM" or "no such source listed" (busy, timed out, refused by the source gate,
  `MSG_OPENDS` failed), that is the answer: a source the 64-bit DSM lists never runs in 32-bit. Else the 32-bit DSM lists it (the helper's
  `ListSources`, only when a 32-bit DSM file exists: `SysWOW64\TWAINDSM.dll` or the legacy `twain_32.dll`): the helper. Else this
  process again by the name without the marker, whose session reports the source not found (or opens a source whose name starts with it)
  as before S3b-8; for a 32-bit choice the open fails with the 32-bit side's reason instead (the DSM is missing, the helper failed or
  refused while listing). An unmarked choice (stored before S3b-8, which is every choice the 32-bit program stored) gets the helper's
  reason too when a 32-bit DSM is installed and the helper could not list its sources (missing or quarantined, did not start, crashed,
  timed out, or refused while another of its capture sessions is open: `TwainSourceResolution.Helper32ErrorText`): the in-process open by
  the name still runs first, and only when it also finds nothing (or the 64-bit DSM is missing) does the open fail with Other and "The
  TWAIN source "..." is not listed by the 64-bit TWAIN data source manager, and the 32-bit sources could not be checked: <the helper's
  reason>", also in the capture log, instead of "not found ... Check Setup > Imaging > Devices" (review fix 3, `net10/s3b8-3`). With no
  32-bit DSM at all an unmarked name the 64-bit DSM does not list is still "not found". A 32-bit program never uses the helper and opens
  by the name as before.
  The capture log records the choice and why (`TWAIN source "...": the 32-bit helper, because only the 32-bit TWAIN data source manager
  (TWAINDSM.dll) lists "..."`).
- **The stored choice** (`TwainSourceChoice`): `ImagingDevice.TwainName` holds the ProductName for a source of the program's own DSM, as
  before, and `<ProductName> (32-bit TWAIN)` for one only the 32-bit DSM lists, so the choice records its DSM. The ProductName (at most 32
  characters, `TW_STR32`) without the marker is what is opened and what the source gate (`[Twain] AllowedSources`) compares; the launcher's
  gate check reads it so (`TwainSourceChoice.GetProductName`). The Test capture record names the stored text (the row's value, as
  before) and the driver build the source reports, so a record made through the helper stays tied to that 32-bit driver: when the vendor's
  64-bit driver appears, the session runs it natively and the record no longer matches until Test capture runs again.
- **The router** (`TwainCaptureSessionRouter`): what the launcher (`CaptureSessionServices.CreateDefault`) and Test capture create now. It
  keeps SessionGuid, QuarantineContext and FuncReadMetadataKeys until Open, gives them to the in-process session it opens first and, when
  the helper runs the source, to the helper's session, which then becomes `Inner`; it forwards only `Inner`'s events; from then on every
  member is `Inner`'s. A BeginClose or Dispose while it is still choosing (the window closed) opens nothing more.
- **The helper's session** (`TwainHelperServer`): a whole `TwainCaptureSession` on the helper's DSM, with its STA worker thread, message loop
  and proxy window (the window the DSM and the source need), the source's own UI, the state 4 negotiation (`CAP_XFERCOUNT`, `ICAP_XFERMECH`
  memory transfer and `ICAP_BITDEPTH` 16/14/8, `ICAP_EXTIMAGEINFO`), `DAT_EXTIMAGEINFO` in state 7 (`TWEI_TWAINDIRECTMETADATA`), the safe
  stop order with the bounded wait after a refused disable, the journal copy of every image before it is raised, the quarantine of what
  arrives after BeginClose and the capture log, all under `%ProgramData%\OpenPMS-Dental\Imaging` (the same user, the same folders as the
  program). The metadata keys of the sidecars come from the helper's copy of `CaptureMetadataParser`, the parser the program gives its
  sessions. The server only queues what the session raises, keeps each image's pixels until the program takes them, and maps the program's
  enable ids to the session's (they are equal unless an enable is refused).
- **The program's side** (`TwainHelperCaptureSession`, `ITwainCaptureSession`): Open sends the open and waits for it (OpenTimeout plus 45 s
  for the helper's start). Then a pump thread sends the posted commands (Enable, RequestRedelivery, Disable, BeginClose, the quarantine
  context) in order and polls; it raises what the helper's session raised, in order, with the program's Tags (they never cross) and each
  image with its pixels, read in pieces of at most 8 MB. Enable returns the program's enable id at once and lets the helper bring the
  source's window to the foreground (`AllowSetForegroundWindow` for the helper's process, without the client's lock). BeginClose keeps
  TwainCaptureSession's rule: no ImageAcquired once it has returned; an image the helper raised before it learnt of the close is quarantined
  in the program and raised as ImageQuarantined, its journal copy marked Delivered=Quarantine. QuarantineImage and ConfirmRedeliveredJournalCopy
  run in the program's process on a twin `TwainCaptureSession` that is never opened (`SetTwinOf`: the helper session's source, options and
  source info), with the same record the helper wrote, so they also work after the helper is gone. The source info's DSM name says
  "(32-bit, in the helper OpenPmsDentalHelper32)", which Test capture shows.
- **Its own helper process** (`TwainHelperChannel.Default`, ImagingCapture): a `Helper32Client` of its own, not `Helper32Client.Default`.
  A TWAIN session polls several times a second for as long as it is open; a call of another module that waits for the user (Topaz's signing
  window, QuickBooks' access question, up to 30 minutes) would hold the shared client and stall the capture, and a TWAIN driver that crashes
  ends only this helper. Both helpers are children of the program, in its job object, and end with it (S3a-13 section 3).

### 2.1 No enumeration outside a session (review fix, `net10/s3b8-2`)

The first version chose the path in `TwainSourcePath.Resolve`, on the thread that called the router's Open (a thread-pool thread of the
session window or Test capture), by listing the program's 64-bit DSM in process. Opening a DSM is not a cheap read: in TWAINDSM 2.5.1
(the approved source, `TWAIN_DSM/src/apps.cpp`) `MSG_OPENDSM` adds the application and loads every installed driver, calling each one's
`DS_Entry` for its identity, and the DSM has no lock. That listing ran before `TwainCaptureSession.Open`'s wait for a session of this
process that is still closing the source (which exists so that its `MSG_CLOSEDS` comes before the next `MSG_OPENDS`), on another thread
than that session's worker: when the window starts over after a failed or timed-out open, or Test capture runs again, the new open called
into the same sensor driver and the same DSM tables while the old worker was still in `MSG_DISABLEDS` or `MSG_CLOSEDS`. It also listed the
drivers twice on every open.

Now nothing enumerates the program's DSM on the open path but the in-process session itself, after its wait, on its own STA worker; the
router asks the helper only after that session found no such source (`TwainCaptureOpenResult.IsSourceNotListed`, or `NoDsm`).
`TwainSourcePath.ListNative` is for the device list only. The in-process sessions wait for one another by the ProductName without the
32-bit marker, so the router's first open of the whole stored text waits too. In the helper, `TwainHelperServer.ListSources` first waits
(at most 30 s) while a session of the helper is closing, so that its `MSG_DISABLEDS` and `MSG_CLOSEDS` come first, and refuses with the
reason ("... has the TWAIN source "..." open. Close that capture window first.") while one is open and not closing: its worker may call the
DSM at any time. The helper keeps every session it created in that list until it has closed, also one that `Release` or a failed open
dropped after a bounded wait. The device list's 32-bit part therefore shows that reason while a 32-bit source is in use; the 64-bit part
lists as before (the device list's native listing next to an open in-process session is as it was before S3b-8).

Tests: `Router_AnotherSessionClosingTheSource_NoDsmEntryBeforeItsCloseDs` and `HelperListSources_WaitsForAClosingSession_RefusesWhileOneIsOpen`
(section 8), on a fake DSM that records the thread of every `DSM_Entry` and holds `MSG_DISABLEDS` at a gate.

## 3. The protocol (TWAIN module, `TwainHelperCommands`, version 2)

The helper's protocol does not change (S3a-13 section 3): one new module, `Twain`. Strings in the request's arguments, structures in its
byte field, written by `TwainHelperWire` (little-endian; a string a presence byte and UTF-8, so null and "" stay apart; a list a count, -1
for null; a nullable value a presence byte; a DateTime its `ToBinary`; a double its bits; every public property but Tag; bounds checked
before any allocation).

| Command | Arguments | Data in | Results / data out |
|---|---|---|---|
| `Hello` | | | version (2; 1 was the first version, without the open result's `IsSourceNotListed`), the helper's bitness ("32"), the DSM file it would load, the sizes of `TW_USERINTERFACE` and `TW_IMAGEMEMXFER` there (8 and 38) |
| `ListSources` | | | the DSM's library name and error text; data: every source (ProductName, manufacturer, family, version). Waits first (at most 30 s) while a session of the helper is closing; while one is open and not closing: no sources and the reason, nothing called (section 2.1) |
| `Open` | session id, ProductName, SessionGuid, "1" to read the metadata keys, a test capture folder ("" in production; honoured only with the test DSM), PatNum, patient name | `TwainCaptureOptions` (with the internal tick and refused-disable wait) | "1"/"0"; data: `TwainCaptureOpenResult` with the source info and `IsSourceNotListed`. Blocks until the source is open or failed. A failed open leaves no session |
| `Enable` | session id, the program's enable id, "1" for a redelivery | `TwainEnableRequest` without Tag | the helper session's enable id ("0": refused, and the program ends it with Refused) |
| `Disable` | session id, the stop reason | | |
| `BeginClose` | session id | | |
| `SetQuarantineContext` | session id, PatNum, patient name | | |
| `Poll` | session id, wait in ms (at most 200) | | "1" when the session has ended and every event is taken; data: the events in order (status, ended, image acquired, image quarantined, log line; an image without its pixels, with their payload id and length) |
| `ReadData` | session id, payload id, offset, count (at most 8 MB) | | data: those bytes; the payload is freed after its last byte |
| `Release` | session id | | the session is closed (bounded wait) and forgotten |

The program sends `Release` when a Poll says the session ended. Every call has a timeout: Open the open timeout plus 45 s, the others 30 s;
the listings 60 s per call.

## 4. The helper's failures end the session cleanly

| What | What the program sees |
|---|---|
| The helper is missing or does not start (at the listing or the open) | A 32-bit choice: the open fails with "The 32-bit helper could not list the 32-bit TWAIN sources: The 32-bit helper program OpenPmsDentalHelper32.exe was not found at ..." (or the start failure); an unmarked choice that the 64-bit DSM does not list either fails the same way: "The TWAIN source "..." is not listed by the 64-bit TWAIN data source manager, and the 32-bit sources could not be checked: ..." (also when the helper times out while listing or refuses because another capture window has a 32-bit source open), not "not found". Nothing stays open |
| The helper crashes during the session (or between two calls and is replaced: another process id answers) | Every running enable ends with Reason Error, StopReason Error, SourceMayHoldImages (images the helper held were not received: "do not re-expose yet; look for it in Unassigned captures"), then StatusChanged Closed; the session is closed (WaitForClose returns), Enable returns 0. The capture log has the reason. The journal copies the helper wrote before it raised each image stay for recovery |
| The helper stops answering (a call's timeout) | The same, "stopped answering ... and was ended": the helper client kills the helper (S3a-13 section 3) |
| The helper lost the session (it was started again) or answers with an error | The same, "failed during the capture session"; the helper is asked to release it |
| A listing hangs | The device list still has the 64-bit sources and the reason; the helper is ended after the timeout |

## 5. The setup (the owner's "32-bit TWAIN manager: yes")

- `installer/OpenPmsDental.iss`: `Source: "{#TwainDsm32File}"; DestDir: "{sys}"; Flags: sharedfile uninsneveruninstall restartreplace
  32bit`: into the 32-bit system folder, `C:\Windows\SysWOW64`, installed when it is missing or older (Inno Setup compares the file
  versions; no `ignoreversion`), a shared file the uninstall leaves in place, counted in the 32-bit view of SharedDLLs. **Not
  `{syswow64}`**, as the package text first named it: with `sharedfile`, Inno Setup's documentation (the `sharedfile` flag, and ISCC's
  warning "DestDir should not be set to "{syswow64}" when the "sharedfile" flag is used", seen in the first dry run) asks for `{sys}` with
  the `32bit` flag, which is the same folder but counts the file under the path every 32-bit installer uses (`C:\Windows\System32\...`
  as a 32-bit process sees it); `{syswow64}` would start a second count for the same file, which a TWAIN driver's uninstall could take to
  zero and delete the DSM. `TwainDsm32File` defaults to `bin\setup-files\x86\TWAINDSM.dll`.
- `tools/Build-Release.ps1`: `Get-TwainDsm -Bits 32` takes `dsm_020501/windows/32/TWAINDSM.dll` from the approved download
  (`od-tools\downloads\s3b7-twaindsm-20261116\dsm_020501.zip`, not downloaded again), checks its SHA-256
  (`cee9a6ff8026dde09eda9f892c57cc928d42e4a4d22bb740fe38ee6e91797a28`), version 2.5.1.0, PE machine 0x14C and TWAIN Working Group
  signature like the 64-bit one, writes it to `setup-files\x86\TWAINDSM.dll`, passes `/DTwainDsm32File=`, and requires it in the setup's
  packed list. `-ListFiles` lists `setup|x86\TWAINDSM.dll` after `setup|TWAINDSM.dll`. New: `-WriteSetupFiles <folder>` writes and checks
  both setup files only (for the tests).
- `tools/Test-Installer.ps1` (ASCII): checks `C:\Windows\SysWOW64\TWAINDSM.dll` after the install and after the uninstall (x86, 2.5.1.0 or
  later, the TWAIN Working Group's signature) and treats it exactly as the 64-bit DSM: its count in
  `HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\SharedDLLs` (under the System32 name, `$TwainDsm32CountName`) saved first
  and written back (or deleted) at the end; the file
  deleted only when none was there before; an older one stays replaced. The header says so.
- `THIRD-PARTY-NOTICES.txt` (TWAIN: both bitnesses, the 32-bit helper carries the TWAIN code too) and `docs/develop/release-process.md` (step 4,
  what the setup installs) name it. The source archive already carries `third-party-source/twain-dsm-2.5.1.zip`, the source of both.

## 7. Pointer sizes (net10-plan section 7)

The helper runs the same TWAIN code as the program, in a 32-bit process: S3a-12's x86 column. `TwainHelperProcessTests` reads the sizes
from the running helper (`TW_USERINTERFACE` 8, `TW_IMAGEMEMXFER` 38) and the test process's (12 in x64), and every capture test through the
helper drives the fake DSM with x86 pointers: the memory transfer's strips, the DSM's memory functions (`DAT_ENTRYPOINT`), the
`TW_EXTIMAGEINFO` read, the message loop's `MSG`. The x64 columns stay ImagingDeviceManagerTests' (S3a-12 section 10), green in x64.

## 9. What still needs the clinic's real devices, and the follow-ups

- **No real 32-bit source has run through the helper.** At the clinic (or on a test PC with a sensor whose vendor ships only a 32-bit
  TWAIN driver): the Twain Name list shows `<name> (32-bit TWAIN)`; Test capture through the helper (its DSM line says "32-bit, in the
  helper"); the source's own window opens in front of the program; a capture session with the sensor (the 8-bit and, once allowed, the
  16-bit path); Task Manager shows a second `OpenPmsDentalHelper32.exe` (32-bit) while the session runs, and none after the program closes;
  ending that helper during a session shows the message and nothing hangs; runbook section 12.1 step 1 records which manager is in use.
- **The vendor's 32-bit driver in a .NET 10 x86 process**: the helper is a .NET 10 process; a driver that needs something of the .NET
  Framework in its own process (rare for a native TWAIN source) would fail there. The clinic run shows it.

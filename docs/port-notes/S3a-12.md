# Port note: S3a-12 (pointer-size-safe native code and registry views)

Package S3a-12 of stage 3a, wave 3 (the first of it), of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S3a-12 row,
decision 19): branch `net10/s3a12-1` from `main` (`303533270`). The program stays x86 on .NET Framework 4.8; this package makes the native
code it calls correct in a 64-bit process too, and proves the TWAIN and DirectShow layers in x64 test runs on .NET Framework (the lane's x64
test build). Every change is a no-op for today's x86 build, with one intended exception (section 8: the image import window's Snipping Tool
folder had its test reversed). No schema change, no package, no download, no new DLL; no program was started.

Commits: `4d27edb9a` (the code), `b643f6e9b` (the tests and the source scan), and this note with the plan's status line.

## 1. What breaks in a 64-bit process

- A pointer, a handle, `WPARAM`, `LPARAM`, `LONG_PTR`, `UINT_PTR` or `SIZE_T` declared as `int`/`uint` (or an enum): in a 64-bit process the
  native side reads 8 bytes. A smaller managed argument arrives without its upper half (in practice zero-extended, so -1 arrives as
  0x00000000FFFFFFFF); a smaller structure field moves every field after it.
- `IntPtr.ToInt32()` throws `OverflowException` in a 64-bit process when the value does not fit an int
  (https://learn.microsoft.com/dotnet/api/system.intptr.toint32).
- Hand-coded sizes and offsets of a structure that holds a pointer.
- Entry points that exist in one bitness only: `SetWindowLongPtr`/`GetWindowLongPtr` are exported by 64-bit user32 only; in a 32-bit process
  winuser.h maps the names to `SetWindowLong`/`GetWindowLong` (https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-setwindowlongptrw).
- WOW64: a 32-bit process on 64-bit Windows sees the 32-bit registry view and the 32-bit system folder (SysWOW64 behind the name System32);
  a 64-bit process sees the 64-bit ones (https://learn.microsoft.com/windows/win32/winprog64/file-system-redirector,
  https://learn.microsoft.com/windows/win32/winprog64/shared-registry-keys).

Return values narrower than the native type are safe (the low 32 bits of the register are read), so an `int` result for an `LRESULT` or
`UINT_PTR` is a verdict "OK" below wherever the value is small.

## 2. TWAIN (`ImagingDeviceManager/TwainProtocol`)

### 2.1 The structures against the TWAIN 2.x header

Source: `twain.h` of TWAIN 2.x (the TWAIN Working Group's public header) and the TWAIN Specification 2.4 (chapter 8, data structures).
On Windows the header packs with `#pragma pack(2)` in both bitnesses; `TW_HANDLE`, `TW_MEMREF` and `TW_UINTPTR` are pointer-sized;
`TW_UINT32`/`TW_INT32` are `unsigned long`/`long`, 4 bytes on Windows in both bitnesses (LLP64), so `TW_IDENTITY.Id` stays 4 bytes there;
`TW_STR32` is 34 bytes. The declarations in `TwainStructs.cs` already used `Pack=2` and `IntPtr` for every pointer-sized field: no field
changed; the summaries now give both sizes. The table is the one `TwainProtocolTests` asserts (`_listSizes`, `_listOffsets`), chosen by
`IntPtr.Size`:

| Structure | x86 size | x64 size | Offsets read (x86 / x64) |
|---|---|---|---|
| `TW_FIX32` | 4 | 4 | |
| `TW_VERSION` | 42 | 42 | |
| `TW_IDENTITY` | 156 | 156 | Version 4, ProtocolMajor 46, SupportedGroups 50, Manufacturer 54, ProductFamily 88, ProductName 122 (both) |
| `TW_USERINTERFACE` | 8 | 12 | hParent 4 / 4 |
| `TW_EVENT` | 6 | 10 | TWMessage 4 / 8 |
| `TW_PENDINGXFERS` | 6 | 6 | EOJ 2 / 2 |
| `TW_STATUS` | 4 | 4 | |
| `TW_STATUSUTF8` | 12 | 16 | Size 4 / 4, UTF8string 8 / 8 |
| `TW_CAPABILITY` | 8 | 12 | hContainer 4 / 4 |
| `TW_IMAGEINFO` | 42 | 42 | BitsPerSample 18, BitsPerPixel 34, PixelType 38 (both) |
| `TW_SETUPMEMXFER` | 12 | 12 | |
| `TW_MEMORY` | 12 | 16 | TheMem 8 / 8 |
| `TW_IMAGEMEMXFER` | 38 | 42 | BytesPerRow 2, BytesWritten 22, Memory 26 (both) |
| `TW_PALETTE8` | 1028 | 1028 | |

The capability containers (`TwContainer`: `TW_ONEVALUE`, `TW_ENUMERATION`, `TW_RANGE`, `TW_ARRAY`) hold `TW_UINT16` and `TW_UINT32` only, so
their hand-coded offsets (2, 6, 10, 14, 18) are the same in both bitnesses: checked, no change. A new test (`Structs_TableCoversEveryTwainStruct`)
fails when a `TW_` structure is added without a row.

**`TW_INFO.Item` and `IsItemHandle`.** `Item` is a `TW_UINTPTR`, 8 bytes in a 64-bit process. The specification's rule (2.4 p.8-43) names a
size, "four bytes": data of up to four bytes is in the field, more is a handle the application frees. The rule was written when the field was
4 bytes wide; it is kept as written in both bitnesses (`TwExtImageInfo.MaxInlineItemBytes=4`), so 5 to 8 bytes of data (two `TW_UINT32`, for
example) are still a handle in a 64-bit process. Reading "fits the field" as 8 bytes there would make the application free data it did not
get as a handle if a source follows the specification; the other reading leaks a handle only if a source stores 5 to 8 bytes inline. The
program asks for two items only (`TWEI_PIXELFLAVOR`, a `TW_UINT16`, and `TWEI_TWAINDIRECTMETADATA`, a `TWTY_HANDLE`), neither of which falls
between 5 and 8 bytes; a value in the field is read from its low bytes (`Item.ToInt64() & 0xFFFF`), which is right for an 8-byte field too
(`ExtImageInfo_InlineItemReadsTheLowBytes`). The `TW_INFO` reads of `TwainSessionCaptureTransfer.ReadExtImageInfo` use `Marshal.SizeOf` and
`Marshal.StructureToPtr`/`PtrToStructure` at `TwExtImageInfo.GetInfoOffset`: checked, no change.

### 2.2 MSG

`NativeMethods.cs` had the offsets of a 32-bit `MSG` by hand (hwnd 0, message 4, wParam 8). They are now the offsets of a declared
`NativeMethods.MSG` (winuser.h, natural alignment: `HWND`, `UINT`, `WPARAM`, `LPARAM`, `DWORD`, `POINT`;
https://learn.microsoft.com/windows/win32/api/winuser/ns-winuser-msg), read with `Marshal.OffsetOf`:

| Field | x86 | x64 |
|---|---|---|
| hwnd | 0 | 0 |
| message | 4 | 8 |
| wParam | 8 | 16 |
| lParam | 12 | 24 |
| time | 16 | 32 |
| pt | 20 | 36 |
| size | 28 | 48 |

`MsgBufferSize` stays 64 bytes, which holds either. The users (`TwainSessionStop.PumpMessages` and its WM_NULL message for
`MSG_PROCESSEVENT`, `TwainCaptureSession`'s quit check, the test fakes) read through the same names, so they needed no edit; the quit exit
code is the low 32 bits of `wParam` (`PostQuitMessage` takes an int), right in both.

**The x64 hang was this.** On `main` the x64 run of ImagingDeviceManagerTests stopped after 87 tests until the lane's five-minute limit ended
it. In a 64-bit process the message loop read `message` at offset 4, the upper half of `hwnd` (zero), so it never saw a `WM_TIMER`: neither
the tick that checks for a stop request nor the loop timeout (`LoopTimeoutMilliseconds`, "a broken test fails instead of hanging") ever
fired, and the first test that waits on the loop waited for ever. With the declared `MSG` all 534 tests pass in x64 (section 10).

### 2.3 The owner window

`ProxyWindow.AttachTo` set `GWL_HWNDPARENT` with `SetWindowLong(..., hwndRoot.ToInt32())`. It now calls `NativeMethods.SetWindowLongPtr`,
which calls user32's `SetWindowLongPtr` in a 64-bit process and `SetWindowLong` in a 32-bit one, both declared with `IntPtr` (in a 32-bit

### 2.4 Loading the Data Source Manager

`NativeTwainDsm.Load` refused a 64-bit process ("TWAIN scanning requires a 32-bit (x86) process"). It no longer does. `GetCandidatePaths()`
now takes the bitness (`GetCandidatePaths(bool is64BitProcess)`, the parameterless form uses `Environment.Is64BitProcess`): a 32-bit process
tries, as before, `TWAINDSM.dll` beside the program, then in the system folder (SysWOW64 on 64-bit Windows), then `twain_32.dll` in the
Windows folder; a 64-bit process tries only `TWAINDSM.dll` in `Environment.SystemDirectory` (System32, the 64-bit DSM that S3b-7 installs),
never `twain_32.dll` (32-bit only) and no copy beside the program. A 64-bit process without it gets "No 64-bit TWAIN Data Source Manager is
installed (TWAINDSM.dll in ...)"; the x86 message is unchanged. `DSM_Entry` is a `WINAPI` (stdcall) function; x64 has one calling convention,
so the delegate's `StdCall` is right in both.

## 13. Lead notes at the merge (from the reviews)

- **A second x86 difference, a fix.** `Direct2d.WrapperHwnd_DeviceResourcesNeedRecreate` now reads a one-byte `bool`, matching the C++
  `bool` that `D2DWrapperHwnd.cpp:17` returns. Before, it read a four-byte BOOL, which could see garbage in the upper bytes as true. The
  gate's launch check therefore also watches Direct2D drawing (any window that draws through `Direct2d`: resize it, minimise it and restore
  it), next to the Snipping Tool fallback of section 11.
- **TW_INFO.Item, corrected reasoning (section 2.1).** The two failure modes run the other way round from what section 2.1 says:
  - If Item is read as 8 bytes and a source follows the 4-byte rule, a handle is taken as inline data: the handle leaks and a wrong value
    is read.
  - With the 4-byte rule the code keeps, a source that stores 5 to 8 bytes inline makes the program free something that is not a handle,
    which can crash.

  So the chosen rule has the more dangerous failure. It is acceptable only because neither item the program asks for falls in the 5-to-8
  byte range: `TWEI_PIXELFLAVOR` is 2 bytes and `TWEI_TWAINDIRECTMETADATA` is a handle. Before 3b, recheck the TWAIN 2.4/2.5 wording and
  the TWAIN Working Group's 64-bit sample source for the inline limit and record the answer here.
- **(int) casts of a window handle that reach native code (section 9 said none).** None can throw, because window handles are 32-bit
  significant on 64-bit Windows, but they are listed:

What 0.1.1 brings since 0.1, each in its section below (the roadmap's "Released in 0.1.1", [roadmap.md](../roadmap.md)); the notes of

- **tamper detection removed**: no row hashes, no warning triangles, no Security Hashes tool;
- **adoption** of Open Dental 26.2 databases, and of 25.3 databases whose version labels differ from their schema;
- **the camera**: every picture setting of its driver, shown readably, and camera buttons that change a setting or run a program action;
- **visuals in their own windows**: the camera session, the X-ray preview and the graphical perio chart;
- **imaging fixes**: Retake, drag and drop in view mode, and a mount type chosen when the mount is made;
- **fixes**: hover flicker, a tooltip crash, crash reports;
- **the new database file** without third-party copyrighted content.

## Before you install this version

**From 0.1:** no database change; it is a program update. Install 0.1.1 with its setup on the update server, as an administrator, start
the program there as an administrator and let it publish this version when it offers to. The other workstations pull it at their next
start, with no new setup; the .NET runtime is the same as 0.1's, so only the program part is downloaded
([release-process.md](../develop/release-process.md), "What the other workstations do").

**A new office** follows 0.1's "Before you install this version" ([v0.1.md](v0.1.md)): the database server must use TLS.

## Tamper detection removed

- **Open Dental's "Database Integrity" row hashes are gone.** The program no longer computes or checks the `SecurityHash` columns of
  appointments, claims, claim procedures, insurance subscribers and verifications, patients, payment plans and payment splits. The columns
  stay in the database with their values, so the schema still matches Open Dental's. The warning triangles in the edit windows, the
  integrity popups of the modules and Database Maintenance's Security Hashes tool are removed. Saving a patient no longer writes the row
  twice. Adoption no longer rehashes (runbook step 5 is no longer needed) and instead checks that every value is left as it was
  ([specs/remove-tamper-detection.md](../specs/remove-tamper-detection.md)).

## Adoption

- **An Open Dental database labelled 25.3.47.0 / 25.3.54.0 can be adopted.** Open Dental changes `DataBaseVersion` only when a convert step
  runs, so a database on Open Dental 25.3.54 reads `DataBaseVersion` 25.3.47.0 and `ProgramVersion` 25.3.54.0 while its schema is that of
  25.3.48. Adoption now accepts exactly that pair, and only when the schema equals the Open Dental 25.3.48 reference exactly (a patient
  portal's `patient._portal_active_email` aside); otherwise it refuses and names the differences. It is adopted as 25.3.48, and the
  adoption record (`ForkAdoptedFrom`), the adoption log and the security log keep the real labels. 24.3.63 and 25.3.48 databases are
  adopted as before.
- **An Open Dental 26.2 database can be adopted** (any 26.2.x point release, `ProgramVersion` on the same line and not below
  `DataBaseVersion`). Its schema must equal Open Dental's published 26.2 schema exactly (owner decision of 2026-11-26: the published
  documents are the schema); adoption checks it first and names any difference. It is adopted as 26.2.0 with the real labels recorded, and
  the fork migration steps add only the program's own tables: no Open Dental table or row is changed apart from the version preferences.
- The adoption tools follow the same rule: `AdoptionValidation migration-preview` says in its first line whether the versions are adoptable
  (with the schema check), `adopt` accepts the pair as its `--original`, and `startup-check` also models an Open Dental 25.3.54 client.
  `SyntheticData generate` and the rehearsal (`Invoke-AdoptionRehearsal.ps1 -VersionLabels office`) can label a synthetic database the same
  way. Runbook step 0.2 accepts 25.3.47.0 / 25.3.54.0.
- **Adoption keeps a patient portal column.** The patient portal column `patient._portal_active_email` and its unique key
  `portal_active_email_uniq` stay as they are (owner decision of 2026-11-25, replacing the earlier decision to drop them): a patient portal
  that added them relies on them for sign-in. The schema check allows them only with their exact known definitions, both after adoption and
  at the program's start. Two active patients still cannot share an e-mail address: saving one stops with a database error naming
  `portal_active_email_uniq` (a clear message comes with a later setting). Backups made by the program (Backup, and the backup before an
  update) skip the generated column, which the backup table computes again. `migration-preview` says the column and key are kept.
- **`claimpayment`'s table checksum may change on adoption** when no claim payment note is empty: the 26.1 step turns `claimpayment.Note`
  into `text`, and `CHECKSUM TABLE` follows the column type although every value stays the same. The rehearsal allows exactly that change.

## The camera: picture settings and buttons

- **Camera Picture Settings** (in a camera session, Camera settings... > Picture settings..., with the Setup permission): every picture
  setting the camera's driver offers, shown readably (exposure as "1/64 s", iris as "f/2.8", white balance in K, power line frequency as Off / 50 Hz / 60 Hz / Auto).
  Changes go to the camera at once; Save keeps them for this computer (`[Camera.Settings]`, applied each time the camera opens) and writes
  a Setup entry to the security log; Close puts back the values found.
- **Camera buttons**: Learn has an optional step, **Other buttons**. A learned button either changes a setting (toggle, one step up or
  down, a set value; the light, for example) or runs a program action: take a photo, next or previous slot, retake the last, freeze,
  record, pause the recording, pick teeth, end the session. A rest sensor can pause the preview or turn the light off while the camera
  rests. Learn and its test page show bits, not hexadecimal values.
- How-to: [set up the intraoral camera](../how-to/set-up-the-intraoral-camera.md).

## Visuals in their own windows

Each visual a patient may want to see opens in an ordinary window with minimise, maximise and close, so it can be dragged to another
monitor and maximised there ([specs/visuals-in-own-windows.md](../specs/visuals-in-own-windows.md)):

- **the camera session**: its full-screen button opens a sizable window, maximised on the module's monitor (it was borderless, without
  window buttons); its close button puts the session back into the module;
- **the X-ray capture preview**: a double-click opens it in its own window, which follows each new image and closes with the session;
- **the graphical perio chart**: no longer blocks the perio chart, and grows with its window.

## Imaging fixes

- **Retake**: in the capture session any filled slot can be tapped to retake it ("Retake slot N"; a second tap clears the choice), and
  the old image moves to the unmounted images only when the capture starts. In the Imaging module, the unmounted bar's Retake and the new
  "Retake X-ray..." on a slot's right-click menu open the capture session on that slot.
- **View mode**: an image can be dragged to another slot (moved, or swapped with the image there), with the same permission and signed
  image checks as Adj mode.
- **A mount holds X-rays or photos, never both**: "Mount holds" is chosen in Generate and in the mount editor, and every slot follows it.
- Capture settings show the capability names of `capture.ini`'s `[CapabilityNames]`.

## Fixes

- **No hover flicker** on text boxes, drop-down lists and scroll bars under Windows 11.
- **A tooltip no longer ends the program** when its window closes under the mouse ("This Visual is not connected to a PresentationSource").
- **Crash reports**: each unhandled exception writes one text file to `%LOCALAPPDATA%\OpenPMS-Dental\CrashReports` (the newest 50 are
  kept) with the exception, the program, the computer and the last actions; the error window names the file. An exception on a WPF window's
  UI thread now reaches the error window instead of ending the program without a message.
- **Setup proposes `openpms_dental`** as the database name.

## The new database file

`db/init/new-database.sql`, the database a new office starts with, holds no third-party copyrighted content: the medical code system
tables are empty (no ICD-9-CM titles), the program link buttons carry no vendor logos, and CDT-style procedure codes are named by their code
only. Program link passwords start blank. Open Dental's own GPL default texts and sounds stay. A database that already exists is not
changed.

## X-ray capture

As in 0.1 ([v0.1.md](v0.1.md), "X-ray capture: on for every new install"):

- **16 bits stay the default** (`Allow16Bit=1`): a computer takes 16-bit X-rays once a Test capture passed for its sensor.
- **No patient X-rays before the phantom comparison:** on the same line-pair and step-wedge phantom, at least the same line pairs and the
  same steps must be visible as in the current imaging program's image of that phantom, and left and right must match the phantom's lead
  markers for every sensor size; the dentist signs off against these criteria (`docs/admin/intraoral-capture-setup.md`, sections 1 and
  12).

## Known limitations

- **The setup is not digitally signed** (as 0.1; code signing is being set up), so Windows SmartScreen or Smart App Control may warn
  about it or block it. Compare its SHA-256 with `SHA256SUMS.txt` first: `Get-FileHash .\OpenPmsDental-0.1.1-Setup.exe -Algorithm SHA256`.
- **Patient X-rays** wait for the phantom comparison ("X-ray capture", above).
